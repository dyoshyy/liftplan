# テストの書き方

進め方の原則は `CLAUDE.md`（テストは先に書いて赤くなる理由を確認する／挙動を変えるときは削除ではなく反転させる）にある。ここに書くのは**具体的な型**。

## 1関数につき1テスト関数。ケースはテーブルへ

同じ関数のテストを `TestFoo_A` `TestFoo_B` `TestFoo_C` と分けない。`TestFoo` にまとめ、違いはケースで表す。

```go
func TestAddedWeight(t *testing.T) {
	cases := []struct {
		name       string
		exercise   *training.Exercise
		totalKg    float64
		conditions training.ConditionLog
		want       float64
	}{
		{
			// ここで体重を0と見なすと引き算が消えて added = total になり、
			// 自重種目に総負荷をそのまま処方する。
			name: "体重を一度も記録していないなら既定値で引く",
			// 77.5 − 0.95 × 70
			exercise: chinning(t), totalKg: 77.5,
			conditions: training.NewConditionLog(nil), want: 11.0,
		},
	}

	for _, c := range cases {
		t.Run(c.name, func(t *testing.T) {
			got := training.AddedWeight(
				mustWeight(t, c.totalKg), c.exercise, c.conditions, loadDay)

			if math.Abs(got.Kg()-c.want) > 1e-9 {
				t.Errorf("加重が %vkg。%v のはず", got.Kg(), c.want)
			}
		})
	}
}
```

- 変数名は `cases` と `c`（`tests` / `tt` ではない。既存に合わせる）
- `name` は日本語で、**検査していることを文で書く**。「正常系」「異常系」は名前ではない
- **期待値の根拠をケースにコメントで残す。** `// 77.5 − 0.95 × 70` のような式か、なぜその値でなければならないかの理由。テーブルにすると「なぜ」が失われやすいので、ここだけは冗長でよい
- 準備が構造的に違うケース（他とフィールドを共有できないもの）は、無理にテーブルへ押し込まず独立した関数にする

## 変異を実際に入れて、赤くなることを確認する

**頭の中で「これは守っている」と判断しない。手を動かして壊す。**

```bash
# 1. 実装を1箇所壊す
sed -i 's/^const defaultBodyWeightKg = 70$/const defaultBodyWeightKg = 0/' internal/domain/training/condition.go

# 2. 期待したテストが落ちるか見る
go test ./internal/domain/training/ 2>&1 | grep -E "FAIL:|^ok"

# 3. 必ず戻す
git checkout internal/domain/training/condition.go
```

先にコミットしてから壊すと、`git checkout` で確実に戻せる。

**実例。** 「負荷不明のセットを間引く実装に戻す」変異を入れたら、それを守るつもりで書いたテストが**緑のままだった**。カバレッジも残差も生の履歴で計算されるので、変換後の履歴が何件になろうと呼び出し側からは観測できなかった。同じことを検査するテストが既にあり、実質の重複だった。

## 「緑だが何も守っていないテスト」の型

このリポジトリで実際に出た3つ。

**出力に現れない契約を、外から検査しようとしている。**
呼び出し側から観測できない性質（内部で作る中間データの件数など）は、外部テストでは固定できない。→ 後述の内部テストで直接検査する。

**テストが自前で用意したデータだけで完結している。**
自重係数の実装で、テストは自分で `BodyweightFactor: 0.95` の種目を組み立てていた。シードに係数を入れ忘れていても緑のまま通り、**本番では機能が完全に無効**だった。データ側（シード・設定・マイグレーション）に値が入っていることは、別のテストで固定する。

**有無だけ見て値を見ていない。**
`if _, ok := set.Weight(); !ok { t.Error(...) }` は「重量が出ること」しか守らない。体重込みの誤った値が出ていても緑になった。**値か、少なくとも値が満たすべき不等式を検査する。**

## 非公開関数の契約は内部テストで固定する

このリポジトリのテストは原則 `package training_test`（外部テスト）。実装の詳細に寄りかからないため。

ただし**出力に現れない契約**はそれでは守れない。その1本だけ `package training` で書き、ファイル名を `*_internal_test.go` にして意図を明示する。

```go
package training

// effectiveHistory は非公開なので、この1本だけパッケージ内から検査する。
//
// 件数が保たれることは呼び出し側から観測できない。カバレッジも残差も生の
// 履歴で計算されるため、変換後の履歴が何件になろうと出力に現れない。
// だが件数が変わる実装に戻ると「やったはずのセットが消える」が復活する。
func TestEffectiveHistory_KeepsEverySet(t *testing.T) {
```

**冒頭に「なぜ外部テストでは書けないのか」を必ず書く。** 理由が無いなら外部テストで書けるはずで、内部テストにする必要がない。

## テストの意図はコメントに残す

このリポジトリのテストは、**何を守っているかと、守らないと何が起きるか**をコメントに書く。後から読んだ人が「これは消してよいテストか」を判断できるようにするため。

```go
// 体重を一度も測っていなくても、自重種目に重量が出る。
//
// 元は「体重が分からなければ推測せず本人に返す」として「自分で決める」を
// 出していた。だが「何kgでやるか」はアプリが答えるべき問いなので、既定体重
// 70kg で処方する。
```

挙動を変えて既存テストを反転させたときは、**元が何を検査していたか**を残す。消すと、なぜ変えたのかが失われる。

## 検収を疑う

「全テストが緑」は、**変更が出力を変えない場合にだけ**検収として意味を持つ。挙動を変える変更では緑は何も証明しない。

同様に「`git grep` が空になった」「行数が減った」も、正しい実装と何もしない実装を区別しない。**その検収は null 実装でも満たせないか**を毎回疑う。

実例として、推定の入口を一本化する案では `MedianOneRepMax` に引数を足して「渡し忘れがコンパイルエラーになる」ことを検収にしようとしたが、ゼロ値を渡すだけで全テストが緑になった。コンパイラが強制するのは「渡すこと」であって「正しく渡すこと」ではない。
