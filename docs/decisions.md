# 実装中の自己判断ログ

実装計画に書かれていなかった、あるいは計画と異なる判断をした箇所と、その根拠。
判断が割れうるものは別エージェントに客観評価させ、その結果も記録する。

## D-001: Go のバージョンを 1.23 ではなく 1.26.3 にした

**計画の記述:** Go 1.23

**実際:** 1.26.3

**根拠:** 開発機の mise に 1.23 が入っておらず、`mise use -g go@1.26.3` が提示された。計画が 1.23 を指定した理由は「`net/http` のメソッド付きパターンマッチ（1.22 以降）が使えること」であり、1.26.3 はこれを満たす。より新しいバージョンを避ける理由が無いため、環境にあるものを採用した。`mise.toml` をリポジトリにコミットし、バージョンを固定している。

**影響範囲:** なし。標準ライブラリのみを使うため、互換性の懸念は無い。

## D-002: 依存方向テストの許可リストに `context` と `sync` を最初から入れた

**計画の記述:** Task 1 では最小の許可リストとし、`context` は Task 19 で追加する

**実際:** 最初から `context` と `sync` を含めた

**根拠:** 許可リストを小刻みに広げても守られる不変条件は変わらず、PR ごとにテストファイルを触る差分ノイズが増えるだけ。`context` はリポジトリインターフェースで必須になることが計画時点で確定しており、`sync` はテストの並行検証で使う。どちらも「外部への依存」ではなく、ドメイン層が外側を知らないという本来の制約には影響しない。

**影響範囲:** 検査の厳密さは変わらない。外部モジュール（ホスト名を含む import）と、自リポジトリの domain 外パッケージは引き続き弾かれる。

## D-004: Date の内部表現を time.Time から年月日の整数に変えた（敵対的検証の結果）

**計画の記述:** `Date` は `time.Time` を内包し、UTC 午前0時に正規化する

**実際:** `struct { year int; month time.Month; day int }`

**きっかけ:** PR #2 への敵対的レビューで、`time.Time` を内包することに起因する問題が3つ挙がった。

1. **`==` と `Equal()` が食い違う。** マップキーは `==`（wall/ext/loc の全フィールド一致）、`Equal()` は瞬間比較。ロケーションだけ違う値で `Equal()==true` かつ `==` が false になり、キーが割れる
2. **正規化の抜け穴。** 同一パッケージ内から `Date{t: 任意のtime.Time}` を書ける。計画では Task 3〜16 が全て同じパッケージに着地するため、将来の自分が踏む経路。正午の time.Time を入れると `String()` は正常なのに `DaysSince` が丸め方向で非対称になり、壊れていることが観測できない
3. **`DaysSince` が ±106751日（約292年）で飽和する。** `time.Duration` は int64 ナノ秒。ゼロ値との差分が 106751 という一見もっともらしい値を返す

整数表現にすると3つとも構造的に消える。加えて `Weekday`/`AddDays`/`DaysSince` を通日（Howard Hinnant の days_from_civil）で実装することで `time.Duration` への依存自体が無くなった。

## D-005: NewDate をエラーを返す形にし、MustDate をテスト専用として追加した

**計画の記述:** `NewDate(year, month, day) Date`（エラーを返さない）

**実際:** `NewDate(...) (Date, error)` + `MustDate(...) Date`

**判断の経緯:** 計画の Global Constraints は「値オブジェクトは不変かつ自己検証。コンストラクタで検証してエラーを返す」と定めているのに、`NewDate` だけがこれに反して `2026-02-30` を黙って `2026-03-02` に正規化していた。ただし変更は後続の全タスクに波及するため、**別エージェントに客観判断を委ねた**。

エージェントの結論は案A（エラーを返す + MustDate）。決め手は次の3点だった。

- **内部表現が整数になった時点で、案B（正規化を維持）は「現状維持」ではなく「新規実装」になる。** 正規化を保つには `time.Date` を呼び戻すか、うるう年と月末繰り上がりを手書きする必要がある。一方「不正なら弾く」は比較2本で済む。安い方が実は検証する側だった
- **「呼び出し箇所100以上」は事実誤認だった。** 実測33箇所、うち計画コード側は11箇所で、その多くはテストのパッケージ変数（`var testDate = ...`）。パッケージ変数は `if err != nil` を書けないので、エラーを返すなら `MustDate` は必然
- **同パッケージの他の値オブジェクト（Weight, Reps, RIR ほか8種）は全て `NewXxx(v) (T, error)`。** Date だけ例外にすると、型を見て挙動を推測できなくなる

**MustDate の誤用対策:** 「テスト専用」を規約で守らせると必ず破られるため、`TestDomain_MustDateIsTestOnly` が AST を走査し、`_test.go` 以外での `MustDate` 使用を検出する。

**残る穴:** ゼロ値 `training.Date{}` はどんなコンストラクタ設計でも塞げない。対策として、ゼロ値に対する演算はゼロ値に閉じるようにし（`AddDays`/`WeekStart` はゼロ値を返し、`DaysSince` は0を返す）、`String()` が `"0000-00-00"` という**パース不能な文字列**を返すようにした。履歴に混入しても正常な日付に見えない。

## D-006: 「タイムゾーンを閉じ込める」ために FromTime を追加した

**計画の記述:** 記載なし

**きっかけ:** レビューの指摘。`time.Time` から `Date` を作る API が無いため、Application 層が必ず `NewDate(now.Year(), now.Month(), now.Day())` と手で分解することになる。そのとき **どのタイムゾーンで分解するかの判断が型の外に漏れる**。

具体的な壊れ方：JST のユーザーが朝7時（前日22時 UTC）に記録を送ったとき、サーバーが UTC で分解すると前日の日付になる。すると週内セッション番号が1本ズレ、`WeekStart()` 上で前週に落ち、週ボリュームの残差が別の週に計上される。48時間ルールも1日甘くなる。

`FromTime(t time.Time, loc *time.Location) (Date, error)` を追加し、**ロケーションを引数で強制**した。暗黙に UTC やローカルを選ばせない。

## D-007: テストをミューテーションで検証した

レビューの最も重い指摘は「DST 不変条件を主張するテストが、その退行を検出できない」だった。`d.AddDays(i).DaysSince(d)` という自己整合的な式は、両辺が同じ壊れた算術を使うため常に通ってしまう。

そこで、テストを書いたあとに**実装を意図的に壊してテストが落ちるか**を確認した。

| 変異 | 検出したテスト |
|---|---|
| `Equal` を年だけの比較にする | `TestDate_EqualMatchesStructEquality` |
| `DaysSince` を `time.Duration` 経由に戻す | `TestDate_DaysSinceIsConsistentWithAddDays` / `TestDate_DaysSinceDoesNotSaturate` |
| 閏年判定から400年ルールを削る | `TestNewDate_RejectsCentennialNonLeapYear` |
| `FromTime` が loc を無視して UTC 固定 | `TestFromTime_UsesTheGivenLocation` |
| 週初を日曜起点にする | `TestDate_WeekStartIsMonday` / `TestDate_WeekStartInvariants` |

**以降のPRでも、テストを書いたら必ずミューテーションで検出力を確認する。** 通るテストを書くことと、壊れたら落ちるテストを書くことは別物。

## D-008: 列挙型の Valid を一覧から導出し、値をゴールデンテストで固定した（敵対的検証の結果）

**きっかけ:** PR #3 への敵対的レビュー。「ミューテーションで検出力を確認した」と主張していたが、**最も重要な変異を守れていなかった**。

**指摘と対応:**

| # | 指摘 | 深刻度 | 対応 |
|---|---|---|---|
| 1 | 表記規約（大文字・空白なし）しか見ておらず、`CHEST_UPPER` → `CHEST_CLAVICULAR` のような規約を保ったままの改名が素通りする。永続化される値なのに壊れても気づけない | 高 | 21+3+3 個の値をリテラルで固定するゴールデンテストを追加 |
| 2 | `ExerciseKind.Valid()` の switch と `AllExerciseKinds()` が独立の手書きリスト。switch にだけ追加すると素通りする。**Valid が緩くなる方向だけ無防備**という危険な非対称 | 中〜高 | `MuscleRegion` と同じく一覧から `Valid` を導出する構造に統一 |
| 3 | 定数を宣言して一覧に入れ忘れても検出されない。シードが参照した瞬間、コンパイル時でなく**起動時**に落ちる | 中 | `taxonomy.go` の const 宣言を AST で読み、一覧との差を検出するテストを追加 |
| 4 | `sortedRegions` が可変長引数のスライスをその場でソートし、`sortedValues(s...)` と書かれたら呼び出し側を破壊する | 低 | コピーしてから並べ替えるよう変更 |
| 5 | 「走査順が補助種目の選択結果に影響する」という根拠が事実と違う。後続の `topRegion` はその場でローカルソートしており、この一覧の順序は選択結果に届かない | 低 | コメントと PR 本文を訂正。ソート基準が「識別子の昇順」でなく「文字列値の昇順」である点も修正 |

**構造で消す方を選んだ理由（指摘2）。** テストを足して二重管理を検出することもできたが、そもそも二重管理をやめれば検出する対象が消える。`MuscleRegion` は既に一覧から `Valid` を導出しており、同じファイル内で守り方が不統一だった。

**Valid の特例に対する防御（指摘2の派生）。** 一覧から導出しても、`return validExerciseKinds[k] || k == "WARMUP"` のような特例を後から足すことはできる。この変異は最初の修正では検出できなかった。特例は必ずソース上の文字列リテラルとして現れるので、`taxonomy.go` の全文字列リテラルを集め、`Valid()` が true を返すものが一覧に載っているかを検査するテストを追加した。

**検証:** レビュアーが素通りさせた攻撃を再現し、修正後は検出することを確認した。

- 規約を保ったまま4つの値をリネーム → ゴールデンテストが8件検出
- 定数 `SERRATUS` を宣言して一覧に入れ忘れ → AST 検査が検出
- `Valid` に `|| k == "WARMUP"` の特例 → リテラル走査が検出

**教訓:** 「ミューテーションで確認した」と書くときは、**守りたい性質そのものを壊す変異**を選ばなければ意味がない。表記規約を壊す変異を検出できても、値の改名を検出できなければ、列挙型のテストとしては無内容だった。

## D-009: quantize を検証の前に移し、数値型に上限を入れた（敵対的検証の結果）

**きっかけ:** PR #4 への敵対的レビュー。`quantize`（浮動小数点残差を落とす処理）を**検証の後**に置いていたため、コンストラクタが自分で不変条件を破っていた。

**発見された壊れ方:**

```
NewWeight(1.8e302)  → err=nil, kg=+Inf   （quantize で v*1e6 がオーバーフロー）
NewIncrement(1e303) → err=nil, kg=+Inf   → RoundTo が NaN の Weight を生む
NewRatio(1e-7)      → err=nil, v=0       （quantize で0に潰れる）
```

`Weight` と `Reps` はクライアントの JSON 由来なので、`{"weight_kg": 1e303}` という正当な JSON で到達できる。しかも NaN は比較がすべて false になるため、以降の検証をすり抜けて静かに壊れる。テストのコメント自身が「NaN が1つでも通ると静かに壊れる」と書いていたのに、実装がその経路を開けていた。

`NewRatio(1e-7)` が 0 を返す方は、PR の主張そのものを崩していた。「`Scale` の引数を検証済みの `Ratio` に限ることで結果が0以下になる経路を型で塞いだ」と書いたが、**`Ratio` 自身がゼロになれる**ので塞げていなかった。強度0は `0kg のセットが処方される`ことを意味し、「履歴が無ければ重量を返さない（数字を捏造しない）」という設計を 0kg という捏造で貫通する。

**対応:**

| # | 指摘 | 対応 |
|---|---|---|
| 1 | quantize が検証の後にあり +Inf を作る | quantize を検証の**前**に移動 |
| 2 | quantize のアンダーフローでゼロ値と区別できない有効値ができる | 同上。下限を `1/quantum` にして量子化で潰れる値を弾く |
| 3 | Weight/Reps/RIR/SetCount に上限が無く int オーバーフローに到達する | 現実的な上限を設定（重量1000kg、レップ1000、RIR100、セット100、刻み50kg） |
| 4 | `RoundTo` のゼロ値 Increment ガードが「黙って丸めずに返す」 | エラーを返すよう変更。バーに載らない重量が処方されるより落ちる方がよい |
| 5 | `NewIncrement` の不正値テストが1本も無い（変異が生存） | 0・負・上限超のテストを追加 |
| 6 | エラーメッセージが一切検証されていない（HTTP 400 のボディになる） | 各コンストラクタのメッセージに項目名が含まれることを検査 |
| 7 | `Scale(Ratio)` は呼び出し側に `NewRatio(1-drop)` のエラー握り潰しを強いる | `Reduce(pct float64)` に置き換え。低下率を内部で丸めるのでエラーが要らない |

**maxRatio などの定数をゴールデンで固定した。** 「1.2 は通る／1.21 は落ちる」というテストだけでは、定数を 1.205 に変える改変を検出できなかった。`taxonomy` では値をゴールデンで固定していたのに、ここだけ緩かった。

**到達不能な分岐を消した。** `Reduce` に「結果が下限を割ったら丸める」というガードを入れたが、低下率の上限を 0.5 にしたことで到達不能になっていた（最小強度 1e-6 に 0.5 を掛けても量子化で切り上がる）。テストで殺せない分岐はデッドコードなので削除し、代わりに「どんな有効な入力の組み合わせでも0にならない」ことを性質テストで保証した。

**検証:** レビュアーが挙げた生存変異18種のうち、該当する12種を再実行し、すべて検出されることを確認した。

## D-010: RatioTo を削除し、Epley 式の適用範囲を制限した（敵対的検証の結果）

**きっかけ:** PR #5 への敵対的レビュー。

### 削除した API: `OneRepMax.RatioTo`

`x.RatioTo(y)` は英語として「x の y に対する比 = x/y」と読めるが、実装は `y/x` だった。ドメイン用語でも「対メイン係数」はバリエーション側の属性なので、呼び出し側は自然に `variation.RatioTo(main)` と書く。

問題は、**その誤用が現実の係数域で全部素通りする**こと。`maxRatio = 1.2` のガードは「1/r ≤ 1.2 ⇔ r ≥ 0.833」の範囲で無力になる。

| 実比率 | 逆に呼んだ結果 | 判定 | 処方重量 |
|---|---|---|---|
| 0.85（インクライン） | 1.176 | 通る | +36% |
| 0.90（ポーズスクワット） | 1.111 | 通る | +24% |
| 0.95 | 1.053 | 通る | +10% |

つまりガードが効くのは「そもそも起きにくい極端な係数」だけで、実運用で起きる誤用は全て通る。しかも `VariationRatioResolver` はエラー時に初期値へ戻す設計なので、値が妥当に見えるぶん誰も気づけない。

**この PR にも計画にも呼び出し元が無かった**（未使用API）ため、削除した。対メイン係数の算出は Task 10 で、分子分母が引数順から自明な形で実装する。

### 追加した制限: Epley 式の適用範囲

計画には無い判断。`maxReps = 1000` は「int オーバーフロー防止」としか言っておらず、Epley 式が妥当な範囲（〜10レップ前後）の制約がどこにも無かった。

| 記録 | 推定1RM | 0.81倍で処方 | 実績重量比 |
|---|---|---|---|
| 60kg×20 @RIR2 | 104.0 | 85.0kg | 142% |
| 40kg×50 @RIR0 | 106.7 | 87.5kg | 219% |
| 20kg×100 @RIR0 | 86.7 | 70.0kg | 350% |

高レップ・低重量のセット（カール、リアレイズ、入力ミス）が1本混ざるだけで、実際に扱った重量の 1.4〜3.5倍が処方される。中央値は「1セットだけの外れ値」には効くが、**高レップ種目は全セットが高レップなので中央値では守れない**。

限界までの総レップが 20 を超える記録からは推定しないことにした。通常のトレーニング（12レップ + RIR2）は通り、明らかに範囲外の記録を弾く境界。

### その他の修正

| 指摘 | 対応 |
|---|---|
| `WorkWeight` が 0kg を nil エラーで返す（粗い刻み × 軽い種目）。PR が防いだと主張した事象そのもの | 丸めて0になったらエラーにする |
| RIR 6以上の寄与を値で検証するテストが1本も無く、RIR を5で飽和させる変異が生存 | ゴールデンテストで RIR 6/10/18 の値を固定 |
| `quantize` を殺すテストが無く、`IsComparable` が空虚（同じ経路を2回回して比べているだけ） | 桁数の検査と、同じ意味の値が等しくなることの検査を追加 |
| 上限定数そのものを固定するテストが無く、`1e9` への緩和が生存 | 境界のゴールデンテストを追加。上限も 40000 → 2000 に縮小 |

### 後続タスクへ持ち越す課題

**教訓:** 検証結果を報告するときは、検証手順そのものが健全であることを先に確かめる。壊れた計測器で測った値を根拠として提示するのは、測らないより悪い。

### ブランク明けの危険な処方を塞いだ

`Estimate` は日付を一切見ていなかった。EWMA はセッション数だけで畳み込むため、**2セッションの間隔を3日から11ヶ月に変えても推定値が1ビットも動かない**（レビュアーの実測）。

`ForExercise` の絞り込みを「その種目を含む日」に緩める変異が生存した。同日にベンチとスクワットを記録すると、スクワットの重量がベンチの中央値に混ざり **+80% の過大処方**になる。

1. **初期値バイアス。** 最初のセッションが重み1.0で入る。シードの初回は重量未確定なのでユーザーが仮の値を入れるが、それが実力と乖離していると影響が長く残る。実力100kgの人が60kgと入れた場合、処方が正しくなるまで約10セッション（週2で5週間）。逆に重く入れた場合は1回目の処方が実力の134%になる。`VariationRatioResolver` の `minSessions` に相当するガードの要否を判断する必要がある
2. **閉ループの固定点。** 処方どおり完遂すると推定1RMが完全に同一値になり（`100 × (1+10/30) × 0.75 = 100` がグリッドに一致）、停滞判定が必ず真になる。漸進的過負荷の仕組みが無いと Task 15 で閾値をどう調整しても救えない

## D-015: 対メイン係数の算出方法を作り直した（敵対的検証の結果）

**きっかけ:** PR #11 への敵対的レビュー。設計レベルの致命的な欠陥が見つかった。

### 係数を掛ける意味が約分で消えていた

処方は `メインの推定1RM × 強度 × 係数`。係数を「現在のバリエーション1RM ÷ 現在のメイン1RM」で求めていたため、

```
処方 = mainORM × intensity × (varORM / mainORM) = varORM × intensity
```

**メインの推定1RMが完全に打ち消される。** 計画書が「バリエーション自身の1RMではなく、メインの1RMに係数を掛けるのが正しい」と明記していたことの、ちょうど逆を実装していた。

帰結は固定点。レビュアーの再現では、メインの推定1RMが12週間で 160→189kg に伸びる間、バリエーションの処方は **50.00kg のまま1グラムも動かなかった**。係数は 0.4167→0.3527 と下がり続け、ますます固定される。シードの 0.85 を使い続けた方が正しく追随するので、「学習」が機能を悪化させていた。

**修正:** 係数は「同じ時点で観測されたメインとバリエーションの組」の比を平滑して求める。各バリエーションセッションについて、その日までの情報だけでメインの推定1RMを出し、比を取り、古い順に EWMA で畳み込む。

これで、バリエーションが停滞してもメインが伸びていれば処方が押し上がる。テストで「バリエーション横ばい・メイン上昇」の履歴を作り、処方がバリエーション自身の1RM由来の重量を上回ることを固定した。

### 推定器が未来の記録を使っていた

修正の過程で見つかった別の問題。`Estimate(h, id, asOf)` は `asOf` を鮮度判定にしか使っておらず、**平滑化には履歴全体を使っていた**。過去のある時点の推定をやり直すと未来の記録が混ざる。

最初この欠陥のせいで、「メインが伸びたら処方も伸びる」テストが早い時点と遅い時点で同じ値を返し、修正が効いているか判定できなかった。`asOf` より後の記録を落とすようにした。

### 実測比の受容域を分離した

`NewRatio` の範囲（1e-6〜1.2）は「比率として成立するか」しか見ておらず、対メイン係数としては広すぎた。ベンチ200kgの人にラーセンプレス2.5kgを処方する係数（0.0139）が通る。メインの半分も挙がらないものはバリエーションではなく別の種目なので、実測の受容域を 0.5〜1.1 に分離した。

### 変異の粒度についての反省

レビュアーの指摘：「変異は『条件を1つ落とす』ではなく『条件の各項を1つずつ落とす』粒度で切ること」。

PR本文に「asOf を無視 → 検出」と書いたが、**片側ずつ潰すと両方とも生存**した。検出できるのは両側同時に潰したときだけで、テストが両方を同時に stale にしていたため。D-014 で「壊れた計測器で測るな」と書いた直後に、変異の粒度が粗いせいで同種の過大報告をしていた。

また、テストデータでバリエーションがメインに比例して伸びていたため、**核心の変異（EWMA済み1RMどうしの比に戻す）が生存**した。両方式が同じ答えを出すデータでは、方式の違いを検証できない。

### 等価変異として残したもの

## D-016: スロットの並びを変え、週の頻度上限を4に下げた（敵対的検証の結果）

**きっかけ:** PR #12 への敵対的レビュー。

### 設定頻度＞実施頻度でプログラムが恒久的に死ぬ

スロットは「その週の何本目か」で決まる。設定週4回のユーザーが週2回しか通わないと、先頭2つしか使われない。旧構成では先頭2つが両方バリエーションだった。

バリエーションのスロットではメイン種目そのものを実施しない（差し替える）ので、**メインリフト本体の記録が1件も増えない**。D-014 で追加した鮮度ガード（42日）が効いて、7週目に推定1RMが「古すぎる」と判定され、メインもバリエーションも全部の重量が未確定になる。

しかも回復経路が無い。週2回を続ける限り先頭2つしか引かないので、永久に直らない。皮肉なことに、正直に「週2回」と設定したユーザーは正常に回る。**「頑張るつもりで4回と設定した」ことだけが原因で壊れる。**

**修正:** 並び順を「強度の昇順」から「重要な役割ほど先」に変えた。標準スロットを必ず先頭に置くことで、週に一度でも通えばメインリフト本体を実施することが保証される。

| 頻度 | 旧 | 新 |
|---|---|---|
| 週3 | V(0.76) → S(0.81) → H(0.88) | **S(0.81) → H(0.88) → V(0.76)** |
| 週4 | V(0.76) → V(0.78) → S → H | **S → H → V(0.76) → V(0.78)** |

### 週の頻度上限を 7 から 4 に下げた

週5回以上は4スロット構成を巡回させていたが、レビュアーの指摘どおり破綻していた。

- テストが「強度は必ず昇順」と宣言していたのに、週5〜7回では成立していなかった。テストは `For()`（4要素）を見ていたので永久に気づけない
- 毎セッションで BIG3 すべてにスロットを割り当てる設計なので、週7回だと**1種目あたり27セット/週、BIG3合計81セット/週**になる。デッドリフトを週27セットこなす前提のプログラムは成立しない

上限を4にして巡回そのものを廃した。`For()` の要素数が頻度と一致することもテストで固定した。それより多く通う場合は、頻度を上げるのではなく補助種目の日を自分で足す。

### その他

| 指摘 | 対応 |
|---|---|
| `newSlotTemplate` の panic に AST ガードが無い（`MustDate` にはあるのに、隣のファイルが同じ規約ベースの防御に戻っていた） | panic する関数の使用可能ファイルを一覧で管理する検査に一般化。プローブで検出を確認 |

## D-017: 残差を週次の台帳に変え、補助スロット数を残差から導くことにした（敵対的検証の結果）

**きっかけ:** PR #13 への敵対的レビュー。

### 週目標が構造的に達成できなかった

旧設計は「週目標 ÷ 頻度」の固定値を毎セッション使い、そのセッションのメイン分だけを引いていた。週を通した台帳が無いため、**過不足が次に繰り越されない**。

補助種目は3セット固定なので、目標の小さい区分（週6セット÷頻度4＝1.5）は毎回3倍超過し、目標の大きい区分（週14セット÷頻度4＝3.5）は毎回埋まらない。どちらの誤差も次に伝わらないまま毎週繰り返される。

**修正:** `SessionResidual(target, coveredThisWeek, sessionsRemaining)` に変えた。週目標からその週にすでに埋めた分を引き、残りのセッション数で割る。**割る前に引く**のが要点で、これで過不足が翌セッションへ繰り越される。`PerSession` は削除した（「週あたり」と「セッションあたり」が同じ型で、二重適用が静かに通る問題も同時に消えた）。

### ただし本質は容量不足だった

修正後に自分でも検証したところ、繰り越しだけでは達成率が改善しない場面があった。原因を切り分けると、**補助スロットの容量そのものが足りない**。

- シードの週目標は21区分合計で198セット相当
- 補助が埋められるのは 3スロット × 3セット × 寄与合計 ≒ 15セット相当/セッション
- 頻度4でも週合計 85% 程度にしか届かない

これは残差の計算方法ではなく、**スロット数を3で固定していること**が原因。計画書 Task 13 を修正し、スロット数を残差から導くようにした。

```
必要スロット数 = ceil(残差の合計 / 補助1種目あたりのセット数)
実際のスロット数 = min(必要スロット数, セッション長の上限)
```

残差が小さい日は短く、大きい日は長くなる。

### その他

| 指摘 | 対応 |
|---|---|
| `NewProgram` がメイン種目の存在を検査せず、空のワークアウトがエラー無しで返る | 集約は種目マスタを知らないので検証できない。計画書 Task 16 に「メインが1つも無ければエラー」を明記した |
| `NewProgram` が `NewExerciseID` を呼ばず独自判定していた。前後に空白のあるIDが通り、種目マスタと永久に一致せず、選んだ種目が理由なく消える | `NewExerciseID` に委譲 |
| `StimulusCoverage` が公開マップ型で、ゼロ値への `Add` が nil マップ代入で panic する。外から NaN や `+Inf` も書ける | 非公開マップを持つ構造体にし、`Add` を「新しい値を返す `Plus`」に変更。ゼロ値がそのまま使える |
| `Residual` の `!math.IsNaN(gap)` は到達不能（NaN との比較は常に false なので `gap > 0` を抜けた時点で NaN ではない）。本当の穴は公開マップ経由の異常値だった | 削除。入口を閉じることで対処 |
| `PerSession` の下限判定 `>=` の境界がテストされていない | 削除したので消滅 |
| `WeeklyTarget()` アクセサのカバレッジが0%。Task 16 の入口で使われる | テストを追加 |
| `Regions` のソートテストが2区分しか使わず、マップの反復順で50%通ってしまうフレーキーテストだった | 6区分に増やした |
| 量子化のテストが、量子化してもしなくても同じ判定になる値を使っていた | 境界のすぐ外側（0.4999996）を使う形に修正 |
| 計画は `residual.go` を別ファイルにすると明記していたのに1ファイルに入れていた | 分割 |

## D-018: 補助種目の選択アルゴリズムを作り直した（敵対的検証の結果）

**きっかけ:** PR #14 への敵対的レビュー。シードで実測したところ、D-017 の「残差から導けば週目標に届く」が成立していなかった。

### 実測で判明した破綻

| 頻度 | 週目標の達成率 | 症状 |
|---|---|---|
| 1 | 35% | CALF・CHEST_LOWER・TRAP_UPPER・TRICEPS_LONG が**4週間すべて0セット** |
| 2 | 66% | TRAP_UPPER が0セット |
| 3 | — | 月水金の水曜が補助1種目（他の日は8種目） |
| 4 | **122%** | 積みすぎ |

原因は3つあった。

**1. スロット数の事前計算が誤り。** `ceil(残差合計 / 3)` は「1種目が複数区分を埋める」事実を無視している。シードの補助種目は平均1.5〜1.9区分に寄与するので、1スロットの実効は3ではなく4.5〜5.7。頻度4で22%の積みすぎになる。逆に頻度1では上限8に張り付き、埋める余地を残して終わる。

→ **事前計算をやめた。** 残差が無くなるか、埋められる種目が尽きるか、上限に達するまで選び続ける。

**2. 残差の大きい順に選ぶと小さい区分が飢餓に陥る。** 大腿四頭筋（週16セット）が常に勝ち、僧帽筋上部（週6セット）にスロットが一度も回らない。しかも `SessionResidual` は週ごとにリセットされるので、不足が翌週に繰り越されず**永久に0セット**になる。

→ **「最も長く刺激していない区分から」に変えた。** 一度も刺激していない区分が最優先になる。同じなら残差の大きい方、それも同じなら名前の昇順。

**3. 回復期間が実質72時間だった。** `[date-2, date)` の半開区間だと、月曜の記録が火曜**と水曜**を塞ぐ。月水金という最も一般的なスケジュールで、水曜がほぼ何も選べなくなる。

→ **`(date-2, date)` の開区間**に変えた。「2日空ければ解禁」の意味になる。

### 48時間ルールが名前どおりに機能していなかった

回復期間を「狙う区分」の除外にしか使っていなかったため、多関節種目が塞がれた区分を平気で叩いていた。レビュアーの実測では、選ばれた補助75件のうち**31件（41%）**が回復期間中の区分を刺激していた。

回復期間中の区分を**主働筋として使う**種目（寄与度1.0以上）を候補から外すようにした。補助的な関与（三頭が0.4など）まで避けると多関節種目がほとんど選べなくなるので、そこは許す。

### 私の検証の失敗

PR本文に「22種すべて検出」と書いたが、レビュアーが34種に広げると**11件が生存**した。最も重いのは、**アルゴリズムの中核である `consume` の呼び出しを丸ごと削除しても全テストが緑**だったこと。

私が「手当てした」と書いた2つのテストは、どちらも「候補を使い切って区分ごと諦める」経路で同じ結果になるため、消費の有無を区別できていなかった。

D-014・D-015・D-016 に続いて4度目の同種の指摘。変異を自分で選ぶ限り、自分が意識している性質しか壊せない。**中核ロジックについては「その処理を丸ごと削除する」変異を必ず含める**ことにする。

### その他

| 指摘 | 対応 |
|---|---|
| `+Inf` や `1e30` の残差で `int(math.Ceil(+Inf))` が負になり `make` が panic する | 事前計算をやめたので消滅。加えて非有限値を残差から除外 |
| `setsPerAccessory > 100` が通り、消費側の `NewSetCount` が失敗して無言の no-op になる（残差が永久に減らない） | コンストラクタで `NewSetCount` に委譲 |
| 未来日のログがある種目が永久に選ばれない（時計のずれで1件入るだけで唯一の担当種目が消える） | 経過日数を0でクランプ |
| 連日トレーニングで補助が0種目になる | 仕様として許容。回復期間の設計どおりの挙動で、無理に埋める方が有害 |

### 等価変異として残したもの

- `consume` の「追跡外の区分は触らない」ガード（追跡外の区分は負値になって即削除されるため、結果が同じ）

## D-019: 体重トレンドをロバスト推定に変え、部分レコードを合成するようにした（敵対的検証の結果）

**きっかけ:** PR #15 への敵対的レビュー。

### 最小二乗法が計測ノイズで判定を反転させていた

睡眠の基準には「1日の徹夜で下がらないように」中央値を使っていたのに、**体重の傾きだけ生の最小二乗法**だった。窓は21日でも最低サンプルは5点なので、週2回計測だと5〜7点しかなく、1点の外れ値が支配的になる。

レビュアーの実測：

| 状況 | 傾き | 減量中と判定されるか |
|---|---|---|
| 体重は完全に横ばい、3週間前の1点だけ +0.4kg | -0.112 kg/週 | **される（偽陽性）** |
| 本当に週 -0.3kg で減量中、今日だけ着衣 +1kg | -0.090 kg/週 | **されない（偽陰性）** |

+0.4kg は食後・飲水・便通で日常的に出る幅。これを閾値 -0.1kg/週（1日14g）という細い判定に直結させていた。

偽陽性側の帰結が重い。体重が1グラムも減っていないのに「減量中」と判定されると、**本物のオーバーリーチによる停滞でデロードが永久に出なくなる**。しかも症状はサイレント。このPRの存在理由（2種類の停滞を見分ける）そのものを潰していた。

**修正:** Theil-Sen 推定（全ペアの傾きの中央値）に変えた。睡眠の基準に中央値を使っているのと同じ理由。

### 同じ日の部分レコードが丸ごと潰れていた

`DailyCondition` は体重と睡眠が独立に欠損しうる設計なのに、重複解決が**レコードごと置換**だった。睡眠が先に届いて体重が後から届くと、睡眠が消える。

Health Connect では睡眠（起床時）と体重（体重計に乗ったとき）が別のデータ型・別のタイミングで入るので、**これは例外ではなく通常の経路**。HTTP の DTO も両フィールド nullable。

レビュアーの実測では、この経路で `RIRAdjustment` が 1 から 0 に変わった。ユーザーからは「機能が動いたり動かなかったりする」ように見える。

`DailyCondition.Merge` を追加し、フィールド単位で合成するようにした。

### アーキテクチャ検査を弱めすぎていた

`With` 系ビルダーの誤検出を直すとき、値レシーバを丸ごと対象外にした。しかし**値レシーバでも内部のマップやスライスへの添字代入は呼び出し側に波及する**。

レビュアーの実測：検査対象が **132メソッド → 23メソッド（-82%）**。`ConditionLog.items[0] = ...` や `History.lastPerformed[id] = ...` を書くコードが素通りするようになっていた。`checked == 0` の空振りガードは23で通るので、この崩壊はテスト自身から見えない。

除外条件を「値レシーバ**かつ**平フィールド代入」に絞った。プローブで、添字代入は検出しつつ `With` 系は通ることを確認した（検査対象は133メソッドに戻った）。

### その他

| 指摘 | 対応 |
|---|---|
| `NewConditionAnalyzer` が `+Inf` を通す。`validateRange` に集約する規約から外れていた | `validateRange` に寄せた |
| 窓に上限が無く、`make([]float64, 0, 1<<30)` で panic する。設定を外部から与えるようになった時点でプロセスが落ちる | 上限365日。確保も `log.Len()` を使う |
| `baselineDays < 5` が通るのに、最低サンプル数5に満たず機能が黙って死ぬ。テストがその設定を「境界値」として肯定していた | 窓の下限を最低サンプル数に揃えた |
| トレンド窓が閉区間で22日ぶんあった（睡眠側は14日ちょうど）。同じ「N日窓」で挙動が違う | 半開区間にして21日ちょうどに |
| `denominator == 0` が到達不能（日付が一意なので分母が0にならない） | Theil-Sen 化で消滅 |
| 「単位の取り違え（ポンド）を弾く」というコメントが事実に反する。実在する成人のポンド値は全て kg の範囲に収まる | コメントを訂正 |

**RIR補正が +1 の二値であること。** 睡眠3時間と5.5時間が同じ扱いで、5.6時間と5.5時間の間に断崖がある。Health Connect の睡眠推定は30分単位でブレるので、計測誤差で結果が反転しうる。また補正が全スロット・全種目に一律適用される点も、高重量コンパウンドと低負荷アイソレーションで影響が非対称なはず。Task 16 の API 形を縛るので、そこに入る前に結論を出す。

## D-020: デロードの窓と判定条件を作り直した（敵対的検証の結果）

**きっかけ:** PR #16 への敵対的レビュー。D-010/D-014 の持ち越し課題に「許容幅は置かない」と答えたが、**同じ分解能の論法が窓の長さにも当てはまることを見落としていた**。

### 実測された誤発火

レビュアーが週3回プログラムを39セッションぶんシミュレートした結果：

| 状況 | 提案が出た回数 |
|---|---|
| 完全維持 | 34 / 39（最長32連続 = 11週間） |
| 真の伸び +0.25kg/週 | 28 / 39（72%） |
| 真の伸び +0.50kg/週 | 20 / 39（51%） |
| 真の伸び +2.00kg/週 | 4 / 39（10%） |

**中級者の現実的な伸び（+0.5kg/週）で、半数のセッションに「停滞」の提案が出る。**

原因は窓の長さ。推定1RMが動く最小単位は 85kg で1レップぶん ≒ 2.83kg（2.5%）。週+0.5kg の伸びだと1レップ増えるまで約5.7週かかる。メイン種目はバリエーションの日に実施しないので週2回として、約11セッション。**窓3セッションは、判定に使う指標の分解能より3〜4倍短かった。**

D-010 が「0.005 という閾値は分解能に対して無意味」と指摘したのと同じ話が、閾値ではなく窓の長さに現れていた。許容幅の側だけ答えて、窓の側を答えていなかった。

**修正:** 既定の停滞セッション数を 3 → **8**（週2回なら約1ヶ月）にした。

### 回復中を停滞と呼んでいた

基準が窓の先頭1点だけだったので、窓の入口に高い値があると、その後どれだけ連続で更新しても「更新していない」になる。**病み上がり・ブランク明け・デロード直後**がこの形。毎回更新しているのに過去の値に届いていないだけの人に、さらに10%下げるのは誤り。

判定を2条件にした。

1. 窓の先頭を、それ以降のどのセッションも上回っていない
2. 直近のセッションが、窓の途中のどれも上回っていない

条件2で「1つ前」ではなく「窓の途中の最大値」と比べるのは、上下に振れているだけの状態（85 → 82.5 → 85 → 82.5 → 85）を回復と誤認しないため。

### 停滞種目が文字列の中にしか無かった

`DeloadProposal` が持つのは根拠の日本語文字列と低下率だけだった。後続の `SessionPlanner` は全メイン種目・全補助種目に同じスケールを適用するので、**ベンチだけ停滞している人のスクワットもデッドリフトも補助種目も全部10%下がる**。

`StalledExercises() []ExerciseID` を追加した。これは公開 API の変更なので、後続タスクでは回収できない。計画書 Task 16 にも「停滞した種目にだけ適用する」ことを明記した。

### 承知の上で残す限界

**体重の減量判定（-0.1kg/週）は推定量のノイズ床（σ0.5kg・21日窓で標準偏差0.13kg/週）より小さい。** レビュアーのモンテカルロでは、真に体重維持している人に対して体重計のノイズだけで提案の有無が22%反転した。真に -0.25kg/週 で減量中の人の12.5%に提案が出る。

D-019 の Theil-Sen 化は外れ値には効くが、ガウスノイズ下の分布は最小二乗法とほぼ同じ（sd 0.131 vs 0.125）なので、この問題は解決していない。

現時点では受け入れる。理由は、窓を8セッションに延ばしたことで提案の頻度自体が大幅に下がり、かつ提案は適用ではなく承認を求めるものだから。トレンド窓を延ばす（21日→42日）ことで標準偏差は下げられるが、それは `ConditionAnalyzer` の既定値の変更であり、実データで効果を測ってから決める。

## D-021 セッション中の実績を残差に即反映する

**判断**: `coveredThisWeek` の窓を「週初〜当日（当日を含む）」に広げ、当日すでに記録したメイン種目だけを計画ぶんの積み上げから除外する。加えて、当日実施した種目を補助種目の候補プールから外す。

**根拠**: 当日を丸ごと除外していたため、セッション中にこなした**補助**がどこにも計上されなかった。敵対的検証で、1種目こなすたびに計画を開き直すシナリオを回すと、提示される補助が 8件 → 8件 → 8件 と一切減らず、種目が尽きると同じ種目を無限に再提示した。従うとセッションが原理的に終わらない。

「未来を保存せず毎回導出する」という設計は、導出が実績に対して単調減少することを前提にしている。当日を除外するとその前提が崩れる。除外が必要なのはメイン種目だけ（計画ぶんを別途足すため）なので、除外の粒度を「日」から「当日記録済みの種目」に下げた。

**代償**: メイン種目を当日に記録した場合、その日の刺激量は計画値ではなく実績のログ件数で数える。ユーザーが4セット中2セットで切り上げれば残差はその分だけ多く残り、補助が増える。実態に即しているのでこれでよい。

## D-022 デロードの承認は種目の一覧で受け取る

**判断**: `PlanRequest.DeloadAccepted` を `bool` から `[]ExerciseID` に変更。提案の有無とは独立に、承認された種目にだけ適用する。

**根拠**: 敵対的検証で3つの壊れ方が出た。

1. **承認したのに下がらない**。提案は毎回 `Propose` で計算し直される。体重の記録が数日途切れると `BodyWeightTrendKgPerWeek` が false を返して提案ごと消え、`hasProposal && accepted` が偽になる。エラーもフラグも立たず、ユーザーには「承認したのに10%重い」としか見えない。体重計に乗り忘れるのは日常なので、これは頻繁に踏む。
2. **承認していない種目まで下がる**。単一の bool だと、ベンチの提案を承認した状態のまま後からスクワットが停滞判定に入った瞬間、新しい承認を経ずに全部下がる。D-020 で `StalledExercises()` を足して適用の粒度を種目単位にしたのに、承認の粒度がそれに追随していなかった。
3. 承認が種目に紐づかないので、クライアント側でも「何を承認したのか」を保持できない。

承認の粒度を提案の粒度に揃えることで3つとも消える。

## D-023 デロード直後は再提案しない

**判断**: `isStalled` に「窓の最高値から低下率ぶん以上すでに落ちていれば停滞と見なさない」を追加。

**根拠**: `SessionPlanner` が初めて `DeloadPolicy` と `OneRepMaxEstimator` を閉ループに繋いだ結果、下降スパイラルが発生した。デロード後の軽い重量が記録される → 推定1RMが下がる → 窓の最高値を更新しないので再び停滞判定 → さらに10%低い重量。8週間のシミュレーションで **24セッション中24回**提案が出続け、ベンチが 82.5 → 72.5 → 60.0kg と落ち続けた。デロードは停滞を破る機能なのに、承認すると停滞を確定させていた。

デロードを適用したこと自体はどこにも保存していない（未来を保存しない設計）ので、記録から検出する。「窓の最高値より低下率ぶん以上低い」状態は、デロード直後か体調を崩している段階のどちらかで、いずれもさらに下げてよい理由がない。閾値を低下率と同じ値にしているのは、これが「1回ぶんのデロードで落ちる量」そのものだから。

**代償**: 通常の上下動（レップ1本ぶん = 2.4〜2.9%）は低下率10%に遠く届かないので握りつぶさない（テストで固定）。一方、本当に長期低迷している人には提案が出なくなる。これは「軽くし続けるより休むべき」局面であり、重量を下げる提案は答えではない。

## D-024 頻度を超えたセッションでも補助を出す

**判断**: `sessionsRemaining` の下限を1にする。

**根拠**: 週3設定で週4回以上通うと `sessionsRemaining` が 0 以下になり、`SessionResidual` が空を返して補助が1つも出なくなっていた。しかも `SlotCatalog.Select` は剰余で巡回するため、4本目・5本目に**メインリフトのフルスロット**が再び割り当たる。実測で週5回時のデッドリフトが 18セット/週 に達した。D-016 が「週5回以上は1種目19セット/週で成立しない」として頻度上限を4に下げ、超過分は補助種目の日にすると決めたのに、実装はその逆をやっていた。

下限を1にすると、超過セッションは「週の残りを1回で埋める」つもりの残差を受け取る。すでに埋まっている区分の残差は0なので、実際に不足している区分だけが出る。

## D-025 コンディション分析器はデロードポリシーから取る

**判断**: `SessionPlanner` の RIR 補正を `DefaultConditionAnalyzer()` の直接呼び出しから `p.deload.Analyzer()` に変更。`DeloadPolicy.Analyzer()` を公開した。

**根拠**: 注入した分析器が RIR 補正に一切効いていなかった。同じセッションの中で「デロード判定は注入した分析器、RIR補正は既定値」という状態になり、睡眠不足の閾値を変えてもデロードの挙動だけが変わるという説明のつかない振る舞いをする。分析器を2つ持つ理由が無いので、ポリシーが持つものを共有する。

## D-026 補助種目にデロードは適用しない

**判断**: `planAccessory` からデロード分岐を削除。

**根拠**: 到達不能なデッドコードだった。`deloadTargets` のキーは `proposal.StalledExercises()` ⊆ `mainIDs` で、`chosen` は `KindAccessory` に限られる。種別は排他なので分岐は常に偽。残しておくと「補助にもデロードが効く」と読めてしまう。停滞判定はメイン種目しか対象にしていないので、効かせないのが正しい。

## D-027 週目標は頻度でスケールする

**判断**: `seed.DefaultWeeklyTarget()` を `DefaultWeeklyTarget(f training.Frequency)` に変更し、週3回を基準にしたプロファイルを頻度で線形にスケールする。

**根拠**: 固定値だと、頻度が正当な入力（1〜4）であるにもかかわらず、頻度1・2のユーザーは**全21区分が永久に赤字**になる。通し検証の実測で平均達成率は 週1回 34%、週2回 65%、週4回 107〜120% だった。1週間に供給できるセット数は頻度に比例する（メイン12セット＋補助8枠×3セット）のに、目標だけが固定だったため。

D-018 は同じ数字（35% / 66% / 122%）を「破綻」と認定して補助種目の選択器を作り直したが、容量側（目標値）は据え置きだった。選択器をどう賢くしても、週1回で198セット相当は供給できない。

スケール後の実測は全頻度で **65〜140%** に収まる。

**代償**: スケールは線形だが、供給の内訳は線形ではない。8スロットを21区分に配る形が頻度で変わるため、区分ごとの達成率は ±40% ほど振れる。目標を実測値に収束させれば ±12% まで詰められるが、それをやると目標が「アルゴリズムの出力の写し」になり、サイドレイズ週4セットのような**訓練の意図として意味を持たない数字**になる。目標は意図であって実測の記述ではないので、手で置いた値を保ち、テストの許容帯を広く取った。

## D-028 週目標と刺激係数は通し検証で担保する

**判断**: `seed/simulation_test.go` を常設のテストとして置き、頻度1〜4で8週間シミュレートして達成率・種目の出番・セッション長・重量の確定を検証する。計画書の Task 18（通し検証）を Task 17 に前倒しした。

**根拠**: シードは「値が入っていること」を確かめても意味がない。週目標と刺激係数はセッション生成器を通してはじめて挙動になる。実際、当初のテストはミューテーション15種のうち**3種しか検出できなかった**（20%）。**全種目の主働筋寄与を 1.0 → 0.3 に潰す**変異すら緑のままで、これは刺激係数という中核データを丸ごと無意味にする変異である。

D-018 で「中核ロジックには丸ごと削除する変異を必ず含める」と決めたが、データにも同じことが要る。通し検証を入れたあとは **15種すべて検出**する。

## D-029 レッグカール・ヒップスラストが週3回の BIG3 構成で出ないのは正しい

**判断**: 現状の挙動を仕様として受け入れ、テストは「どこかの構成で出番があること」を検証する。

**根拠**: 通し検証で、`leg_curl`（ハム1.0のみ）と `hip_thrust`（臀筋1.0のみ）が週3回・BIG3 全部入りの構成で8週間まったく選ばれなかった。原因は、デッドリフトが毎セッションその2区分を主働筋として叩くため、補助種目の選択が使う「最も長く放置している区分から埋める」順位で永久に負けること。

選択規則を「残差の大きい区分から」に変えて実測したところ、`hip_thrust` は出るようになる一方で、**小さい区分が飢える**（週3回で僧帽筋上部50%、腹斜筋65%など、D-018 が防いだ問題が再発）。この規則変更は割に合わない。

デッドリフトをプログラムから外した構成で回すと `leg_curl` は24セッション中11回選ばれる。つまり「デッドリフトをやる人にハムの単関節種目は要らない」という判断が効いているだけで、種目が死んでいるわけではない。

## D-030 自重種目は加重前提でシードに入れる

**判断**: `pull_up`（チンニング）と `dip`（ディップス）を加重前提の種目として置く。自重のみのユーザーには重量が未確定のまま出る。

**根拠**: `NewOneRepMax` の下限が正の数なので、0kg のログからは推定1RMが立たない。自重で記録し続けるユーザーには毎回「未確定」が出る。

自重を表現する手段（体重を重量として使う、自重フラグを持つ）を今入れると、`SetLog` と `Weight` の意味に例外が増える。この2種目は加重できる器具が普及しており、加重すれば他の種目と同じ経路に乗る。除外するほうが害が大きい（ラットプルダウンだけでは背中の主要種目が薄い）。

**持ち越し**: 自重のみのユーザーが多いと分かったら、体重を `DailyCondition` から引いて実効重量にする経路を検討する。体重の記録はすでにあるので、追加のデータは要らない。

## D-031 ProgramRepository に Save を持たせる

**判断**: `ProgramRepository` に `Save(ctx, *Program) error` を追加し、`ConfigureProgram` ユースケースと `PUT /api/program` を計画に足す。

**根拠**: 敵対的検証で、**ユーザーがプログラム（頻度・週目標・選択種目）を設定する経路が Task 19〜24 のどこにも無い**ことが判明した。Task 21 のインメモリ実装には `Set` があるがインターフェースに無い具象メソッドで、テストからしか呼ばれない。本番経路はシードから固定のプログラムを組んで注入するだけ。結果、`ErrProgramNotConfigured` → 409 の分岐は本番で到達不能なデッドコードで、仮に到達させても解消する API が無い。次の計画（Postgres 差し替えと認証）にも設定機能は無い。

「メニュー設定が面倒だから自動化する」アプリで、頻度と使う種目を選べないのは機能の欠落。

インターフェースはドメイン層にあるので、後から足すとユースケース・インメモリ実装・HTTP・main・依存方向テストを全部触り直すことになる。この PR が最も安く直せる地点だった。

## D-032 種目マスタとの突合はアプリケーション層で行う

**判断**: `ErrExerciseNotFound` を定義し、`ConfigureProgram` が選択された種目IDの実在を突合する。

**根拠**: `Program` は種目マスタを知らないので、選択された種目IDが実在するかを自分で検証できない（`program.go` の作者自身がコメントで警告している）。`SessionPlanner.usablePool` は一致しないIDを黙って落とし、補助枠の `findExercise` も nil のとき重量なしの枠を返して終わる。エラーはどこにも立たない。

シードから種目を1つ削除・リネームした瞬間、既存ユーザーのメニューからその種目が理由の説明なく消える。デプロイ後に気づく類の不具合。

突合をドメインに置かないのは、種目マスタの取得が I/O だから。ユースケースは「データを集めてドメインに渡すだけ」だが、**渡す前の入力検証はユースケースの仕事**で、判断ではない。

## D-033 保存の契約を明文化する

**判断**: `SetLogRepository.Save` に `ErrConflictingSetLog` と「全か無か」を、各 `FindAll` に「リポジトリ内部の可変状態をエイリアスしない」を、インターフェースの契約として書く。

**根拠**: 冪等性の要求がドキュメント止まりだった。重複そのものは読み側（`NewHistory` が ID で潰す、`NewConditionLog` が日付で Merge する）が吸収するが、その先に3つ残る。

1. **非決定性**。`NewHistory` の重複解決は「スライスの後にあるものを採用」。同じIDで内容の違うログが2件あると、リポジトリが返す順序（`ORDER BY` の付け忘れ、map の range）次第で採用される値が変わる。同じ日付に同じリクエストを2回投げると違う重量が返る。コンディション側も同じで、体重が揺れると `BodyWeightTrendKgPerWeek` が閾値をまたぎ、**デロード提案が出たり消えたりする**。
2. **検出手段が無い**。`SetLog.Equals` の doc は「保存側がこれで検出しエラーとして弾けるようにする」と書いているのに、`Save` にそれを表すセンチネルが無かった。プレゼンテーション層が 409 と 500 を区別できない。
3. **原子性が未定義**。1セッション25セットの半分だけ保存された状態は、その週の刺激量を実態とずらしたまま計画に効き続ける。

インメモリ実装は失敗しないので Task 21 では露呈せず、Postgres で初めて問題になる。契約テストをインメモリ・Postgres 両方で回せる形で書く（Task 21）。

## D-034 FindAll のスケールは今は変えない（持ち越し）

**判断**: 範囲クエリを導入せず、`FindAll` のまま進める。

**根拠**: 実測（週3セッション×25セット）で、1リクエストあたり 1年分 1.4ms / 2.0MB、3年分 7.0ms / 10.4MB、10年分 17.0ms / 26.6MB。超線形（データ3倍で時間4.9倍）だが、単一ユーザー・週数リクエストなら許容範囲。

プランナが実際に使う範囲は狭い（週内カバレッジは7日、コンディションは21日、デロード判定は8セッション）が、**推定1RMだけは全履歴を要求する**。`OneRepMaxEstimator` は種目の全セッションを古い順に EWMA で畳み込むので、範囲を切ると結果が変わる。幾何減衰なので実用上は無視できるが、意味論としては等価ではない。

**持ち越し**: マルチユーザー化するか Postgres で全件 SELECT がネットワークを跨ぐ時点で効いてくる。範囲クエリへ移る前に、EWMA が「直近Nセッションで打ち切っても同じ答えになる」ことを確認し、その N を定数として置く必要がある。

## D-035 種目の突合は「実在」だけでなく「種類」も見る

**判断**: `ConfigureProgram` がメイン種目ゼロの選択を `training.ErrNoMainExercise` で弾く。

**根拠**: D-032 で実在の突合を入れたが、種目の**種類**を見ていなかった。補助種目だけ・バリエーションだけの選択が通り、保存は 200 で成功するのに、以後すべての `GET /api/sessions` が 500 になる（`SessionPlanner.Plan` はメイン種目ゼロを致命エラーにする）。しかも 500 なのでクライアントは初期設定へ誘導できない。UI の種目チェックボックスからメインを外せる限り、通常操作で到達する。

D-032 の論拠（「`Program` は種目マスタを知らないので突合はアプリケーション層の仕事」）は `Kind()` にも等しく当てはまる。突合を半分しかやっていなかった。

**あわせて**: 週目標のどの区分も刺激しない選択も弾く。補助種目が毎回ゼロになり、設定した週目標が永久に埋まらないのにエラーがどこにも立たない。ただし区分ごとに種目を要求はしない。特定の区分を埋める種目を持っていないのは普通のことで、達成率が低く出るのは情報として正しい（D-027）。弾くのは、目標と選択がまったく噛み合っていない場合だけ。

## D-036 入力の不正と I/O 障害を分類する

**判断**: `usecase.ErrInvalidInput` を定義し、入力起因の失敗をすべてこれで包む。I/O 起因はそのまま通す。あわせて、I/O を必要としない検証を `FindAll` より前に移す。

**根拠**: `ConfigureProgram` の失敗9系統のうち**7つが裸の `fmt.Errorf`** で、呼び出し側に残された判別手段が文字列マッチしかなかった。特に「頻度が範囲外」と「データベースが落ちている」が同じ形なので、`PUT /api/program` のハンドラは 400 と 500 を原理的に区別できない。入力ミスが全部 500 になるか、障害が全部 400 になるかの二択になり、前者はクライアントに無駄なリトライをさせる。

ドメイン側で分類できないのは、`NewFrequency` / `NewWeeklyVolumeTarget` / `NewProgram` が返すのが匿名のエラーだから。センチネルを全部ドメインに足すのは、エラーの語彙をドメインの関心事でないもの（HTTP ステータス）に引きずられて増やすことになる。分類はプレゼンテーションに近い側の関心なので、アプリケーション層で包む。

検証順序も直した。`PerWeek=99` は I/O を必要としない自明な不正入力なのに、種目マスタが落ちていると「種目の取得に失敗」が返っていた。

## D-037 リポジトリの契約違反をユースケースで受け止める

**判断**: `GetSession` が `program == nil` を `ErrProgramNotConfigured` に読み替える。

**根拠**: `repository.go` は「`(nil, nil)` を返してはならない」と明記しているが、守らせる手段がない。契約違反時は `SessionPlanner.Plan` の匿名エラー（「プログラムが指定されていない」）になり、プレゼンテーション層が未設定と判別できず 500 に落ちる。インメモリ実装がセンチネルを返すことに全面的に依存していた。

## D-038 キャンセルされた context で全件読み込みを走らせない

**判断**: `GetSession` と `ConfigureProgram` のリポジトリ呼び出しの合間に `ctx.Err()` を見る。

**根拠**: `GetSession` は4本のリポジトリを直列に叩き、履歴は全件を読む（D-034 の実測で10年分 17ms / 26.6MB）。クライアントが切断済みでも最後まで走らせると、その全部を無駄に払う。`RecordSets` はキャンセル済みでも保存を呼んでいた。

## D-039 空の保存は成功として扱う

**判断**: `RecordSets` / `RecordConditions` は空の入力で I/O を起こさず nil を返す。`nil` 要素は `ErrInvalidInput` で弾く。

**根拠**: クライアントは同期のたびに送ってくるので、送るものが無い回に I/O を起こす理由がない。「空を送ってきた」をエラーにすると、正常な同期がエラーログを埋める。ポリシー判断なので理由を書いた（無言だと後から見て意図が読めない）。

一方 `nil` 要素は別で、実装側で panic するか黙って飛ばされるかが実装依存になるため境界で弾く。

## D-040 インメモリ実装で保存の契約を実際に守らせる

**判断**: 計画にあった「同じIDは黙って上書き」「同じ日付は丸ごと置き換え」を捨て、D-033 の契約どおりに実装する。

**根拠**: 計画のインメモリ実装は3点で契約に反していた。

1. **同じIDで内容が違うログを黙って上書き**していた。計画のテスト（`SaveOverwritesSameID`）はその挙動を正しさとして固定していた。上書きすると、どちらが正しいか分からないまま推定1RMが動く。`ErrConflictingSetLog` を返し、同じ内容の再送だけを黙って受け入れる。
2. **同じ日付を丸ごと置き換え**ていた。体重だけを送り直すと睡眠時間が消える。クライアントは体重と睡眠を別のタイミングで記録するので日常的に起きる。これは D-019 がドメイン側で潰した失敗モードが、インフラ側で再発したもの。`Merge` と同じ規則で項目ごとに上書きする。
3. **`ProgramRepository.Set` がインターフェースに無い具象メソッド**だった（D-031 で指摘済み）。`Save(ctx, p) error` に置き換えた。

あわせて「全か無か」も実装した。衝突を1件でも見つけたら1件も書かない。半分だけ保存された状態は、その週の刺激量を実態とずらしたまま計画に効き続ける。

**取得順の安定**: `map` の range は順序を保証しない。順序が揺れると `History` の重複解決（後にあるものを採用）や推定1RMの畳み込みが呼び出しごとに変わり、同じ入力から違う計画が出る。ID・日付でソートしてから返し、20回呼んで順序が変わらないことをテストで固定した。この性質は Postgres 実装でも `ORDER BY` として要求される。

## D-041 インメモリ実装の検証結果

**判断**: 契約の検証・並行性・性能を実測し、無音のデータ破棄を1件塞いだうえで、その他は現状のまま進める。

**根拠（実測）**:

- **全か無かは並行下でも保たれる**。既存と衝突するログを含む保存を64 goroutine から同時に投げ、64件すべてが `ErrConflictingSetLog` を返し、リポジトリの件数は1のまま。書き込みロックが検出とコミットの両方を覆っているため、間に割り込む窓が無い。
- **`ErrConflictingSetLog` はユースケース経由で `errors.Is` で辿れる**。`RecordSets` → `memory.SetLogRepository.Save` の経路で確認。`ErrInvalidInput` には分類されないので、プレゼンテーション層は 409 と 400 を区別できる。
- **エイリアスの穴は無い**。`NewHistory` / `NewConditionLog` はどちらも新しいスライスを組み立てる。共有されるのは `*SetLog` と `*Exercise` のポインタだが、どちらも生成後に変更されず、内部のマップ（`StimulusProfile.m`、`WeeklyVolumeTarget.m`、`Program.selected`）に外部から到達する経路が無い（`Regions()` も `SelectedExercises()` もコピーを返す）。
- **`SetLog.Equals` は全フィールドを比較している**（`*s == *o`）。内容が違うのに同一と判定される抜けは無い。
- **`FindAll` の実測**: 3,925件 0.60ms/0.74MB、11,750件 1.81ms/1.61MB、39,125件 6.30ms/6.17MB。D-034 が測ったリクエスト全体（10年分で17ms/26.6MB）の約4割で、内訳として妥当。毎回ソートしている分は O(n log n) だが、支配的なのはスライスと索引の再構築。D-034 の判断（今は変えない）を維持する。

**塞いだもの**: `ConditionRepository.Save` が日付の無い記録を黙って読み飛ばしていた。クライアントは保存に成功したと思ったまま記録が消える。`nil` のセットログと同じ扱いにしてエラーで弾く。ドメインの `NewConditionLog` も読み飛ばすが、そちらは「集めた記録から不正なものを除く」場面で、保存要求を捨てるのとは意味が違う。

## D-042 ステータスの分類を1箇所に集める

**判断**: `respondError(w, err)` を1つ置き、センチネルからステータスへの翻訳をそこだけで行う。

**根拠**: ハンドラごとに `errors.Is` を並べると、新しいセンチネルを足したときに拾い漏らすハンドラが出る。実際、計画のハンドラは `handleGetSession` だけが `ErrProgramNotConfigured` を見ており、`handlePostSetLogs` は D-033 で新設した `ErrConflictingSetLog` を無条件で 500 にしていた。クライアントは自分のID採番ミスに気づかずリトライを繰り返す。

| 条件 | ステータス |
|---|---|
| `context.Canceled` | 499（クライアント切断） |
| `context.DeadlineExceeded` | 504 |
| `usecase.ErrInvalidInput` | 400 |
| `training.ErrProgramNotConfigured` | 409（セッション導出の文脈）／404（`GET /api/program`） |
| `training.ErrConflictingSetLog` | 409 |
| それ以外 | 500 |

**499 を使う理由**: クライアント切断はサーバーの障害ではない。500 と混ぜると、ログと警報がクライアントの都合で汚れる。標準ライブラリに定数が無いので自前で置いた。

**未設定が文脈で変わる理由**: `GET /api/program` では「まだ存在しない」という意味なので 404。セッション導出では「前提が満たされていない」という状態の衝突なので 409。

## D-043 500 では内部のエラー文を返さない

**判断**: 500 のときだけ固定文言を返す。400 は原因をそのまま返す。

**根拠**: ドメインとインフラのエラーには種目ID・閾値・テーブル名・接続文字列が載っている。計画のハンドラは全部 `err.Error()` をそのまま返していた。

400 で隠さないのは、ユーザーが直せる情報だから。「頻度は1〜4回である必要がある」を隠すと、クライアントは何を直せばいいか分からない。

## D-044 実測できない分解は直接テストする

**判断**: `parseExerciseIDs` を `export_test.go` 経由でテストする。

**根拠**: `deload_accepted=,bench,` の空要素を落とさなくても、空の種目IDはデロード対象のマップに入るだけで実害が出ない。HTTP 経由では観測できず、ミューテーションが生存し続ける。境界で落とすのが正しい以上、観測できる形でテストする。

「実害が出ないから放置」を許すと、後でその ID が別の用途（ログ出力、集計のキー）に渡ったときに初めて壊れる。

## D-045 HTTP 境界で入力を閉じる

**判断**: リクエストボディに 1MB の上限、`Content-Type: application/json` の要求、末尾トークンの検査を入れる。種目IDに 64 文字の上限を足す。

**根拠**: 敵対的検証で、無認証のエンドポイントに対する実測が出た。

- **上限が無い**: 20MB の `exercise_id` を 10 回投げると GC 後のヒープが 1MB → 201MB。**保存に成功する（204）ので解放されない**。しかもその後の `GET /api/sessions` は毎回そのゴミを全件読み、117ms に劣化する。`SetLogID` には 64 バイトの上限があるのに `ExerciseID` には無かった。
- **エラー応答が入力を反射する**: `NewExerciseID` はエラー文に入力全体を埋め込む。20MB の不正な ID に対し 20MB の 400 応答が返っていた。確保・保持・送出の三重取り。長さの検査を他の検証より前に置いて塞いだ。
- **末尾のドキュメントを黙って捨てる**: `{"logs":[...]} {"logs":[...]}` が 204 を返し、2つ目は保存されていなかった。クライアントは保存されたと受け取ったまま実績が消える。これは同じ PR が「読み飛ばすと保存に成功したと思ったまま実績が消える」として塞いだのと同じ事故の別経路。
- **`Content-Type` を検証していない**: `text/plain` も `form-urlencoded` も 204 だった。後者はブラウザがプリフライト無しで送れるので、認証を入れた時点で CSRF がそのまま通る。

## D-046 保存要求では「捨てる」判断を採らない

**判断**: `POST /api/conditions` で範囲外の体重・睡眠時間を 400 にする。両方欠けている記録も 400 にする。

**根拠**: `DailyCondition.WithBodyWeight` / `WithSleepHours` は範囲外を「無かったこと」にする（D-019）。1日ぶんの異常値で取り込み全体を止めないための判断で、**集めた記録を扱う場面では正しい**。しかし保存要求では意味が違う。実測:

| 当日の入力 | 応答 | 目標RIR |
|---|---|---|
| `sleep_hours: 3` | 204 | 3（補正が効く） |
| `sleep_hours: -3`（符号の打ち間違い） | 204 | 2（黙って捨てられた） |

睡眠3時間の日に、システム自身のルールでは軽くすべきところを通常強度で処方する。取得のエンドポイントが無いのでクライアントは損失を検知できない。これは D-041 で `ConditionRepository.Save` が日付欠落について採ったのと同じ立場。

## D-047 実績ログも種目マスタと突合する

**判断**: `RecordSets` が `ExerciseRepository` を受け取り、種目の実在を検証する。

**根拠**: D-032 でプログラムの選択種目は突合したが、実績ログは素通しだった。実在しない種目のログは、どの筋区分にも計上されないまま履歴に残り続ける。削除の口が無く、同じIDの再送は `ErrConflictingSetLog` になるので、**打ち間違い1回で復旧できない**。

あわせて実測されたのは、`9999-12-31` のログを1件入れると当日の補助種目の構成が変わること。未来日そのものの拒否は入れていない（クライアントの時計とサーバーの日付がずれる余地があり、境界の定義が難しい）。ドメイン側は未来日のログをクランプする防御をすでに持っている（D-021 の `pickVariation`、`AccessorySelector`）。

## D-048 プレゼンテーション層からリポジトリを直に叩かない

**判断**: `GetProgram` ユースケースを足し、`handleGetProgram` をそれ経由にする。`RecordSets` / `RecordConditions` にも `ctx.Err()` の検査を入れる。

**根拠**: `handleGetProgram` だけがリポジトリを直に叩いており、キャンセルの扱いが規約から外れていた。実測で `GET /api/program` はキャンセル済みの context でも 200 を返し、`POST /api/set-logs` と `POST /api/conditions` は 204 を返しつつ書き込んでいた。D-042 の分類表と実装が一致していなかった。

6つのエンドポイントのうち一部だけ規約が違う状態は、DB 実装に差し替えたときに誰も気づけない。

## D-049 500 は隠すが記録する

**判断**: 500 のときに `slog.Error` でサーバー側に記録する。

**根拠**: D-043 で 500 の内容をクライアントから隠したが、内部にも記録していなかった。障害時に運用者へ残るのは「内部エラーが発生した」だけで、原因が完全に消える。隠すことと捨てることは別。

## D-050 依存方向の検査に兄弟層の相互依存を含める

**判断**: プロジェクト全体の依存方向テストに、同じ深さの層どうしの依存を禁じる検査と、具象のリポジトリ実装を知ってよいのは `cmd` だけという検査を足す。

**根拠**: 計画の検査は「外側の層を import してはいけない」だけを見ていた。`infrastructure` と `presentation` は同じ深さ（2）なので、**HTTP のハンドラがインメモリ実装を直接 import しても検出されない**。実際に試すと素通りした。

これが通ると「リポジトリ実装の差し替えが `cmd/api/main.go` に閉じる」という Task 24 の受け入れ基準が崩れる。Postgres へ移るときに、どこを触る必要があるか分からなくなる。

深さを同じにしているのは、どちらも外界との境界で内側から見て等距離だから。互いに依存してよいという意味ではない。

**テストファイルは兄弟の検査の対象外**にした。テストが具象実装を組み立てるのは正当で、むしろインメモリ実装で HTTP 層を検証できること自体が Onion の狙いそのもの。内向きの検査からは除外していない（ドメインのテストが外側を必要とするなら、それは設計が壊れている）。

**走査件数の下限**も足した。走査が壊れて0件になっても緑になるのでは、検査を通ったのか何も見ていないのかを区別できない。これは PR9 で自作のミューテーション基盤が赤いベースラインの上で走り「全件検出」と誤報したのと同じ失敗の形。

## D-051 依存方向の検査は許可リスト方式にする

**判断**: 層に属さないパッケージを「分類対象外」として無視するのをやめ、**すべてのパッケージに層の宣言を要求する**。パスの照合を `strings.Contains` からディレクトリ境界の一致に変える。検査本体を純粋な関数に切り出し、既知の違反を食わせる陽性コントロールを置く。

**根拠**: 敵対的検証で、D-050 の検査が**中継パッケージを1枚挟むだけで完全に無力化する**ことが実証された。

```
internal/glue が infrastructure を import し、
internal/presentation/httpapi が internal/glue を import する
→ go build / go vet / go test すべて緑
```

本番の HTTP ハンドラがインメモリ実装のインスタンスを保持している状態で、検査が何も言わない。原因は、`layerOf` がマッチしないパスに `false` を返し、そのファイルが**収集対象から丸ごと落ちる**こと。落ちたファイルは import 元としても import 先としても存在しないことになる。`internal/adapter`、`internal/config`、`pkg/` — 今後足されるディレクトリの大半がこの穴に落ちる。

`strings.Contains` による照合にも別の穴があった。`internal/infracmd` は `Contains(path, "cmd/")` に一致して **cmd の特権（最外層）を得る**。`internal/domainsql` は domain 扱いになる。

**陽性コントロールを置いた理由**: 検査をゆるめる変異10種のうち6種が緑で通っていた（内向き検査を1段ゆるめる、`Errorf` を `Logf` に、全ファイルをテスト扱いに、など）。違反が無ければ検査は静かに検出力を失ったまま緑でいる。走査件数の下限だけでは「走査が壊れた」形しか捕まえられない。

これは D-050 自身が書いた「PR9 で赤いベースラインの上で『全件検出』と誤報したのと同じ失敗の形」を、まさに繰り返していた。

## D-052 起動と停止をテストできる形に分ける

**判断**: `run()` を `newServer` / `serve` / `serveListener` に分け、シグナルの購読解除を停止前に行う。停止の猶予を最長のリクエスト予算より長く取る。リクエストの context に期限を付ける。

**根拠**: 敵対的検証の実測。

- **2回目以降のシグナルが握り潰される**。`defer stop()` だと購読は `run()` が返るまで続き、ctx はキャンセル済みなので2回目の SIGTERM も SIGINT も何も起こさない。Ctrl-C を連打しても止まらず `kill -9` が要る。停止処理に入る直前に `stop()` を呼んで既定の動作に戻す。
- **停止の猶予（10秒）が `writeTimeout`（30秒）より短かった**。サーバー自身が許可した長さのリクエストを必ず切ることになる。実測で、12秒かけてボディを送るリクエストが空応答で切られ、ステータスすら返らなかった。「処理中のリクエストを落とすと、クライアントは保存できたのか分からないまま再送する」というコメントの通りのことが起きていた。
- **504 が本番で発火しない**。リクエストの context に期限を付ける配線がどこにも無く、`respondError` の `DeadlineExceeded` → 504 はテストの中でしか起きなかった。README のステータス表が嘘になっていた。`http.TimeoutHandler` を使わないのは、あちらが独自の 503 を書いて D-042 の分類を迂回するため。
- **`run()` が1行もテストされていなかった**。ミューテーション20種のうち15種が生存し、スローロリス対策のタイムアウトを全部消しても、グレースフル停止を丸ごと消しても緑だった。listener を受け取る形に分けてテストできるようにした。
- **停止の失敗が「起動に失敗」と記録されていた**。`main` が `run()` の全エラーを同じ文言で吐くため、障害時にログから原因が読めない。

**残る等価変異**: 「シードのエラーを無視する」はシードが常に正しいので挙動が変わらない。シードが壊れたときにだけ差が出るが、それを作るにはシードを差し替え可能にする必要があり、`buildHandler` の役割（具象を1箇所に集める）と噛み合わない。

## D-053 デロードの停滞種目を機械可読で返す

**判断**: `deload_proposal` に `stalled_exercises` を足し、`deload_accepted` に実在しない種目IDが来たら 400 を返す。

**根拠**: 敵対的検証で、承認フローが API から完走できないことが分かった。ドメインは `DeloadProposal.StalledExercises()` を公開し「根拠の文字列からしか取れないと、呼び出し側がどの種目を下げるか選べない」とコメントまで書いているのに、**DTO がその1フィールドだけ落としていた**。クライアントは承認する種目IDを日本語の散文から括弧を剥がして抜くしかなかった。

さらに悪いことに、IDを間違えても**黙って無視される**（200 が返り、重量は変わらない）。散文のパースが外れる → デロードが効かない → ユーザーは承認したつもりでいる、という無音の失敗が成立していた。実在しない承認は 400 で弾く。

## D-054 ドライバは pgx を直接使う

**判断**: `database/sql` を挟まず `pgx/v5` を直接使う。

**根拠**: `database/sql` の抽象が守るのは「SQL ドライバの差し替え」だが、このアプリの差し替え点はリポジトリインターフェースであって SQL ドライバではない。Postgres から別の DB へ移るなら、書き換わるのは SQL そのものであって、ドライバ層の抽象は何も助けない。挟むと prepared statement のキャッシュと型の扱い（`numeric`、`jsonb`、NULL 可能な数値）を捨てることになる。

## D-055 マイグレーションは自前で流す

**判断**: 埋め込んだ SQL を自前のランナーで流す。golang-migrate などは使わない。

**根拠**: 必要なのは「連番の SQL をトランザクションで順に流し、適用済みを記録する」だけで、80行で書ける。それに CLI とドライバ登録を持ち込む依存を足す理由がない。

**設計上の要点**:
- **アドバイザリロック**を取る。複数インスタンスが同時に起動しても二重適用しない（8並行で起動して適用履歴が1件のままであることをテストで固定）
- **1ファイル1トランザクション**。途中で失敗したらそのファイルの変更が丸ごと巻き戻り、適用済みとしても記録されない。半分だけ当たったスキーマは、次の起動で「適用済みでないのに既にある」という直しようのない状態になる
- **起動時に流す**。手で流す運用にすると、流し忘れたインスタンスが古いスキーマに書き込む

## D-056 スキーマの型の選び方

**判断**: `weight_kg` は `numeric(6,2)`、週目標と選択種目は `jsonb`、`program` は1行に固定。

**根拠**:
- **`numeric`**: `double precision` だと 87.5kg や 7.25時間が往復で揺れうる。桁数はドメインの量子化（小数6桁）に合わせる（当初 `numeric(6,2)` にして壊した。D-059）
- **`jsonb`**: 週目標を列に開くと、筋区分を1つ足すたびにマイグレーションが要る。読み出しは必ずコンストラクタを通すので、`jsonb` が形を検査しなくても境界で弾かれる（DB に `per_week = 99` を直接入れて読み出しが失敗することをテストで固定）
- **`id boolean PRIMARY KEY DEFAULT true CHECK (id)`**: 単一ユーザー前提を型で表す。2行目を作れないことをテストで固定した
- **`date` に渡す時刻は UTC 固定**: `date` 型に時刻もタイムゾーンも無い。DB 上の値が同じ暦日であることを、ドメインを経由せず生の `::text` で確かめる。ドメイン経由で読み直すと同じずれで戻ってきて気づけない

## D-057 契約テストは共有する

**判断**: 保存の契約を `repositorytest` パッケージに切り出し、インメモリ実装と Postgres 実装の両方に同じコードを流す。

**根拠**: D-033 で定めた契約は、インメモリ実装のテストにしか書かれていなかった。実装ごとに書き直すと、片方だけが契約を満たす状態に気づけない。**インメモリ実装は失敗しないので、契約の破れは Postgres で初めて露呈する**。そのとき「インメモリでは通っていた」では原因の切り分けにならない。

実際、Postgres 実装のミューテーションと敵対的検証から**契約側の穴が6つ**見つかった。

1. **取得順は「毎回同じ」では足りない**。`ORDER BY` を外しても、Postgres は小さなテーブルなら挿入順で返す。挿入順と辞書順をずらしたうえで ID の昇順を要求する
2. **並行時の衝突も `ErrConflictingSetLog` として返ること**。`FOR UPDATE` を外すと主キー違反が生のまま返り、409 のはずが 500 になる。クライアントは自分のID採番ミスに気づかず再送を繰り返す
3. **同一呼び出し内の合成は「後勝ち」まで見る**。睡眠だけ・体重だけという欠損しない項目どうしで書いていたため、合成の向きを逆にする変異を区別できなかった
4. **小数がそのまま往復すること**（D-059）
5. **同じ内容の並行再送は全部成功すること**（D-060）
6. **同じバッチの二重送信が詰まらないこと**（D-060）

いずれもインメモリ実装だけを見ていては出てこない。

## D-058 差し替えが cmd に閉じたことの確認

**判断**: 第5部の完了条件を「`internal/domain/`・`internal/application/`・`internal/presentation/` の差分がゼロであること」とし、実際にそうなった。

**根拠**: Onion の主張は「インフラが差し替え可能である」だが、主張のままでは検証されない。実際に差し替えて、内側の層に1行も変更が要らないことを確かめて初めて答え合わせになる。

第5部で変わったのは `cmd/api/main.go`（配線）、新設の `postgres` パッケージ、テスト用の `repositorytest`、それと `memory` の契約テストへの接続だけだった。

**ただし1箇所だけドメインに手を入れた**。`ErrRepositoryUnavailable` の追加（D-061）で、`internal/domain/training/repository.go` にセンチネルを1つ足している。これは配線の都合ではなくリポジトリの契約そのものの不足で、「保存先に到達できない」を表す語彙が無いと 500 と区別できない。インメモリ実装では起こりえない状態なので、Postgres を入れて初めて必要だと分かった。差し替えが内側を汚した例ではなく、**インフラを1つ実装したことで契約の抜けが見つかった例**として記録する。

**持ち越し**: D-034 で記録した `FindAll` が全件を返す設計は、Postgres でも据え置いた。実測値は D-065 に載せた。範囲クエリへ移る前に、`OneRepMaxEstimator` の EWMA が「直近Nセッションで打ち切っても同じ答えになる」N を実測する必要があるのは変わらない。

## D-059 桁数はドメインの量子化に合わせる

**判断**: `weight_kg` を `numeric(6,2)` から `numeric(10,6)` へ、体重を `numeric(9,6)`、睡眠を `numeric(8,6)` へ変更する（0002 で `ALTER`）。

**根拠**: D-056 の「ドメインは 1e-6 で量子化しているので `numeric(6,2)` で足りる」は論理が逆だった。`quantum = 1e6` は**小数6桁を保持する**という意味で、`numeric(6,2)` は2桁しか持てない。

実サーバーで確認した壊れ方:

```
POST 87.125kg → 204、DB には 87.13 が入る
まったく同じ内容を再送 → 409（内容が違うと判定される）
```

保存に成功したセットが**二度と再送できなくなる**。オフライン記録とタイムアウト後の再送を前提にした設計なのに、その経路が恒久的に 409 を返す。削除の口が無いので復旧手段もない。記録そのものも静かに書き換わり、推定1RMがずれたまま残る。

テストが通っていたのは、往復テストの値が `{0, 1.25, 2.5, 42.5, 87.5, 102.5, 187.5, 999.99}` と**全部2桁以内**だったから。3桁目を持つ値が1つも無かった。契約テストに `87.125` などを足し、**同じ内容の再送が通ることまで**確かめるようにした。

**マイグレーションは書き換えず新しいファイルを足した**。0001 を直すと、既に適用した DB との差異が検出できない。この規律を守らせるため、適用済みマイグレーションのチェックサムを記録して照合するようにした（バージョンだけだと、内容を変えても永久にスキップされる）。

## D-060 冪等性は「並行しても成り立つ」まで含む

**判断**: `SELECT ... FOR UPDATE` してから `INSERT` する形をやめ、`INSERT ... ON CONFLICT DO NOTHING` の後に読み直して内容を比べる形にする。保存対象は ID 昇順に固定する。デッドロックとシリアライズ失敗は再試行する。

**根拠**: 敵対的検証で、冪等性が3つの理由で壊れていた。

1. **`FOR UPDATE` は存在しない行を締められない**（READ COMMITTED に述語ロックが無い）。同じIDがまだ無ければ全員が「新規」と判断し、後発が主キー違反を踏む。その経路が内容を見ずに衝突と決めつけていたため、**内容が完全に同一でも 409** になっていた。実測で、同一内容の並行再送 2,400回のうち **2,093回が 409**。クライアントが「タイムアウトしたから再送」した瞬間に元のリクエストが生きていれば起きる
2. **保存順が呼び出しごとに変わっていた**（map の反復順）。同一リクエストの二重送信どうしが互いの行を待ち、実測で 50回中 **14回がデッドロックで 500**、正しく 204 になったのは26回だけ
3. **`40P01` / `40001` が 500 に落ちていた**。どちらもやり直せば成功する一時的失敗で、500 は「送り直しても無駄」という意味になる

読み直して比べる形にすると、同一内容の並行再送は全員が成功する（誰が入れたかを問わず、入っている内容が同じなら目的は達成されている）。ID 昇順への固定でロックの取得順が揃い、デッドロックが消える。

契約テストに「同じ内容の並行再送は全部成功する」「同じバッチの二重送信が詰まらない」を追加した。既存の並行テストは**内容が全部違っていた**ため、この穴を構造的に踏めなかった。

## D-061 保存先に到達できないことを 503 で表す

**判断**: `training.ErrRepositoryUnavailable` を追加し、接続断・接続数上限・シャットダウン中を翻訳する。プレゼンテーション層は 503 を返す。`/healthz` は保存先への疎通を含める。

**根拠**: DB が落ちている間、全リクエストが 500 を返し、**`/healthz` だけが 200 を返していた**。何も処理できないインスタンスがヘルスチェックに合格し続け、ロードバランサはトラフィックを流し込む。

500 は「送り直しても無駄」という意味を持つ。DB 断は後で送り直せば通るので、区別できる形で返す。

`/healthz` の差し替えは `cmd` で行う。プレゼンテーション層は保存先を知らないので、そこに疎通の口を持たせると依存の向きが崩れる。ルータの前に被せれば `cmd` に閉じる。

**実測（DB を停止・再開）**:

```
起動後            healthz=200
DB 停止後         healthz=503  sessions=503  program=503  set-logs=503
DB 復帰後         healthz=200  sessions=200
```

## D-062 使われない索引は落とす

**判断**: `set_logs_performed_on_idx` と `set_logs_exercise_idx` を 0002 で落とす。

**根拠**: `set_logs` を読む SQL は `FindAll` の1本だけで、`WHERE` 句が無い。日付や種目での絞り込みは全て Go 側のメモリ上で行っている（D-034）。実測で両索引とも**走査回数ゼロ**、合計1.9MB（5万件）を占め、`INSERT` ごとに2本ぶんの更新コストを払っていた。0001 のコメント（「週内カバレッジとデロード判定が日付で絞る」）は事実ではなかった。

範囲クエリへ移るときに、実際に使う形で作り直す。

## D-063 CI で Postgres のテストを必ず走らせる

**判断**: CI に Postgres のサービスコンテナと `TEST_DATABASE_URL` を足し、**スキップされていないことを検査する**ステップを置く。

**根拠**: `TEST_DATABASE_URL` が無いとテストは `t.Skip` し、パッケージは `ok` と表示される。検証で、`SetLogRepository.Save` の本体を丸ごと no-op に潰しても **CI は緑のまま**だった。D-057 が「契約の破れは Postgres で初めて露呈する」と言っている、その露呈の場が存在しなかった。

設定を消してもテストは緑になるので、走ったこと自体を検査する。

## D-064 取得順の照合順序を "C" に固定する

**判断**: `ORDER BY id COLLATE "C"`。

**根拠**: 照合順序を DB の既定に委ねると、ICU 照合の環境（Neon の既定）で大小文字混在や記号入りのIDの順序が変わり、**インメモリ実装と Postgres 実装の返す順序が食い違う**。ULID は大文字英数のみなので今すぐは壊れないが、「順序が揺れると同じ入力から違う計画が出る」（D-033）と言っている以上、環境依存の照合順序に委ねるのは筋が通らない。

## D-065 性能の実測値（D-058 の訂正）

**判断**: D-058 の「単一ユーザーなら許容範囲」に実測値を添える。

| | インメモリ | Postgres |
|---|---|---|
| `FindAll` 39,125件 | 6.30ms / 6.17MB | 27.1ms / 21.0MB |
| `FindAll` 50,000件 | — | 32.6ms / 25.8MB |
| `GET /api/sessions` 50,000件 | 17ms / 26.6MB | 72.6ms / 88.2MB |

3〜4倍。単一ユーザーなら許容範囲だが、**リクエスト1本あたり 88MB を確保する**ので `maxConns = 8` を使い切る並行度では GC 圧が跳ねる。D-034 の持ち越し（範囲クエリへ移る前に EWMA の打ち切り N を実測する）は、Postgres でより早く効いてくる。

## D-067 Cloudflare Workers ではなく Cloud Run に載せる

**判断**: Cloud Run（コンテナ）+ Neon（Postgres）。

**根拠**: Workers は V8 isolate なので、Go を載せるなら WASM にする必要がある。ところが Go の WASM ターゲット（`GOOS=js` / `wasip1`）では **`net` パッケージが使えない**。pgx は `net.Conn` の上に立っているので、Postgres へ繋ぐ手段がそもそも無い。Hyperdrive も Worker のバインディングで `nodejs_compat` 前提の JS ドライバ向けなので解決にならない。Workers に載せるにはサーバーを TypeScript か Rust で書き直すことになり、ドメイン層と判断記録を捨てる価値は無い。

Cloudflare Containers なら Dockerfile を載せられるが、beta（SLA 無し）で、前段に TypeScript の Worker と Durable Object のバインディングが要り、コールドスタートが 2〜3秒、最小インスタンスが 1/2 vCPU / 4 GiB。Cloud Run なら同じことが TS の層なしでできる。

**Neon は直接接続の文字列を使う**（`-pooler` ではない）。pgbouncer のトランザクションモードは prepared statement と相性が悪く、pgx の既定（statement cache 有効）だとエラーになる。単一ユーザーの接続数なら pooler は要らない。

## D-068 認証は Bearer トークン1つ

**判断**: 長いランダムトークンの Bearer 認証。ミドルウェアは presentation 層。

**根拠**: 単一ユーザーの個人アプリなら十分で、Android 側は安全なストレージに入れるだけで済む。OAuth へはミドルウェアの差し替えで移れる。

**ユーザーという概念を内側へ持ち込まない**。ドメインもユースケースも「誰が」を知らないままにする。マルチユーザーに開くときは、スキーマに `user_id` を足す作業とセットになるので、そのときにまとめてやる。

**細かい判断**:
- **定数時間で比較する**（`crypto/subtle`）。素朴な `==` は、一致する接頭辞が長いほど応答が遅くなるので、トークンを1バイトずつ推測できる
- **方式名は大文字小文字を無視する**（RFC 7235 の要求）。`bearer` と送るクライアントを弾くと、原因の分からない 401 になる
- **401 に `WWW-Authenticate: Bearer`** を付ける。クライアントが「認証が要る」と「壊れている」を区別できる
- **送られたトークンをエラーに載せない**。ログや画面に残る

## D-069 トークンが未設定なら起動しない

**判断**: `AUTH_TOKEN` が空、または32文字未満なら `buildHandler` が失敗する。

**根拠**: 「未設定なら認証しない」にすると、環境変数の設定漏れがそのまま全公開になる。**気づかないまま公開されるより、起動しないほうがよい**。32文字を下限にしたのは `openssl rand -hex 16` の出力長（128bit 相当）で、これ未満は総当たりの射程に入る。

## D-070 /healthz の持ち主を1つにする

**判断**: `/healthz` をルータ（`httpapi.Routes`）から外し、`cmd` が被せるものだけにする。

**根拠**: D-061 で保存先への疎通を含めるために `cmd` で `/healthz` を差し替えたが、ルータ側にも残っていた。ミューテーションで、**`cmd` の被せを外してもテストが緑のまま**になることが分かった。ルータ側の素朴な `/healthz` が応答してしまい、「DB が落ちていても 200」という D-061 で潰したはずの状態に戻る。

保存先への疎通を含める必要がある以上、プレゼンテーション層は `/healthz` を持てない（保存先を知らない）。両方に置くと、どちらが応答しているのか読んで分からなくなる。持ち主を1つにすれば、被せ忘れは 404 として現れる。

**残った等価変異**: 「Authorization の空トークンを通す」と「未設定でも起動する」の2つは、どちらも別のガードが受け止める。前者は空文字どうしの比較になるが `AUTH_TOKEN` が空では起動しないので到達しない。後者は長さの検査が拾う。多重の防御なので残す。

## D-071 Neon は直接接続、Cloud Run はシンガポール

**判断**: 接続文字列は `-pooler` の付かない直接接続を使う。Cloud Run のリージョンは `asia-southeast1`。

### 直接接続にする理由（D-067 の訂正）

D-067 では「pgbouncer のトランザクションモードは prepared statement と相性が悪く、pgx の既定だとエラーになる」と書いた。**これは実際の Neon に流して再現しなかった。** pooler 経由でもサーバーは起動し、読み書きとも通った。

本当の理由は別にある。**マイグレーションがセッションレベルのアドバイザリロック（`pg_advisory_lock`）を使っている**こと。トランザクションプーリングはトランザクションの外でバックエンドの固定を保証しないので、ロックを取ったバックエンドがプールに戻り、解放が別のバックエンドに当たりうる。二重適用を防ぐという保証が成立しない。

実測では、負荷の無い状態だと pooler でもセッションが固定されて `pg_advisory_unlock` が成功した。**固定されることもある、は保証ではない。**

もう1つの理由として、テストは `search_path` でスキーマを分離しており、pooler はこれを明示的に拒否する（`unsupported startup parameter in options: search_path`）。本番とテストで違う経路を通すのは、この設計で何度も潰してきた失敗の形なので、直接接続で揃える。

**接続数の見積もり**: `--max-instances=2` × プール上限8 = 16接続。0.25 CU の上限に収まる。

### リージョンをシンガポールにする理由

**Neon に東京リージョンが無い**（AWS の最寄りは ap-southeast-1）。この前提を私が間違えており、当初「東京に作り直す」と提案していた。

DB がシンガポールに固定される以上、Cloud Run をどこに置くかは往復の回数で決まる。`GET /api/sessions` はリポジトリを4本叩く。

| 構成 | 内訳 | 概算 |
|---|---|---|
| Cloud Run 東京 + DB シンガポール | 10ms + 70ms×4 | 約290ms |
| Cloud Run シンガポール + DB シンガポール | 70ms + 1ms×4 | 約74ms |

**ユーザーに近づけるより DB に近づけるほうが速い。** これは D-034 で据え置いた「`FindAll` が全件を返す設計」の帰結でもあり、往復が減れば配置の自由度が上がる。

## D-072 テストの分離が実際の Neon で壊れていた

**判断**: テスト用の `search_path` の渡し方を `?search_path=` から `options=-c search_path=` に変える。pooler が指定されたらテストを止める。

**根拠**: 実際の Neon に契約テストを流したら、**全テストが同じスキーマを共有していた**。あるテストが壊した `schema_migrations` を他のテストが踏み、原因の読めない失敗が並んだ。

原因は `?search_path=` が **libpq のパラメータではない**こと。psql は `invalid URI query parameter` で拒否する。pgx は独自に起動パラメータとして送るので、ローカルの Postgres には素通しで届き、**ローカルでは緑のまま**だった。Neon のプロキシは通さないので、`search_path` が効かず全部が `public` に落ちていた。

標準の `options=-c search_path=...` なら両方で効く。

**これはローカルの Docker では絶対に見つからなかった。** D-057 で「契約の破れは Postgres で初めて露呈する」と書いたが、同じことがもう一段あった。**本物のマネージド Postgres に流して初めて露呈するものがある。**

pooler を指定されたときに黙って共有スキーマへ落ちるのではなく止めるのは、同じ混乱を繰り返さないため。

## D-073 ヘルスチェックの経路は /healthz にしない

**判断**: `/healthz` をやめて `/health` にする。

**根拠**: Cloud Run にデプロイして初めて分かったが、**Google のフロントエンドが `/healthz` を完全一致で横取りする**。アプリまで届かず、Google の HTML の 404 が返る。

実測（同じホスト）:

| 経路 | 応答 | Content-Type |
|---|---|---|
| `/healthz` | 404 | `text/html`（Google のエラーページ） |
| `/healthz/` | 401 | `application/json`（アプリの応答） |
| `/health` | 401 | `application/json` |
| `/`・`/foo` | 401 | `application/json` |

完全一致のときだけ横取りされる。ローカルの Docker では同じイメージが 200 を返すので、**デプロイするまで気づけない**。

これが放置されると、D-061 で入れた「ヘルスチェックに保存先の疎通を含める」が本番で機能しない。DB が落ちていても Google が 404 を返すだけで、こちらの 503 は誰にも届かない。監視を繋いでも意味を持たない。

経路の定数を `httpapi.HealthPath` として1箇所に置き、認証の除外リストと `cmd` の被せの両方がそれを参照する。値を戻していないことをテストで固定した。

**この種のものは、本物の環境に出すまで見つからない。** D-072（実際の Neon で初めて露呈したテストの分離不良）と同じ形で、今回はプラットフォームの側から来た。

## D-074 自動デプロイは Workload Identity 連携で鍵を持たない

**判断**: GitHub Actions から Cloud Run へ自動デプロイする。認証は Workload Identity 連携（OIDC）で、サービスアカウントキーを GitHub に置かない。

**根拠**: サービスアカウントキーの JSON を GitHub Secrets に置く方式は広く使われているが、**漏れたら取り返しがつかない**（失効させるまで誰でも本番へデプロイできる）うえ、定期的な入れ替えを人手で回す必要がある。Workload Identity 連携なら、GitHub が発行する短命の OIDC トークンを GCP が検証するので、**盗まれて困る長期の秘密がそもそも存在しない**。

**借用できる範囲を絞る**: プロバイダに `assertion.repository=='dyoshyy/liftplan-server'` の条件を付け、サービスアカウント側の `workloadIdentityUser` も同じリポジトリの principalSet に限定した。条件を付けないと、**GitHub のどのリポジトリからでもこのサービスアカウントを借りられる**（他人のフォークを含む）。これは Workload Identity 連携で最も多い設定ミス。

**権限は2つだけ**: `run.admin` と `artifactregistry.writer`。加えて実行用サービスアカウントへの `actAs`。`editor` のような広いロールを与えない。

## D-075 デプロイの前にテストを回し、後で疎通を確かめる

**判断**: Deploy ワークフローの中でテストを回し、デプロイ後に `/health` と 401 を確認する。

**根拠**:

- **CI の成功を当てにしない**。「CI が通っているはず」に依存すると、`workflow_dispatch` のような CI を経ない経路で無検証のまま出てしまう。同じテストを Deploy の前段で回すほうが、経路が増えても壊れない
- **デプロイの成功は起動の成功ではない**。Cloud Run はリビジョンを作れても、起動に失敗していれば意味がない。実際、`AUTH_TOKEN` が未設定なら起動しない設計（D-069）なので、秘密の設定漏れはここで初めて分かる
- **認証がかかっていることも確かめる**。ヘルスチェックは認証を通さない経路なので、認証を壊したまま出しても 200 が返る。401 を確認して初めて「壊れていない」と言える

**イメージのタグはコミットの SHA**。`latest` だけだと、ロールバックしたときに何に戻ったのか分からない。

**`concurrency: deploy`** で同時実行を止める。連続で push したとき、古いビルドが後から新しいリビジョンを上書きしうる。

**main への push で CI と Deploy を二重に走らせない**。CI は PR だけを見るようにした。
## D-066 application 層のディレクトリを1段深いまま残す

**判断**: `internal/application/usecase` をフラットな `internal/usecase` にせず、4層すべてを同じ形（`internal/<層>/<パッケージ>`）で揃える。

**根拠**: 中身が `usecase` 1つしかない現状では、`application/` は1段ぶん無駄になっている。Go の実践ではフラットな `internal/{domain,usecase,infrastructure,presentation}` のほうが多く、import パスの最後のセグメント（＝パッケージ名）で意味は足りている。

それでも残すのは、**import 行そのものが層を語るから**。

```go
import "github.com/dyoshyy/liftplan-server/internal/presentation/httpapi"
import "github.com/dyoshyy/liftplan-server/internal/infrastructure/postgres"
```

この2行が同じファイルに並んでいれば、依存方向の違反だと読んだ瞬間に分かる。フラットだと `internal/httpapi` が `internal/postgres` を import しているだけに見えて、どちらが外側かを知っていないと気づけない。`internal/architecture_test.go` は落としてくれる（D-051）が、レビューで気づけることはそれとは別の価値がある。

`domain/training` の1段は意味が違い、こちらは**境界づけられたコンテキスト**の名前。別の領域が増えたら `domain/nutrition` のように並ぶ。

**枠だけ作ったもの**: `application/query/`。過去の記録を集計して見せる経路は `SessionPlanner` を通らず、リポジトリでもないので、ユースケースとは別のパッケージになる。

**作らなかったもの**: 認証（第6部）は、単一ユーザー向けの最小構成ならトークンを見るミドルウェアで済むので presentation 層に入る見込み。application に置くのは、ログインやセッション管理まで育ってから。port（Clock、ID 生成）は、いま日付を外から渡す設計なので必要になっていない。**来るか分からないものの枠は作らない。**空のディレクトリは、そこに何かがあるという誤った期待を生む。

## D-077 クライアントは PWA を先に出す

**判断**: Android の前に、サーバーに同居する PWA を出す。

**根拠**: 「使い始める」と「Android を学ぶ」は別の目的で、最短路が違う。サーバーは完成しているのに**まだ1度も使われていない**。スロットの強度も週目標もシミュレーションでしか検証されておらず、**本人の体では検証されていない数字の上に積み上げている**状態が続いている。Android をゼロから立ち上げる間ずっと記録が取れないのは、その損失が大きすぎる。

PWA は捨てる前提で作り込まない。Android ができたら消してよい。

## D-078 画面はサーバーに同居させる

**判断**: 静的資産を Go のバイナリに埋め込み、同じ Cloud Run が返す。

**根拠**:

- **CORS が要らない**。同一オリジンなのでプリフライトもオリジン許可リストも不要
- **デプロイ経路が増えない**。既存の自動デプロイにそのまま乗る
- **画面と API のバージョンがずれない**。成果物が1つなので「新しい画面が古い API を叩く」が原理的に起きない

代償は、画面を直すたびにサーバーごと再デプロイになることと CDN に載らないこと。単一ユーザーでは体感に出ない。**Android からは CORS が無関係**なので、後で分ける動機も薄い。

**公開する経路は明示的な一覧にする**。「`/api` 以外は公開」にすると、後から足した経路が既定で公開になる。fail-closed を保つ。

**ルートは `GET /{$}` で登録する**。`GET /` にすると Go の ServeMux では**全ての GET の受け皿**になり、POST しか無い経路への GET が 405 ではなく静的配信に流れて 404 になる。クライアントは「経路が無い」と「メソッドが違う」を区別できなくなる。実装中に実際に踏んだ。

## D-079 記録は待ち行列に積んでから送る

**判断**: 記録はまず localStorage に積み、それから送る。送れたものだけ消す。

**根拠**: ジムの電波は途切れる。送信を先にすると、失敗した瞬間に記録が消える。**保存してから送れば、失敗しても次の機会に送れる**。

**IDはクライアントが採番する**。サーバー採番だと、応答が届かなかったときに「保存されたのか分からない」が発生する。クライアント採番なら同じIDで何度でも再送してよい（D-060 で冪等にした経路がここで効く）。

**4xx は捨てる**。409（同じIDで内容が違う）も 400 も、再送しても永久に通らない。残すと後続が全部詰まる。5xx と通信断だけを残す。

**API の応答はキャッシュしない**。Service Worker が持つのは画面の殻だけ。古いメニューを出すくらいなら出ないほうがよい。「昨日の重量が表示されているのに気づかない」は記録そのものを壊す。
## D-076 リリース台帳は Cloud Run のリビジョン

**判断**: リビジョン名に短縮コミットSHAと実行番号を入れ、`commit` と `run-id` をラベルに貼る。Git のタグは打たない。

**根拠**: 自動デプロイを入れた直後の状態では、履歴は追えるが**一手間かかった**。リビジョン名が `00004-fgj` のような自動採番で、**名前を見ても何のコードが動いているのか分からない**。イメージのタグがコミットSHAなので辿れはするが、`services describe` を叩いてタグを切り出す必要があった。

リビジョン名に短縮SHAを入れると、`revisions list` を見るだけで分かる。

**実行番号を足す理由**: 同じコミットを出し直すと名前が衝突してデプロイが失敗する。再実行やロールバックのやり直しで普通に起きる。

**Git のタグを打たない理由**: リリースの事実は Cloud Run 側に既にある（いつ・何が・今どれが動いているか）。タグを打つと同じ事実が2か所に増え、片方だけ失敗したときに食い違う。分かることが増えないなら、増やさない。

**`make releases`** で一覧する。コミットの件名は `git log` から引くので、リビジョン一覧だけでは読めない「何をした版か」が並ぶ。

**ロールバックの注意をドキュメントに書いた**: トラフィックは戻せるが**マイグレーションは戻らない**。いまの2つは後方互換（型の拡張と索引の削除）だが、列の削除を入れた瞬間に戻せなくなる。

## D-080 読み取り専用の経路を query パッケージに置く

**判断**: 履歴・推移・週目標の充足を `internal/application/query` に置く。ユースケース（`usecase`）とは分ける。

**根拠**: 責務が違う。ユースケースはデータを集めてドメインに渡し、状態を進める。読み取りは状態を変えず、既にある記録を読める形に整えるだけで、`SessionPlanner` を通らない。

整形をプレゼンテーション層に置くと、画面ごとに同じ集計を書き直すことになる。ドメインに置くと、表示の都合がドメインに漏れる。

D-066 で `application/query/` の枠を作ったときに「来る」と言っていたもの。

**数え方はエンジンと共有する**。週目標の充足は `training.CoverageBetween` を使い、`SessionPlanner` も同じ関数を通す。別々に実装すると、画面に出る数字とエンジンが使う数字がずれる。ずれた瞬間、どちらが正しいのか誰にも分からなくなる。

## D-081 実績の削除を契約に足す

**判断**: `SetLogRepository.Delete(ctx, id)` を追加し、`DELETE /api/set-logs/{id}` を出す。

**根拠**: `SetLog` は「確定した実績1セット」で生成後は変更しない。削除はその前提と衝突するように見えるが、意味が違う。値を書き換えるのではなく「**これは起きなかった**」と言っている。

訂正の手段が無いほうが害が大きい。同じIDで直そうとすると衝突として弾かれ（D-060）、別IDで正しい値を入れても間違った記録は残り続けて推定1RMを汚す。単一ユーザーの個人アプリで、消せない記録に価値は無い。

**存在しないIDの削除は成功として扱う**。再送で二度目が来ることがあり、そこでエラーにすると「消えているのに消せない」という状態になる。

画面での訂正は「消してから入れ直す」の2操作を1つの操作として見せる。同じIDで内容を変えるのはサーバーが拒否するので、クライアントが分ける。

## D-082 Sessions は日付でまとめたもので、種目単位ではない

**判断**: 履歴の整形で、1日の中を種目ごとに分ける処理を `query` 側に書く。

**根拠**: `History.Sessions()` は**同じ日でまとめる**もので、1日の中に複数の種目が入る。これをセッション＝種目と取り違えて `logs[0].ExerciseID()` で代表させると、**その日の最初の種目しか出ない**。

実際にそう書いて、実データを流して初めて気づいた。テストは1日1種目のケースしか書いておらず、緑のまま通っていた。1日に複数種目をやるのはこのアプリの前提そのもの（全身法）なのに、その当たり前をテストが確かめていなかった。

`ForExercise(id).Sessions()` のように先に絞ってから使うのは正しい（推移の計算はそうしている）。絞らずに使うときだけ危ない。

## D-083 期間の指定に上限と既定を置く

**判断**: `from` / `to` を省略したら直近56日。上限は400日。

**根拠**: 既定を持たせるのは、画面が毎回日付を組み立てなくて済むようにするため。端末とサーバーの日付がずれる余地も減る。

56日にしたのは、デロードの判定が8セッション（D-020）で、判断に使う窓をひととおり含む長さだから。

上限が無いと、3年ぶんを1回で要求されたときに応答が数MBになる。単一ユーザーでも、画面が固まれば使えないことに変わりはない。

## D-084 前回との差分バッジを出さない

**判断**: 種目カードに「前回比 +11.5kg」のようなバッジを出さない。前回の実績（重量とレップ）だけを出す。

**根拠**: 実際に画面を見て気づいた。ベンチが `前回 91kg → 今日 102.5kg「+11.5kg」` と出ていたが、これは**伸びではない**。前回が標準スロット（強度0.81）、今日が高強度スロット（0.88）というだけで、役割が違えば重量が違うのは当然。

差分を出すと「増えた＝良い」という誤った要約を押し付けることになる。伸びているかは推定1RMの推移でしか答えられない（レップ数が違う日どうしを比べられるのはそちらだけ）。

これはドメインの思想と同じ形をしている。RIR は止め時の指示でレップは結果、というのと同じで、**要約しすぎない**。判断の材料を出して、判断は人に残す。

同じ役割の前回と比べる案もあったが、`SetLog` に役割を持たせることになり、実績が「その日の計画」に依存し始める。実績は起きたことだけを持つべきなので採らない。

## D-085 画面を見ないと分からないものがある

**判断**: ヘッドレスの Chromium を chromedriver 経由で操作し、実際の画面を撮って確かめる工程を入れる。

**根拠**: テストは全部緑、API も正しい応答を返していたのに、**画面は真っ白だった**。初期状態で全ての section が `hidden` なのに、`setup` が隠れているかどうかで表示切り替えを判定していて、一度も切り替わらなかった。

同時に、動かして初めて分かったものが他に4つあった。

- 差分バッジが誤解を生む（D-084）
- 筋区分が英語のまま（`CHEST_LOWER` はジムで読めない）
- 週目標が21区分すべて並んで長すぎる（上位6件＋展開に変更）
- 点が2つしかないのに面グラフが描かれ、無い情報があるように見える

いずれも構文検査でも API のテストでも出てこない。**出力を見るまで存在しない情報**がある。

`chromedriver` は環境に既にあり、WebDriver プロトコルは JSON over HTTP なので、追加の依存なしに操作と撮影ができる。

## D-086 その日の提示は、その日が始まる前の記録から決める

**判断**: 重量の推定に当日の記録を含めない（`historyBefore`）。週内カバレッジ（D-021）は当日を含めたまま。

**根拠**: 実ブラウザで1セット記録したら、**今日の目標が 102.5kg → 105kg に上がった**。記録（102.5kg × 6 RIR1）が推定1RMに反映され、同じセッションの中で提示が動いた。

しかも向きが最悪で、**RIR を守ってきついセットをこなすほど推定が上がる**（Epley はレップが少なくRIRが低いほど高い1RMを出す）。追い込むほど次のセットが重くなる。

「今日どれだけ埋めたか」は当日が本質なのでカバレッジには含める。「今日いくつでやるか」は当日の結果が入ると自己参照になるので含めない。同じ履歴でも、問いによって見る範囲が違う。

## D-087 セッションの途中でメニューが動かないようにする

**判断**: 補助種目の選択に渡す履歴からも当日を外す。提示の並びは種目IDの昇順に固定する。

**根拠**: 実サーバーで消化していて2つ踏んだ。

1. **1セット記録すると、その種目がリストから消えた**。記録によってその筋区分が「たった今刺激した」扱いになり、`nextRegion` の優先順位（最も長く放置している区分から）で最下位に落ちて、種目ごと枠から外れる。残り2セットが記録できない
2. **並びが毎回入れ替わった**。残差が当日の記録で変わるため、同じ8種目でも順序が動く

どちらも「ジムで消化している最中に、リストが自分の下で動く」という同じ形。何を選ぶかは、その日が始まる前に分かっていたことで決める。

並びについては、`Select` が返す順序は「最も放置している区分から」という優先度だが、**その中での並びは情報ではない**。8枠に選ばれたかどうかに優先度は既に表れている。安定を取る。

## D-088 補助の枠は「その日にやる種目数」であって、常時埋める数ではない

**判断**: 提示は「着手して途中の種目」を必ず含め、「こなし終えた種目」のぶん枠を減らし、残りを新規で埋める。

**根拠**: 通しで消化する検証を書いたら、**60手やってもセッションが終わらなかった**。補助を3セット終えると枠が空き、新しい種目が補充される。種目マスタに26種目あるので延々続く。

D-021 で「セッションが終わらない」を潰したはずだったが、あのときの原因は当日の実績がカバレッジに入っていないことで、今回は枠の補充。**同じ症状の別の原因**だった。

3つの規則はどれが欠けても壊れる。着手済みを残さないと1セットで種目が消える。終えたぶんを引かないとセッションが終わらない。残り枠を埋めないと、途中でやめた日に次の種目が出てこない。

修正後、通しで消化して**予定どおり36セットで完了**することを実サーバーとテストの両方で確認した。

## D-089 使ってみるまで見つからないものがある

これまでに見つけ方が3段階あった。

1. **テスト**（緑でも壊れているものがある）
2. **本物の環境**（D-072 の Neon、D-073 の Cloud Run）
3. **実際に触る**（D-085 の真っ白画面、D-086〜088）

3で見つかった4件は、どれもテストが緑で API も正しい応答を返していた。**セッションを最後まで消化する**という当たり前の使い方を、テストが一度もしていなかったのが共通の原因。

以後、通しで消化する検証をテストに置いた（`TestSessionPlanner_SessionEndsAfterThePlannedWork`）。

## D-090 送信キューは毎回 store から読み直す

`flush` は手元に配列を持ったまま `setQueue` していた。送信を待っている間に `enqueue` が走ると、flush が持っている古い配列で上書きされ、**あとから積んだぶんが送信されないままキューからも消える**。

電波の細いジムで続けて2セット記録すると、2つ目が黙って失われる。画面には「同期済み」と出るので、気づく手がかりが無い。

再現を書いて確かめた。修正前は送信されたのが `["A"]`、修正後は `["A","B"]`。

毎回 `store.queue()` から読み直すようにした。先頭から順に処理し、末尾に積まれるという性質があるので、読み直しても処理位置はずれない。

## D-091 訂正しても同じIDを使う

セットを直すとき、古いIDを消して**新しいID**で入れ直していた。並び順は `ORDER BY id`（IDが `Date.now()` 由来なので実質は作成時刻順）なので、直したセットだけが末尾に飛ぶ。**1セット目を直すと3セット目になって出てくる**。

先に消してから入れ直すので、同じIDでも衝突にはならない。IDを使い回すようにして位置を固定した。

なお実施順そのものは記録していない（`performed_on` は日付のみ）。IDの作成時刻順で代用している。

## D-092 セットごとの重量を畳まない

履歴は `sets[0].weight_kg` を代表として「100kg × 8, 8, 8」と出していた。途中で重量を変えると、**もう片方の重量が画面から消える**。実際 105kg と 101kg のセットが「101kg × 5, 5」と表示された。

サーバー側の「前回」も同じで、`ls[0]` の重量で代表させていた。

両方直した。同じ重量が続くならまとめ、変わったら区切る（`105kg × 5　/　101kg × 5`）。`LastPerformance` にはセットごとの `Weights` を持たせ、`WeightKg` は「次に何kgから入るか」の目安なのでその日の最重量にした。

## D-093 alert() を使わない

入力が足りないとき `alert()` を出していた。ダイアログを閉じるまでページ全体が止まり、直したい入力欄そのものが隠れる。検証中に実際にこれで画面が固まった。

シートの中と設定カードの中に、その場で出すようにした。破壊的操作の確認（トークン削除）だけ `confirm` を残している。

## D-094 query パッケージにテストが無かった

`application/query` はテストが1本も無いまま出ていた。D-092 のバグが出た場所でもある。

`Days` / `LastPerformances` / `Trends` / `WeeklyVolume` にテストを書き、変異21個を入れて**21個すべて検知**することを確かめた。最初は「同じ種目に過去の日が複数あるとき最新を選ぶ」が抜けていて1個すり抜けたので、テストを足した。

## D-095 圏外で開いたときに画面を出す

`loadAll` が失敗すると `showView` に到達せず、**起動直後は全ての画面が hidden なので真っ白**になる。状態表示に「つながりません」と小さく出るだけで、何が起きたか分からない。

D-085（真っ白画面）と同じ症状で、原因は別。あちらは `showView` を呼んでいなかった。こちらは例外で飛び越していた。

圏外でも画面を出し、なぜメニューが出せないかを書いた。古いメニューをキャッシュして出さない理由（前回の重量が今日の重量として出ると記録が壊れる）も、その場に書いてある。

圏外でも体重と睡眠は入力できてキューに溜まる。実際に溜めて、復帰後に送られることを確かめた。

## D-096 Service Worker は自分のところのファイルだけ扱う

`fetch` ハンドラが全ての GET を通していたため、**Google Fonts の woff2 が殻キャッシュに溜まっていた**。日本語フォントは100以上のサブセットに分かれて配られるので、文字が出るたびに増える。上限は無い。

実測すると、少し触っただけで殻に十数個のフォントが入っていた。同一オリジンだけを扱うようにして、4件（`/`, `/app.js`, `/app.webmanifest`, `/icon.svg`）に収まることを確認した。

あわせて、失敗の応答を殻に保存しないようにした。500 のエラーページを掴むと、次に圏外で開いたときそれが画面として出続ける。

## D-097 捨てた記録を黙って消さない

4xx はキューから捨てる。再送しても永久に通らないので、残すと後続が全部詰まる（この判断自体は変えない）。

ただし捨てたあと「同期済み」と表示していた。**記録したはずのセットが無いのに、画面はうまくいったと言う**。今回このセッションで潰してきた無言のデータ消失（D-090）と同じ形をしている。

捨てたものを端末に残し、何を失ったかを1行で出すようにした（`2026-08-23 ベンチプレス 100kg × 5（400）`）。リロードしても消えず、本人が「消す」を押すまで残る。上限は20件。

## D-098 承認したデロードはその日のあいだ覚える

デロードを承認すると重量が10%下がるが、**更新やリロードで元に戻っていた**。承認は `deload_accepted` というクエリパラメータで渡すだけで、どこにも残していなかった。

トレーニング中に更新を押すと、指示が 87.5kg から 97.5kg に跳ね上がる。下げた重量でやると決めた直後に、上げた重量が出てくる。

日付つきで端末に持たせた（`{date, ids}`）。日付が変われば使わないので、翌日に持ち越さない。サーバーに持たせなかったのは、承認がその日その場の判断で、記録として残す性質のものではないため。実績が入れば推定1RMがそれを追うので、翌日以降は履歴から導出される。

## D-099 承認後も同じ提案を出し続けない

承認したあとも「ベンチプレスを10%落とす」というボタンが同じ文言のまま残っていた。効いたのかどうか分からず、もう一度押したくなる（押しても二重には効かないことは確認した）。

承認後は「落として組み直しました」と出し、ボタンは「元に戻す」に変える。承認は判断であって確定ではないので、戻せるようにしてある。

## D-100 実際に直したバグを、テストで留める

D-086〜088 は画面を触って見つけ、手で直した。あとから変異を入れて確かめたところ、**同じバグを戻しても半分はテストが緑のまま**だった。

| 入れた変異 | 最初 | 対処後 |
|---|---|---|
| メインの推定に当日を混ぜる | 見逃し | 検知 |
| 補助の並びを固定しない | 見逃し | 検知 |
| 推定に当日を含める | 検知 | 検知 |
| 枠の調整を外す | 検知 | 検知 |

1つ目が見逃されたのは、既存のテストが**同じ重量**で当日のセットを記録していたため。当日を混ぜても推定が動かず、数字が変わらないことがあった。明らかに重いセットで確かめるテストを足した。

2つ目は、その場の並びがたまたま整っていたため差が出なかった。**着手済みの補助があると並びが崩れる**という、実際に踏んだ状況を作るテストを足した。

直したときに「テストが緑だから大丈夫」ではなく、**壊し直して赤くなるか**を見る。

## D-101 読み取り経路の変異カバレッジ

## D-102 予定を超えたセットも画面に出す

枠は `planned.sets` ぶんしか描いていなかった。予定より多く記録すると、**はみ出したセットは画面から消え、取り消すこともできない**。取り消しを試していて、消したはずの1件が別の記録に置き換わったので気づいた（隠れていた4セット目が繰り上がっていた）。

記録の数が予定を超えたら、その数だけ枠を出す。超えたぶんは「4セット目・追加」と書く。

## D-103 今日やったものは今日の画面に残す

補助種目は終わると枠から外れる。セッションを最後まで消化して開き直すと、**カードが11枚から3枚に減り、やった24セットが今日の画面から消える**。履歴には残っているが、今日の画面から消えれば記録が飛んだように見える。

画面のボタンだけで36セット通して消化したところ（リスト入れ替わり0件で完走）、直後のリロードでこれを踏んだ。

予定に入っていないが今日の記録があるものを「今日やったもの」として出す。予定として出すと「これからやる」と読めるので、重量やRIRは出さず「今日やった Nセット」とだけ書く。設定を変えて種目が外れた場合にも同じように残る。

## D-104 トークンが弾かれても記録は残っている

401 を受けると端末のトークンを消して初期設定の画面に戻る。このとき**未送信のキューは残っているのに、画面には何も出ない**。記録ごと消えたと思う。

トークンが変わったのは送り先の話で、記録の話ではない。初期設定の画面に「未送信の記録が N 件あります。トークンを入れ直せば送られます」と出すようにした。誤ったトークン → 正しいトークンと入れ直して、保留していた記録が届くことを確認した。

## D-105 記録が1回しか無いときに増減を出さない

推定1RMの推移で、記録が1セッションしか無い種目にも「0.0」と出していた。比べる相手がまだ無いだけなのに、伸びていないように読める。

スパークラインは3点未満で出さないようにしてある（無い情報があるように見せないため）。増減も同じ理屈なので、2点未満では出さない。

## D-107 待ち行列を localStorage から IndexedDB に移す

同じ端末で2つ開いていると、**両方の記録が互いを消す**。localStorage には「読んで、足して、書く」を割り込まれずに行う手段が無いため、`enqueue` の読み書きがぶつかると、あとから書いた方が相手の追記を巻き戻す。

2タブから3セットずつ記録して確かめた。

| | 記録した重量 | キューに残ったもの |
|---|---|---|
| 修正前 | 100,101,102 / 204,205,206 | 204,101,206（**3件消失**） |
| 修正後 | 同上 | 100,204,101,205,102,206（**全6件**） |

携帯とPC、あるいはPWAとブラウザタブという、ごく普通の使い方で踏む。

IndexedDB の書き込みはトランザクションなので、追記どうしがぶつからない。2つのタブが同時に送ると二重送信になるが、同じIDの同じ内容はサーバーが黙って受け入れる契約（D-070）にしてあるので害はない。復帰後に両タブから送って、6件が重複なく届くことを確認した。

表示は同期で描くため、件数と捨てたものの一覧は手元にも保持する。古い版が localStorage に残したぶんは起動時に引き取る（捨てると記録が消える）。引き取りも実際に確かめた。

D-090 と同じ「無言のデータ消失」だが、あれは1つのタブの中の競合で、こちらはタブ間。直し方も別で、あちらは読み直し、こちらは保存先そのものを替えた。

## D-109 コンテナで動かして確かめる

Cloud Run に出す前に、同じイメージを Cloud Run と同じ渡し方（`PORT` 環境変数、非 root）でローカルに立てて通した。

- distroless の nonroot（uid 65532）で起動し、マイグレーションが通る
- 画面のボタンだけで36セット完走、入れ替わり0件、Postgres に36件保存
- ログに error / panic / warn なし
- SIGTERM で「処理中のリクエストを待つ → 停止した」を出して exit 0

これで残る差分は、雲の上の設定（Secret Manager、Workload Identity、ネットワーク）だけになる。

**ひとつ現実と噛み合っていない点**: `shutdownTimeout` は 35秒（`writeTimeout` 30秒 + 5秒）だが、Cloud Run は SIGTERM のあと約10秒で強制終了する。35秒ぶん待てるという前提は Cloud Run では成り立たない。ただし実測でリクエストは1ms未満なので、待つべきものが残っていることは実際には起きない。値は変えず（短くすると `writeTimeout` を下回り、サーバー自身が許可した長さのリクエストを必ず切ることになる）、ここに書き残す。

## D-110 実環境の検証は、本番に触らずに使い捨てで行う

Cloud Run 上でしか出ないバグは、マージを待たないと確かめられない——と考えていたが、そうではなかった。**使い捨てのサービスと DB ブランチ**を作れば、本番に触れずに同じことができる。

やったこと（すべて本番とは別物）:

1. Neon に検証用ブランチを切る（期限を24時間に設定し、放っておいても消える）
2. このブランチのコードでイメージを組み、Artifact Registry に上げる
3. `liftplan-verify` という別サービスとしてデプロイし、上のブランチDBを向ける
4. 確かめたら、サービスとイメージを消す

**接続文字列は `-pooler` が返ってくる**。D-072 のとおり直結に直して使う。Neon の既定がプール側なので、毎回ここで踏む。

確かめた結果:

| | 結果 |
|---|---|
| 起動 | cold 0.42s / warm 0.21s |
| マイグレーション | 4テーブルすべて作成 |
| 認証 | トークン無し 401 / 正しいトークン 200 |
| 通しで消化 | 画面のボタンだけで33セット完走、入れ替わり0件 |
| Neon への保存 | 当日ぶん33件ちょうど、**重複0** |
| Cloud Run のログ | error / panic / warn なし |

今回直したものが実環境で効いていることも見た。`95kg × 8, 8　/　100kg × 8`（D-092 の重量分割）、リロード後の「今日やったもの」（D-103）、記録が1回だけのデッドリフトに増減が出ていないこと（D-105）。

**本番サービスに対しては読み取りだけ**行った。`/health` が 200 を返すこと自体が、Secret Manager と Neon がつながっている証拠になる。`/healthz` は 404 で、Google のフロントエンドが予約している（D-074 の改名が正しかった）ことも確認できた。

以後、デプロイに関わる変更はこのやり方で確かめてからマージする。

## D-111 CI の認証経路を、マージせずに確かめる

残っていた未検証部分は「GitHub Actions が Workload Identity で Google に認証して本番に出す」経路だった。マージしないと確かめられないと思っていたが、**読み取りしかしない一時ワークフローをブランチに置けば**確かめられる。

結果は成功だった。`github-deployer@liftplan-85309.iam.gserviceaccount.com` として認証され、Artifact Registry と Cloud Run にアクセスできた。

**ただし、成功したこと自体が問題だった。** 実行したのは `refs/heads/feat/33-stories` である。つまり **main 以外のどのブランチからでも、本番デプロイ用のサービスアカウントが取れる**。

## D-112 本番に出せるのは main だけにする

穴は2つあった。

1. `deploy.yml` の push トリガーに `feat/30-auth` が残っていた。「マージ前に外す」と自分でコメントを書いたまま外し忘れており、ブランチも remote に実在していた。ここに push すれば本番に出る。
2. Workload Identity の条件が `assertion.repository` だけで、ref を見ていなかった。`workflow_dispatch` は ref を選んで実行できるので、push の `branches` では止められない。さらに、新しいワークフローを任意のブランチに置けば同じ権限が取れる（実際にそうやって確かめた）。

両方を塞いだ。

- 条件を `assertion.repository=='dyoshyy/liftplan-server' && assertion.ref=='refs/heads/main'` にした
- `deploy.yml` のトリガーから `feat/30-auth` を外した
- デプロイの手前で `GITHUB_REF` を確かめる段を足した。Workload Identity 側の条件はリポジトリの設定から見えないので、ここにも書いておく

**両方向で確かめた。**

| | 結果 |
|---|---|
| ブランチから認証 | `unauthorized_client: The given credential is rejected by the attribute condition.` |
| main からデプロイ（同じコミットを出し直し） | 成功。`liftplan-server-2f3cf06-7`、本番 `/health` 200 |

絞り込みで本番のデプロイを壊していないことまで確認してある。片方だけ見て終わりにすると、次にマージした人が詰まる。
