# 判断の記録

**いま効いている判断と、その根拠。**覆された判断は消してある。

- **D番号は当時の通し番号。**コードのコメントから参照されているので、生きている判断は番号のまま残す
- **欠番は覆された判断。**やめた理由が今も効くものだけ「やめたもの」に残した
- **全文は git 履歴にある。**当時の経緯（敵対的検証の指摘一覧、変異の件数、PR番号）はそちらで読む

書き方は t-wada の教えに従う。ここに書くのは **Why** と **Why not**。How はコード、What はテストにある。

## 値オブジェクトと型

### D-004 Date は年月日の整数で持つ

`time.Time` を内包しない。`struct { year int; month time.Month; day int }`。

`time.Time` だと3つ壊れる。`==`（wall/ext/loc 全一致）と `Equal()`（瞬間比較）が食い違ってマップキーが割れる。同一パッケージから `Date{t: 正午の time.Time}` を書けて正規化を素通りできる。`DaysSince` が ±106751日（int64 ナノ秒）で飽和し、一見もっともらしい値を返す。

整数表現にすると3つとも構造的に消える。`Weekday` / `AddDays` / `DaysSince` は通日（Howard Hinnant の days_from_civil）で実装した。

### D-005 NewDate はエラーを返す。MustDate はテスト専用

`2026-02-30` を黙って `2026-03-02` に正規化しない。値オブジェクトは全て `NewXxx(v) (T, error)` なので、Date だけ例外にすると型を見て挙動を推測できなくなる。

正規化を保つほうが実は高い。内部表現が整数なので、正規化には `time.Date` を呼び戻すかうるう年と月末繰り上がりを手書きする必要がある。「不正なら弾く」は比較2本で済む。

**`MustDate` は規約ではなく検査で守る。**`TestDomain_MustDateIsTestOnly` が AST を走査し、`_test.go` 以外での使用を検出する。

**ゼロ値 `Date{}` はどんなコンストラクタ設計でも塞げない。**演算をゼロ値に閉じ（`AddDays` / `WeekStart` はゼロ値、`DaysSince` は0）、`String()` が `"0000-00-00"` というパース不能な文字列を返すようにした。履歴に混入しても正常な日付に見えない。

### D-006 time.Time からの変換はロケーションを引数で強制する

`FromTime(t time.Time, loc *time.Location) (Date, error)`。暗黙に UTC やローカルを選ばせない。

無いと、アプリケーション層が `NewDate(now.Year(), ...)` と手で分解し、**どのタイムゾーンで分解するかの判断が型の外に漏れる**。JST の朝7時（前日22時 UTC）を UTC で分解すると前日になり、週の境界がずれて残差が別の週に計上される。

### D-008 列挙型の Valid は一覧から導出し、値をゴールデンで固定する

`switch` と `AllXxx()` を別々に手書きしない。片方にだけ追加すると素通りし、**Valid が緩くなる方向だけ無防備**という危険な非対称ができる。

**値はリテラルで固定する。**表記規約（大文字・空白なし）しか見ていないと、`CHEST_UPPER` → `CHEST_CLAVICULAR` のような規約を保ったままの改名が通る。API の契約値なので、変えるなら意図的な判断として通す。

**一覧から導出しても特例は足せる。**`return valid[k] || k == "WARMUP"` のような変異を検出するため、`taxonomy.go` の全文字列リテラルを集めて `Valid()` が true を返すものが一覧に載っているかを検査している。

### D-009 quantize は検証の前に適用する

後にすると、コンストラクタが自分で不変条件を破る。

```
NewWeight(1.8e302)  → err=nil, kg=+Inf   （quantize で v*1e6 がオーバーフロー）
NewRatio(1e-7)      → err=nil, v=0       （quantize で0に潰れる）
```

`{"weight_kg": 1e303}` という正当な JSON で到達する。NaN は比較が全て false になるので、以降の検証を素通りして静かに壊れる。強度0 は「0kg のセットを処方する」で、**履歴が無ければ重量を返さない（数字を捏造しない）という設計を 0kg という捏造で貫通する**。

あわせて、全ての数値型に現実的な上限を置いた（重量1000kg、レップ1000、RIR100、セット100、刻み50kg）。定数そのものもゴールデンで固定している。「1.2 は通る／1.21 は落ちる」だけでは 1.205 への改変を検出できない。

### D-010 Epley 式は総レップ20までに限る

限界までの総レップ（レップ + RIR）が 20 を超える記録からは推定しない。

| 記録 | 推定1RM | 0.81倍で処方 | 実績重量比 |
|---|---|---|---|
| 60kg×20 @RIR2 | 104.0 | 85.0kg | 142% |
| 20kg×100 @RIR0 | 86.7 | 70.0kg | 350% |

カール・リアレイズ・入力ミスが1本混ざるだけで実際に扱った重量の1.4〜3.5倍が処方される。**中央値では守れない**——高レップ種目は全セットが高レップなので、外れ値ではなく全体がずれる。

通常のトレーニング（12レップ + RIR2）は通る境界にしてある。

### D-012 SetLog は値等価を持つ

`SameIdentity`（IDのみ）では「同じIDだが内容が違う」＝クライアントの採番ミスを検出できない。リポジトリが ID をキーに上書きすると**実績が黙って1件消える**。`Equals` があるので保存側がエラーとして弾ける（D-060）。

**HTTP の DTO はポインタにする。**非ポインタだと `weight_kg` の欠落が 0kg（正当な自重セット）に、`rir` の欠落が RIR 0（限界まで追い込んだ）になる。どちらも有意味な値なので「送られなかった」と区別できない。欠落は 400 で弾く。

## 推定1RM

### D-013 最終実施日は索引で引く

`LastPerformed` は1回のセッション生成で数百回呼ばれる。全ログの線形走査だと3年ぶん12000件で `Plan` 1回の 5.5ms を占めていた。生成時に `map[ExerciseID]Date` を1度だけ構築する。絞り込み（`filter`）も同じコンストラクタを通す。

**`OnOrAfter` は上限を持たないので、必ず `.Before(date)` で閉じる。**閉じないと計画対象日そのもののログが入り、たった今やった種目が自分の候補から消える。

### D-014 42日より古い記録からは推定しない

`Estimate` は `asOf Date` を必須で取る。

EWMA はセッション数だけで畳み込むので、日付を見ないと**2セッションの間隔を3日から11ヶ月に変えても推定値が1ビットも動かない**。週2で8回記録 → 3ヶ月ブランク → 復帰日に離脱前と同じ 100kg が処方される。実際は 70kg しか扱えず、それを記録すると次回は実力の130%が出る。

古ければ「推定できない」を返し、ユーザーが自分で重量を決める。数字を捏造しないという方針と同じ扱い。

**`asOf` より後の記録も落とす。**平滑化に履歴全体を使うと、過去のある時点の推定をやり直したときに未来の記録が混ざる。

**持ち越し課題：閉ループの固定点。**処方どおり完遂すると推定1RMが同じ値に収束する（`WorkWeight → EstimateOneRepMax` の往復が収縮写像）。漸進的過負荷の仕組みが無いので、処方どおりやり続けると重量が停滞する。現状を数値で固定してあるだけで、修正は入っていない（`lane_prescription_internal_test.go`）。

**持ち越し課題：初期値バイアス。**最初のセッションが重み1.0で入る。実力100kgの人が仮に60kgと入れると、処方が正しくなるまで約10セッション。

### D-113 推定1RMは種目ごとに持つ。対メイン係数は使わない

派生種目の重量を `親の1RM × 強度 × 係数` で出すのをやめた。派生は自分の記録から自分の推定1RMを持つ。

**使い方が破綻していた。**ルーマニアンデッドリフトをハムの種目としてやり、床引きデッドリフトはほぼやらない人の場合、RDL の処方は床引きの1RM由来なので、**床引きをやらなければ42日で古くなり RDL の重量が永久に「自分で決める」になる**。しかも床引きは毎回メニューに出続けて、毎回飛ばすことになる。

数えると割に合っていなかった。605行（実装145行 + テスト460行）が対象7種目のためにあり、実測係数が効くのは「同じ日に親と派生の両方をやる」が3セッション揃ってから。**ほとんどの場面で汎用の定数を掛けているだけ**だった。

**失うもの。**一度もやったことがない種目の初回に目安が出せない。初回だけ「自分で決める」になり、以降は自分の記録から出る。初回1回ぶんの手入力と605行を交換した。推測より記録、という筋にも合う。

「バリエーション自身の1RMを使うと履歴の少ない種目で数字が暴れる」は事実だが、**土台の種目をやらない人には土台自体が無い**。暴れるリスクより、永久に重量が出ないほうが重い。

## 今日の計画の導出

### D-116 今日の計画は、その日の始まりに確定する

`Plan` は当日の記録を一切見ない。重量の推定も、残差も、補助の選択も、全て前日までの履歴から決める。

**ここは壊してはいけない。**受け入れ条件は `TestSessionPlanner_PlanIsFixedForTheWholeDay`——同じ日について記録を1セットずつ足しながら `Plan` を呼び直し、種目の並びと数が最後まで一致すること。

当日を見ていたせいで、症状を1つずつ潰す手当てが積み上がっていた。終えた補助が再提示されてセッションが終わらない、1セット記録すると種目がリストから消える、記録のたびに並びが入れ替わる、枠が補充されて60手やっても終わらない。**どれも同じ1点の派生**で、当日を見なくしたら手当てが全部要らなくなった（`session_planner.go` は495行から330行台へ）。

**挙動が1つ変わる。**3セット終えた補助種目がリストに残り続ける。サーバーが「今日は終わり」を宣言しなくなる代わりに、全部のマスが緑かどうかは画面が判断する。**今日のリストはノルマではなく、上から消していって好きなところでやめられるキュー。**やめどきを決めるのは本人であって、サーバーではない。

**表示と計画で基準が違ってよい。**画面の「今週の充足」（`query.Stats.WeeklyVolume`）は当日を含んだまま。表示は「今週どれだけやったか」、計画は「今日やると決めたこと」。意味が違う。

### D-117 軸は枠ではなく「伸ばしたい種目の宣言」

目標は2種類あり、独立に設定する。

- **ボリューム側**：目標の対象は筋区分。種目は手段で、等価なら入れ替えてよい
- **強度側**：目標の対象は種目そのもの。入れ替えられない

軸の正体は後者、「**この種目を伸ばしたい**」という宣言。枠でも優先順位リストでもない。定期的にやらないと推定1RMが古くなるので、**結果として**必ず出る。

**枠にしたのが誤りだった。**胸・背中・前腿・後腿の枠に種目を割り当てる案を実装の手前まで進めて、2つ出た。前腿と後腿が1つの枠か2つかを決める根拠がドメインに無い。`ADDUCTOR` はスクワットで使うのに前腿ではなく、`CALF` は脚なのに脚の枠に入らない。**モデルが答えの無い問いを立てさせるときは、モデルが間違っている。**

宣言にすると、スクワットと RDL の両方を宣言できる（枠だと片方を補助に落とすしかない）。床引きは宣言しなければ出ない。`ADDUCTOR` / `CALF` の帰属という問い自体が消える。

**ヘビー枠は1セッション1つ。定数であって設定ではない。**宣言が集合で順序を持たないので、同じ日に複数浮上したら**最終実施日が古いほう**を取る（本人に並べさせない）。副産物として頻度が創発する——宣言3つで週3回なら各種目は週1回。

**「N日より古くなったら出す」は書かない。**閾値を置いた瞬間、却下した「種目ごとの週N回」というノブに戻る。比較（どちらが古いか）だけを使い、判定（何日で古いか）は置かない。

**ヘビーのセット数を区分の投与量から借りない。**「支配区分の今日の投与量を使う」案は、胸の週目標を上げるとベンチのヘビーセット数が増える。「ボリュームを増やしたい」が「強度セッションを重くする」に化けるので、2つの目標を独立に保つ骨格に反する。

**割れうる点。**「今日は2種目ともヘビーでやりたい」と言い出したときに壊れる。そのときノブが戻る。**壊れる場所が1箇所に特定できている**ことを利点として採った。

### D-125 メニューは3つのレーンから組み立てる

| レーン | 何を出すか | 何が決めるか |
|---|---|---|
| 軸 | 宣言から1つ | 最終実施日が最も古いもの |
| バリエーション | 重点種目の派生から1つ | 前回から中1日以上空いているか |
| 補助 | 宣言を除いた全種目 | 区分の残差 |

**なぜ足したか。**本人の実際の週では**ベンチだけが週3回**で、他の宣言は週1回。軸は各種目が週1回ずつなので、ベンチの残り2回は補助として出ていた。だが補助レーンは「残差を埋める」ためのもので、**「この種目を重点的に伸ばす」という意図を表していない**。たまたま胸の週目標が大きいから出ているだけで、週目標を変えると消える。

**派生の関係だけを戻した。**`Exercise.derivedFrom` は**種目どうしの関係**であって分類ではない。親が BIG3 である必要も、列挙で数え上げる必要もない。旧実装（`MainLift` という列挙型）は真似しない——列挙なので BIG3 に固定され、種目マスタが「どれがメインか」を知ってしまう（D-117 で否定した構造）。**対メイン係数は戻さない**（D-113）。

**軸との重複の門は「軸が系統に含まれるか」。**「軸 ≠ 重点種目」では塞げない。RDL は宣言にも入りうるうえデッドリフトの派生でもあるので、重点種目がデッドリフトで軸が RDL の日にすり抜け、RDL が軸とバリエーションの両方に出る。

**系統は親から見た向きで、根まで辿らない。**辿ると、重点種目に RDL を指定したとき「RDL の系統」に床引きデッドリフトが入る。床引きは宣言しなければ出ない（D-117）に反する。

**宣言した種目がバリエーションとしても回るのを許容する。**候補から宣言を除くと分岐が増えるうえ、中1日の門が暴走を止めている。破綻したときに除けばよく、戻す手順が想像できる。

**`variationRecoveryDays` を `AccessorySelector.recoveryDays` と共有しない。**値は同じ2だが、あちらは筋区分の回復でコンストラクタの引数、こちらは系統の間隔で設定にしない。共有すると片方を動かしたときにもう片方が黙って動く。

**ノブは1つだけ増えた**——重点種目の指定。「何を最も伸ばしたいか」は本人にしか決められず、アプリが答えるべき問い（何kgでやるか・補助を何にするか）ではないので許容した。**間隔は設定させない。**中1日は定数。

### D-126 3レーンとも強度・セット・RIR は定数

| レーン | 強度 | セット | RIR |
|---|---|---|---|
| 軸 | 0.88 | 3 | 1 |
| バリエーション | 0.80 | 3 | 2 |
| 補助 | 0.71 | 3 | 2 |

`Prescription`（頻度 × 週の何本目 → 強度・セット数・RIR の表）と `Intent`（STANDARD / HEAVY / LIGHT）を消した。

表の前提は「同じ種目を週に何度もやるなら、毎回同じ強度では潰れる。だから週の何本目かで散らす」。正しいが、**散らす相手がいなくなった**。D-117 で軸が「宣言のうち最後にやったのが最も古いもの」で回るようになり、宣言が3つあれば各種目は週1回しか軸に来ない。表の1行目しか引かれていなかった。派生を重ねたい欲求はバリエーションレーンが受け持つ——別種目・別の推定1RMなので、強度を散らさなくても重量は自然に違う。

**軸を 0.88 にしたのは挙動の変更。**実質 HEAVY の行は誰も引いていなかったので、「軸とは何か」を決め直したもの。バリエーションが 0.80 なのは、表から来た 0.81 が 0.88 や 0.76 と並んで初めて意味を持つ刻みで単独では半端だから。

**セット数は3で揃えた。**バリエーションを表の4のままにすると、軸と合わせて胸の実測が週目標の134%まで出ていた。

**補助の処方だけ `prescribe` に合流していない**（`SetsPerAccessory()` をコンストラクタから受け取るため）。3レーンで唯一、セット数が定数ではない。

### D-128 重点種目の番は一巡する。D-126 を部分的に覆す

軸が重点種目の番に来た日だけ、**3レップ相当（0.88）→ 6レップ相当（0.81）→ 派生**の3つを順に回す。それ以外の軸は 0.88 のまま。

**D-126 が表を消した前提が、分割で戻った。**あのとき「散らす相手がいない」と書けたのは、軸が宣言のうち最も古いもので回り、宣言が3つなら各種目が週1回しか軸に来なかったから。分割が入ると変わる。上下2分割で宣言がBIG3なら、**上半身の日に主働を持つ宣言はベンチだけ**で、同じ種目を同じ強度で週2回やることになる。

**測ったら、バリエーションが一度も出ない構成があった。**上下2分割・宣言BIG3・重点ベンチを実シードで8週回して0回。PPLと5分割も0回（いずれもバリエーションを分割で止めたあとの挙動で測った。止める前は脚の日にベンチの派生が出るので0にはならないが、それは別の壊れ方）。バリエーションは「軸が系統に含まれる日は出さない」（D-125）ので、上半身の日が毎回ベンチだと永久に塞がる。**宣言に懸垂を足すと出る**（軸が懸垂に移る日ができる）ので、本人からは理由の見えない挙動になっていた。

**一巡は、番が来たときの中身を変えるだけ。**番が来る頻度は変えない。5分割なら胸の日は5回に1回のままで、そこは周期の組み方（胸の日を2つ置く）の話であって一巡の話ではない。

**同じ日に重ねる形は採らない。**軸ベンチ＋軽いベンチ派生を同日に出す（トップセット＋バックオフ）案を実装して測り、週2.0回まで回復することは確かめたが、**軸とは別の日に出すというレーンの意味を捨てる**ことになる。日ごとに軸そのものが入れ替わるほうが、本人の週（月ベンチ／木ラーセン）に近い。

**強度は Epley の逆算に合わせる。**`1 / (1 + (レップ + RIR) / 30)` で、0.88 は3レップ RIR1、0.81 は6レップ RIR1。D-126 は 0.81 を「表の中でしか意味を持たない半端な刻み」として捨てたが、出どころを外部の表から自前の推定式に変えると値が確定する。**推定（Epley）と処方が同じ式で閉じる**ので、対メイン係数を消したとき（D-113）と同じ形になる。

**一巡の位置は系統のセッション数から導く。**状態を持たない（分割の周期と同じ）。**本体の実施回数で数えてはいけない**——派生をやった日に位置が進まず、同じ派生が出続ける。

**どの派生を回すかは設定を足さない。**`使う種目` から外せば軸の候補にも入らない。D-114 で塞いだ「選択されていなくてもバリエーションは回る」抜け道を開け直さないこと。

**受け入れた代償。**派生が初めて軸に立つ日は推定1RMが無く、その日の主役が「自分で決める」になる。派生を3つ選ぶ人ほど初出が遅れる。長い目で見れば数回ぶんの差なので受け入れた。

**バリエーションレーンは残す。**分割を設定していない人はレーンが発火するので、外すと系統の頻度が週1.9回まで落ちる（許容 2.5〜3.5）。分割のある日は軸が系統に入るのでレーンが出ず、一巡がその役を引き取る。

### D-017 残差は週次の台帳で持つ

「週目標 ÷ 頻度」の固定値を毎セッション使うと、過不足が次に繰り越されない。週を通した台帳にして、補助スロット数も残差から導く。

### D-018 補助は「最も長く放置している区分から」埋める

残差の大きい区分から埋めると**小さい区分が飢える**（週3回で僧帽筋上部50%、腹斜筋65%）。放置時間で順位を付けると全区分が回る。

### D-027 週目標は頻度でスケールする

`DefaultWeeklyTarget(f program.Frequency)`。週3回を基準にしたプロファイルを頻度で線形にスケールする。

固定値だと、頻度が正当な入力であるにもかかわらず**頻度1・2のユーザーは全21区分が永久に赤字**になる（実測で平均達成率 週1回 34%、週2回 65%）。1週間に供給できるセット数は頻度に比例するのに、目標だけが固定だったため。選択器をどう賢くしても、週1回で198セット相当は供給できない。

**目標を実測値に収束させない。**スケール後の区分ごとの達成率は ±40% ほど振れる。実測に寄せれば ±12% まで詰められるが、それをやると目標が「アルゴリズムの出力の写し」になり、サイドレイズ週4セットのような**訓練の意図として意味を持たない数字**になる。目標は意図であって実測の記述ではない。テストの許容帯を広く取るほうを選んだ。

### D-029 種目に出番が無い構成があるのは正しい

`leg_curl`（ハム1.0のみ）は、デッドリフトをやる構成では選ばれない。デッドリフトが毎セッションその区分を叩くため。デッドリフトを外した構成では24セッション中11回選ばれる。

**「どの構成でも全種目が出る」を要求しない。**選択規則を「残差の大きい区分から」に変えれば出るようになるが、小さい区分が飢える（D-018）。死んでいるのではなく「その構成では要らない」だけなので、要る構成で確かめる。

### D-019 体重と睡眠の使い道

**体重トレンドはロバスト推定（Theil-Sen）で出す。**最小二乗法だと体重計の1日の外れ値でトレンドが跳ねる。（体重トレンドは消した。使い道はデロードの減量判定だけで、D-124 のあと呼び出し元が無かった。）

**範囲外の値は「無かったこと」にする。**`WithBodyWeight` / `WithSleepHours` は1日ぶんの異常値で取り込み全体を止めない。**ただしこれは集めた記録を扱う場面の規則で、保存要求では採らない**（D-046）。

**部分レコードは合成する。**体重だけ・睡眠だけを別のタイミングで記録するのは日常なので、日付が同じものは項目ごとに上書きする（丸ごと置き換えない）。

いま体重が効いているのは自重種目の実効負荷（`EffectiveLoad` / `AddedWeight`）、睡眠が効いているのは目標RIRの補正（`ConditionAnalyzer`）。

### D-114 軽い日は同じ種目を軽くやる日

種目を差し替えない。`ExerciseKind` の `VARIATION` と、差し替えの対応表だった `MainLift` を消した。

**抜け道を塞いだのが本体。**`usablePool` に「選択されていなくてもバリエーションは使う」という行があり、7種目は種目選択に入っていなくても回っていた。塞いだので、明示的に選ばれていないと出てこない。

## 記録の保存

### D-033 保存の契約はインターフェースに書く

`Writer.Save` に `ErrConflictingSetLog` と「全か無か」を、`Reader.FindAll` に「リポジトリ内部の可変状態をエイリアスしない」と取得順の要求を書く。

冪等性の要求がドキュメント止まりだと3つ残る。**非決定性**——同じIDで内容の違うログが2件あると、リポジトリが返す順序次第で採用値が変わり、同じ日に同じリクエストを2回投げて違う重量が返る。**検出手段が無い**——`Save` にセンチネルが無ければ、プレゼンテーション層が 409 と 500 を区別できない。**原子性が未定義**——1セッション25セットの半分だけ保存された状態が、その週の刺激量を実態とずらしたまま計画に効き続ける。

**インメモリ実装は失敗しないので、契約の破れは Postgres で初めて露呈する。**だから契約テストは両方に同じコードを流す（D-057）。

### D-060 冪等性は「並行しても成り立つ」まで含む

`INSERT ... ON CONFLICT DO NOTHING` の後に読み直して内容を比べる。保存対象は ID 昇順に固定する。デッドロック（`40P01`）とシリアライズ失敗（`40001`）は再試行する。

`SELECT ... FOR UPDATE` してから `INSERT` する形は3つ壊れていた。**`FOR UPDATE` は存在しない行を締められない**（READ COMMITTED に述語ロックが無い）ので後発が主キー違反を踏み、内容を見ずに衝突と決めつけていた——実測で同一内容の並行再送2,400回のうち**2,093回が 409**。クライアントが「タイムアウトしたから再送」した瞬間に元のリクエストが生きていれば起きる。**保存順が呼び出しごとに変わっていた**（map の反復順）ので、二重送信どうしが互いの行を待ち、50回中14回がデッドロックで 500。**一時的失敗が 500 に落ちていた**——500 は「送り直しても無駄」という意味になる。

読み直して比べる形にすると、同一内容の並行再送は全員が成功する。誰が入れたかを問わず、入っている内容が同じなら目的は達成されている。

### D-064 取得順は `ORDER BY id COLLATE "C"`

照合順序を DB の既定に委ねると、ICU 照合の環境（Neon の既定）でインメモリ実装と Postgres 実装の返す順序が食い違う。ULID は大文字英数のみなので今すぐは壊れないが、「順序が揺れると同じ入力から違う計画が出る」と言っている以上、環境依存に委ねるのは筋が通らない。

### D-059 桁数はドメインの量子化に合わせる

`weight_kg` は `numeric(10,6)`。`quantum = 1e6` は**小数6桁を保持する**という意味で、`numeric(6,2)` では足りない。

```
POST 87.125kg → 204、DB には 87.13 が入る
まったく同じ内容を再送 → 409（内容が違うと判定される）
```

**保存に成功したセットが二度と再送できなくなる。**オフライン記録とタイムアウト後の再送を前提にした設計なのに、その経路が恒久的に 409 を返す。テストが通っていたのは往復テストの値が全部2桁以内で、3桁目を持つ値が1つも無かったから。

**マイグレーションは書き換えず新しいファイルを足す。**0001 を直すと、既に適用した DB との差異が検出できない。この規律を守らせるため、適用済みのチェックサムを記録して照合している（バージョンだけだと内容を変えても永久にスキップされる）。

### D-081 実績は削除できる

`Writer.Delete(ctx, id)` と `DELETE /api/set-logs/{id}`。

`SetLog` は「確定した実績1セット」で生成後は変更しないが、削除は値の書き換えではなく「**これは起きなかった**」と言っている。訂正の手段が無いほうが害が大きい——同じIDで直そうとすると衝突で弾かれ（D-060）、別IDで正しい値を入れても間違った記録が推定1RMを汚し続ける。

**存在しないIDの削除は成功として扱う。**再送で二度目が来たときにエラーにすると「消えているのに消せない」になる。

### D-039 空の保存は成功、nil 要素はエラー

クライアントは同期のたびに送ってくるので、送るものが無い回に I/O を起こす理由がない。「空を送ってきた」をエラーにすると正常な同期がエラーログを埋める。一方 `nil` 要素は、実装側で panic するか黙って飛ばされるかが実装依存になるので境界で弾く。

### D-046 保存要求では「捨てる」判断を採らない

範囲外の体重・睡眠時間は 400。両方欠けている記録も 400。

| 当日の入力 | 応答 | 目標RIR |
|---|---|---|
| `sleep_hours: 3` | 204 | 3（補正が効く） |
| `sleep_hours: -3`（符号の打ち間違い） | 204 | 2（黙って捨てられた） |

睡眠3時間の日に、システム自身のルールでは軽くすべきところを通常強度で処方する。取得のエンドポイントが無いのでクライアントは損失を検知できない。**集めた記録から不正なものを除くこと**（D-019）と**保存要求を捨てること**は意味が違う。

### D-032 / D-047 種目マスタとの突合はアプリケーション層で行う

`Program` も `SetLog` も種目マスタを知らないので、種目IDの実在を自分で検証できない。突合をドメインに置かないのは、種目マスタの取得が I/O だから。ユースケースは「データを集めてドメインに渡すだけ」だが、**渡す前の入力検証はユースケースの仕事**で、判断ではない。

無いと、シードから種目を1つ削除・リネームした瞬間に既存ユーザーのメニューからその種目が理由の説明なく消える。実績ログ側は、実在しない種目のログがどの筋区分にも計上されないまま履歴に残り続ける。

### D-036 入力の不正と I/O 障害を分類する

`apperror` で入力起因の失敗を包む。I/O 起因はそのまま通す。あわせて、I/O を必要としない検証を `FindAll` より前に置く。

裸の `fmt.Errorf` だと、「頻度が範囲外」と「データベースが落ちている」が同じ形になり、ハンドラは 400 と 500 を原理的に区別できない。入力ミスが全部 500 になるか、障害が全部 400 になるかの二択。

**センチネルをドメインに足さないのは**、エラーの語彙がドメインの関心事でないもの（HTTP ステータス）に引きずられて増えるから。分類はプレゼンテーションに近い側の関心。

### D-037 リポジトリの契約違反はユースケースで受け止める

`Reader` は「`(nil, nil)` を返してはならない」と書いてあるが、守らせる手段がない。ユースケースが `program == nil` をセンチネルに読み替える。実装がセンチネルを返すことに依存すると、差し替えたときに 500 に落ちる。

### D-038 キャンセルされた context で全件読み込みを走らせない

`GetSession` は4本のリポジトリを直列に叩き、履歴は全件を読む（10年分で 17ms / 26.6MB）。クライアントが切断済みでも最後まで走らせると、その全部を無駄に払う。

## 層とパッケージ

### D-122 ドメイン層は集約でディレクトリを割る

```
training/           日付・単位・筋区分・推定1RM（どの集約にも属さない値）
training/exercise/  種目マスタ
training/setlog/    実績ログと History
training/condition/ 日次コンディション
training/program/   ユーザー設定
training/planning/  ドメインサービス
training/seed/      初期データ
```

集約の境界は既にソース上にあった（`//ddd:aggregate` が付いていた4つ）。リポジトリのインターフェースが4つあったことと一致する。

**`planning` の中はディレクトリで割らない。**割ると `PlannedSet` のような非公開フィールドしか持たない型が公開コンストラクタを要求される。「提示セットは計画器から出たものだけ」という言語レベルの保証が消える。同じことが `PlannedSession`・`StimulusCoverage`・`SlotTemplate` にも起きる。ファイル名で分け、サービスは役割の名詞で終わらせる（`_planner` `_selector` `_policy` `_analyzer` `_estimator` `_catalog`）。

**公開せざるを得なかったもの**は `training.Quantize` / `ValidateRange` / `SmallestPositive` / `Median`、`condition.DefaultBodyWeightKg` / `MaxSleepHours` の6つ。いずれも純粋な計算か定数で、エンティティの内部状態に触れる口は1つも開けていない。

**テストヘルパは複製した。**共有パッケージ（`trainingtest` のような）を立てると、**テストのためだけに存在する本番パッケージ**が層の中に増え、`architecture_test.go` の走査対象にもなる。数行の重複より高くつく。

**リポジトリのインターフェースは読みと書きに分ける。**集約のパッケージに `Reader` / `Writer` を置き、使う側は要る半分だけを受け取る。

### D-118 ドメイン層の標準ライブラリ許可制はやめた

`architecture_test.go` が見るのは**依存の向き**だけ——外側のパッケージ（`application` / `infrastructure` / `presentation`）を import しない、外部モジュールを import しない。

許可リストが実際に弾いていたのは `slices` のような無害な追加で、そのたびに手続きが要った。本当に防ぎたかった `os` / `net/http` / `database/sql` は**別の力で既に守られている**——ドメイン層は「DBもHTTPも立てずに全機能をテストできる」ことを前提に組まれていて、外界に触れるコードを書くとテストが立たなくなる。そこで気づく。

**禁止リストへの反転も採らなかった。**`io/ioutil`、`os/user`、`syscall` と数え上げ続けることになり、許可制と同じ手続きが裏返しで残る。**網羅できない。**

**割れうる点。**これは制約を弱める判断で、`os.ReadFile` を呼ぶドメインコードが書けるようになる。破れたらこの判断ごと revert すればよい。

### D-051 依存方向の検査は許可リスト方式にする

**すべてのパッケージに層の宣言を要求する。**層に属さないパッケージを「分類対象外」として無視すると、**中継パッケージを1枚挟むだけで検査が完全に無力化する**。

```
internal/glue が infrastructure を import し、
internal/presentation/httpapi が internal/glue を import する
→ go build / go vet / go test すべて緑
```

`layerOf` がマッチしないパスを落とすと、そのファイルは import 元としても先としても存在しないことになる。`internal/adapter`、`internal/config`、`pkg/` ——今後足すディレクトリの大半がこの穴に落ちる。

**パスの照合は `strings.Contains` ではなくディレクトリ境界の一致。**`internal/infracmd` が `Contains(path, "cmd/")` に一致して **cmd の特権（最外層）を得る**。

**陽性コントロールを置く。**違反が無ければ、検査は静かに検出力を失ったまま緑でいる。走査件数の下限だけでは「走査が壊れた」形しか捕まえられない。

### D-050 兄弟層どうしの依存も禁じる

`infrastructure` と `presentation` は同じ深さなので、「外側を import しない」だけでは**HTTP のハンドラがインメモリ実装を直接 import しても検出されない**。具象のリポジトリ実装を知ってよいのは `cmd` だけ。

**テストファイルは兄弟の検査の対象外。**テストが具象実装を組み立てるのは正当で、むしろインメモリ実装で HTTP 層を検証できること自体が Onion の狙いそのもの。内向きの検査からは除外していない。

### D-066 層はディレクトリに現れる

`internal/application/usecase` をフラットな `internal/usecase` にせず、4層すべてを `internal/<層>/<パッケージ>` で揃える。

```go
import "github.com/dyoshyy/liftplan/internal/presentation/httpapi"
import "github.com/dyoshyy/liftplan/internal/infrastructure/postgres"
```

この2行が同じファイルに並んでいれば、依存方向の違反だと読んだ瞬間に分かる。フラットだと `internal/httpapi` が `internal/postgres` を import しているだけに見える。`architecture_test.go` は落としてくれるが、レビューで気づけることはそれとは別の価値がある。

`domain/training` の1段は意味が違い、こちらは**境界づけられたコンテキスト**の名前。

**来るか分からないものの枠は作らない。**空のディレクトリは、そこに何かがあるという誤った期待を生む。

### D-080 読み取り専用の経路は query パッケージに置く

履歴・推移・週目標の充足は `internal/application/query`。ユースケースはデータを集めてドメインに渡し状態を進めるが、読み取りは状態を変えず `SessionPlanner` を通らない。

整形をプレゼンテーション層に置くと画面ごとに同じ集計を書き直す。ドメインに置くと表示の都合がドメインに漏れる。

**数え方はエンジンと共有する。**週目標の充足は `planning.CoverageBetween` を使い、`SessionPlanner` も同じ関数を通す。別々に実装すると、画面に出る数字とエンジンが使う数字がずれる。ずれた瞬間、どちらが正しいのか誰にも分からなくなる。

### D-123 モジュールパスはリポジトリ名に合わせる

`github.com/dyoshyy/liftplan`。GitHub のリダイレクトが効いているうちは壊れないので、いつまでも先送りできてしまうが、**import 文は毎日読む場所**で、そこに存在しない名前が86ファイル分残る。

**単独の PR にした。**置換自体は機械的だが86ファイルに散る。他の変更と混ぜると「機械的な置換以外が紛れていないか」を確かめられなくなる。

Cloud Run のサービス名は `liftplan-server` のまま（変更できず作り直しになり、URL が変わると `API_BASE` とヘルスチェックが全部つられる）。

## HTTP 境界

### D-042 ステータスの分類を1箇所に集める

`respondError(w, err)` を1つ置き、センチネルからステータスへの翻訳をそこだけで行う。

| 条件 | ステータス |
|---|---|
| `context.Canceled` | 499（クライアント切断） |
| `context.DeadlineExceeded` | 504 |
| 入力の不正 | 400 |
| プログラム未設定 | 409（セッション導出）／404（`GET /api/program`） |
| 実績ログの衝突 | 409 |
| 保存先に到達できない | 503 |
| それ以外 | 500 |

ハンドラごとに `errors.Is` を並べると、新しいセンチネルを足したときに拾い漏らすハンドラが出る。

**499 を使う理由。**クライアント切断はサーバーの障害ではない。500 と混ぜると、ログと警報がクライアントの都合で汚れる。

**未設定が文脈で変わる理由。**`GET /api/program` では「まだ存在しない」で 404。セッション導出では「前提が満たされていない」という状態の衝突で 409。

### D-043 / D-049 500 では内部のエラー文を返さない。ただし記録する

ドメインとインフラのエラーには種目ID・閾値・テーブル名・接続文字列が載っている。500 のときだけ固定文言を返し、`slog.Error` でサーバー側に記録する。**隠すことと捨てることは別。**

400 で隠さないのは、ユーザーが直せる情報だから。「頻度は1〜7回である必要がある」を隠すと、クライアントは何を直せばいいか分からない。

### D-045 HTTP 境界で入力を閉じる

ボディに 1MB の上限、`Content-Type: application/json` の要求、末尾トークンの検査、種目IDに 64 文字の上限。

- **上限が無い**: 20MB の `exercise_id` を10回投げると GC 後のヒープが 1MB → 201MB。**保存に成功する（204）ので解放されない**。その後の `GET /api/sessions` は毎回そのゴミを全件読む
- **エラー応答が入力を反射する**: 20MB の不正な ID に対し 20MB の 400 応答。確保・保持・送出の三重取り。長さの検査を他の検証より前に置いて塞いだ
- **末尾のドキュメントを黙って捨てる**: `{"logs":[...]} {"logs":[...]}` が 204 を返し、2つ目は保存されていなかった
- **`Content-Type` を検証していない**: `form-urlencoded` はブラウザがプリフライト無しで送れるので、CSRF がそのまま通る

### D-061 保存先に到達できないことを 503 で表す

DB が落ちている間、全リクエストが 500 を返し、**`/healthz` だけが 200 を返していた**。何も処理できないインスタンスがヘルスチェックに合格し続け、ロードバランサはトラフィックを流し込む。

500 は「送り直しても無駄」という意味を持つ。DB 断は後で送り直せば通るので、区別できる形で返す。

**`/health` の差し替えは `cmd` で行う。**プレゼンテーション層は保存先を知らないので、そこに疎通の口を持たせると依存の向きが崩れる。ルータの前に被せれば `cmd` に閉じる。**持ち主は1つ。**両方に置くと、被せを外してもルータ側の素朴な応答が返り、テストが緑のまま「DB が落ちていても 200」に戻る。

### D-073 ヘルスチェックの経路は /health

**Google のフロントエンドが `/healthz` を完全一致で横取りする。**アプリまで届かず、Google の HTML の 404 が返る。

| 経路 | 応答 | Content-Type |
|---|---|---|
| `/healthz` | 404 | `text/html`（Google のエラーページ） |
| `/health` | 401 | `application/json` |

ローカルの Docker では同じイメージが 200 を返すので、**デプロイするまで気づけない**。放置すると D-061 が本番で機能しない。経路の定数を `httpapi.HealthPath` として1箇所に置き、認証の除外リストと `cmd` の被せの両方がそれを参照する。

### D-068 / D-069 認証は Bearer トークン1つ。未設定なら起動しない（D-136 で差し替え済み）

単一ユーザーの個人アプリなら十分で、OAuth へはミドルウェアの差し替えで移れる。
**実際にそうなった。**差し替えたのはミドルウェア1枚で、内側の形は変わっていない（D-136）。
「未設定なら起動しない」はそのまま生きている。

**ユーザーという概念を内側へ持ち込まない。**ドメインもユースケースも「誰が」を知らないままにする。マルチユーザーに開くときは、スキーマに `user_id` を足す作業とセットになる。

- **定数時間で比較する**（`crypto/subtle`）。素朴な `==` は一致する接頭辞が長いほど応答が遅くなる
- **方式名は大文字小文字を無視する**（RFC 7235）。`bearer` を弾くと原因の分からない 401 になる
- **401 に `WWW-Authenticate: Bearer`** を付ける。「認証が要る」と「壊れている」を区別できる
- **送られたトークンをエラーに載せない**

`AUTH_TOKEN` が空か32文字未満なら `buildHandler` が失敗する。「未設定なら認証しない」にすると、環境変数の設定漏れがそのまま全公開になる。**気づかないまま公開されるより、起動しないほうがよい。**

### D-119 CORS は認証の外側。ワイルドカードは受け付けない

画面は別オリジン（Cloudflare Workers）から配られる。

**ワイルドカードを返さない。**Bearer トークンで守っている API なので、`*` を返すと任意のサイトが利用者のトークン付き要求の結果を読める。許可オリジンは `ALLOWED_ORIGINS` で明示し、**未設定なら起動しない**（`AUTH_TOKEN` と同じ理由）。

**CORS は認証の外側に置く。**preflight の `OPTIONS` にブラウザは `Authorization` を付けないので、内側だと必ず 401 になる。加えてルータはメソッド付きパターンなので、`OPTIONS` が届くと 405 になる。重ね順を逆にすると壊れることは `TestBuildHandler_AnswersPreflightWithoutCredentials` が押さえている。

**契約のずれは記録を消す。**`DisallowUnknownFields` があるので、新しいクライアントがフィールドを足して古いサーバーに送ると 400 が返り、待ち行列はそれを再送不能とみなして `rejected` に落とす。手当ては2つ——クライアントを**同じリポジトリの `web/`** に置いて契約のずれが PR で見えるようにすること、`deploy.yml` の `web` ジョブを `needs: deploy` にして**必ずサーバーを先に出すこと**。

### D-083 期間の指定に上限と既定を置く

`from` / `to` を省略したら直近56日、上限は400日。既定があれば画面が毎回日付を組み立てなくて済み、端末とサーバーの日付がずれる余地も減る。上限が無いと、3年ぶんを1回で要求されたときに応答が数MBになる。

### D-052 起動と停止をテストできる形に分ける

`run()` を `newServer` / `serve` / `serveListener` に分け、listener を受け取れるようにした。分ける前は `run()` が1行もテストされておらず、スローロリス対策のタイムアウトを全部消してもグレースフル停止を丸ごと消しても緑だった。

- **シグナルの購読解除は停止前に行う。**`defer stop()` だと2回目の SIGTERM も SIGINT も握り潰され、Ctrl-C を連打しても止まらず `kill -9` が要る
- **停止の猶予は最長のリクエスト予算より長く取る。**短いと、サーバー自身が許可した長さのリクエストを必ず切ることになる
- **リクエストの context に期限を付ける。**配線が無いと `DeadlineExceeded` → 504 がテストの中でしか起きない。`http.TimeoutHandler` を使わないのは、あちらが独自の 503 を書いて D-042 の分類を迂回するため

## インフラとデプロイ

### D-067 Cloud Run + Neon。Cloudflare Workers ではない

Workers は V8 isolate なので Go を載せるなら WASM にする必要があるが、Go の WASM ターゲット（`GOOS=js` / `wasip1`）では **`net` パッケージが使えない**。pgx は `net.Conn` の上に立っているので、Postgres へ繋ぐ手段がそもそも無い。載せるにはサーバーを TypeScript か Rust で書き直すことになり、ドメイン層と判断記録を捨てる価値は無い。

Cloudflare Containers なら Dockerfile を載せられるが beta で、前段に TypeScript の Worker と Durable Object のバインディングが要る。Cloud Run なら同じことが TS の層なしでできる。

### D-071 Neon は直接接続、Cloud Run はシンガポール

**`-pooler` の付かない直接接続を使う。**マイグレーションがセッションレベルのアドバイザリロック（`pg_advisory_lock`）を使っており、トランザクションプーリングはトランザクションの外でバックエンドの固定を保証しない。ロックを取ったバックエンドがプールに戻り、解放が別のバックエンドに当たりうる。実測では負荷の無い状態だと固定されて成功したが、**固定されることもある、は保証ではない。**

もう1つ、テストは `search_path` でスキーマを分離しており、pooler はこれを明示的に拒否する。本番とテストで違う経路を通すのは何度も潰してきた失敗の形。

**リージョンはシンガポール。**Neon に東京リージョンが無い（AWS の最寄りは ap-southeast-1）。DB がそこに固定される以上、往復の回数で決まる。

| 構成 | 内訳 | 概算 |
|---|---|---|
| Cloud Run 東京 + DB シンガポール | 10ms + 70ms×4 | 約290ms |
| Cloud Run シンガポール + DB シンガポール | 70ms + 1ms×4 | 約74ms |

**ユーザーに近づけるより DB に近づけるほうが速い。**

### D-054 / D-055 / D-056 ドライバとスキーマ

**`database/sql` を挟まず `pgx/v5` を直接使う。**`database/sql` の抽象が守るのは「SQL ドライバの差し替え」だが、このアプリの差し替え点はリポジトリインターフェースであって SQL ドライバではない。挟むと prepared statement のキャッシュと型の扱い（`numeric`、`jsonb`、NULL 可能な数値）を捨てることになる。

**マイグレーションは自前で流す。**「連番の SQL をトランザクションで順に流し、適用済みを記録する」だけで80行。CLI とドライバ登録を持ち込む依存を足す理由がない。アドバイザリロックを取る（複数インスタンスが同時に起動しても二重適用しない）、1ファイル1トランザクション（半分だけ当たったスキーマは次の起動で直しようがない）、起動時に流す（手で流す運用にすると流し忘れたインスタンスが古いスキーマに書き込む）。

**型の選び方。**`weight_kg` は `numeric`（`double precision` だと 87.5kg が往復で揺れうる）。週目標と選択種目は `jsonb`（列に開くと筋区分を1つ足すたびにマイグレーションが要る。読み出しは必ずコンストラクタを通すので境界で弾かれる）。`program` は `id boolean PRIMARY KEY DEFAULT true CHECK (id)` で1行に固定（単一ユーザー前提を型で表す）。`date` に渡す時刻は UTC 固定で、DB 上の値が同じ暦日であることを**ドメインを経由せず生の `::text` で**確かめる（ドメイン経由だと同じずれで戻ってきて気づけない）。

### D-062 使われない索引は落とす

`set_logs` を読む SQL は `FindAll` の1本だけで `WHERE` 句が無い。日付や種目での絞り込みは全て Go 側のメモリ上。実測で両索引とも**走査回数ゼロ**、合計1.9MB（5万件）を占め、`INSERT` ごとに2本ぶんの更新コストを払っていた。範囲クエリへ移るときに、実際に使う形で作り直す。

### D-074 デプロイの鍵を持たない

GitHub Actions から Cloud Run へ、Workload Identity 連携（OIDC）で認証する。サービスアカウントキーの JSON を GitHub Secrets に置く方式は、**漏れたら取り返しがつかない**うえ定期的な入れ替えを人手で回す必要がある。OIDC なら**盗まれて困る長期の秘密がそもそも存在しない**。

**借用できる範囲を絞る。**条件を付けないと **GitHub のどのリポジトリからでもこのサービスアカウントを借りられる**（他人のフォークを含む）。これは Workload Identity 連携で最も多い設定ミス。

**権限は2つだけ**——`run.admin` と `artifactregistry.writer`、加えて実行用サービスアカウントへの `actAs`。

### D-112 本番に出せるのは main だけ

条件は `assertion.repository` だけでなく `assertion.ref=='refs/heads/main'` まで見る。`workflow_dispatch` は ref を選んで実行できるので push の `branches` では止められないし、新しいワークフローを任意のブランチに置けば同じ権限が取れる。

**デプロイの手前で `GITHUB_REF` を確かめる段も置く。**Workload Identity 側の条件はリポジトリの設定から見えないので、ここにも書いておく。

**両方向で確かめる。**「ブランチから認証できないこと」と「main からデプロイできること」。片方だけ見て終わりにすると、次にマージした人が詰まる。

### D-075 デプロイの前にテストを回し、後で疎通を確かめる

- **CI の成功を当てにしない。**`workflow_dispatch` のような CI を経ない経路で無検証のまま出てしまう
- **デプロイの成功は起動の成功ではない。**リビジョンは作れても起動に失敗していれば意味がない。`AUTH_TOKEN` の設定漏れはここで初めて分かる（D-069）
- **認証がかかっていることも確かめる。**ヘルスチェックは認証を通さない経路なので、認証を壊したまま出しても 200 が返る

イメージのタグはコミットの SHA（`latest` だけだとロールバック先が分からない）。`concurrency: deploy` で同時実行を止める。

### D-076 リリース台帳は Cloud Run のリビジョン

リビジョン名に短縮コミットSHAと実行番号を入れ、`commit` と `run-id` をラベルに貼る。**Git のタグは打たない。**リリースの事実は Cloud Run 側に既にある（いつ・何が・今どれが動いているか）。タグを打つと同じ事実が2か所に増え、片方だけ失敗したときに食い違う。

実行番号を足すのは、同じコミットを出し直すと名前が衝突してデプロイが失敗するため。再実行やロールバックのやり直しで普通に起きる。

**ロールバックしてもマイグレーションは戻らない。**いまのものは後方互換だが、列の削除を入れた瞬間に戻せなくなる。

### D-121 Cloudflare の Git 連携（Workers Builds）を使わない

画面のデプロイは GitHub Actions から `wrangler` を叩く形のまま。

**理由は順序。**Workers Builds は Actions と**無関係に**走るので、`deploy.yml` の `web: needs: deploy` が保証している「サーバーが先・画面が後」が消える。画面のビルドは30秒程度、Go 側は数分なので、**ほぼ確実に画面が先に出る**。これは D-119 に書いた一番危ない向きで、記録が消える。

**折衷案（本番の Deploy command を `versions upload` にする）も採らなかった。**同じものを2つの仕組みがビルドする状態になり、片方だけ壊れたときに切り分けが増える。PR ごとのプレビューが要るようになったら、そのときは折衷案から入る。いきなり本番を渡さない。

## クライアント

### D-079 記録は待ち行列に積んでから送る

ジムの電波は途切れる。送信を先にすると、失敗した瞬間に記録が消える。**保存してから送れば、失敗しても次の機会に送れる。**

**IDはクライアントが採番する。**サーバー採番だと、応答が届かなかったときに「保存されたのか分からない」が発生する。クライアント採番なら同じIDで何度でも再送してよい（D-060 で冪等にした経路がここで効く）。

**4xx は捨てる。**409 も 400 も再送しても永久に通らない。残すと後続が全部詰まる。5xx と通信断だけを残す。

**API の応答はキャッシュしない。**Service Worker が持つのは画面の殻だけ。古いメニューを出すくらいなら出ないほうがよい。「昨日の重量が表示されているのに気づかない」は記録そのものを壊す。

### D-107 待ち行列は IndexedDB に置く

localStorage には「読んで、足して、書く」を割り込まれずに行う手段が無い。同じ端末で2つ開いていると、`enqueue` の読み書きがぶつかって**両方の記録が互いを消す**。

| | 記録した重量 | キューに残ったもの |
|---|---|---|
| 修正前 | 100,101,102 / 204,205,206 | 204,101,206（**3件消失**） |
| 修正後 | 同上 | 全6件 |

携帯とPC、あるいはPWAとブラウザタブという、ごく普通の使い方で踏む。IndexedDB の書き込みはトランザクションなので追記どうしがぶつからない。2つのタブが同時に送ると二重送信になるが、同じIDの同じ内容はサーバーが黙って受け入れる契約（D-060）。

### D-090 送信キューは毎回 store から読み直す

`flush` が手元に配列を持ったまま書き戻すと、送信を待っている間に `enqueue` が走ったぶんが**送信されないままキューからも消える**。電波の細いジムで続けて2セット記録すると、2つ目が黙って失われる。画面には「同期済み」と出るので気づく手がかりが無い。

先頭から順に処理し末尾に積まれるという性質があるので、読み直しても処理位置はずれない。

### D-097 捨てた記録を黙って消さない

4xx はキューから捨てる（D-079）が、捨てたあと「同期済み」と表示していた。**記録したはずのセットが無いのに、画面はうまくいったと言う。**

捨てたものを端末に残し、何を失ったかを1行で出す（`2026-08-23 ベンチプレス 100kg × 5（400）`）。リロードしても消えず、本人が「消す」を押すまで残る。

### D-104 トークンが弾かれても記録は残っている

401 を受けると端末のトークンを消して初期設定の画面に戻るが、このとき未送信のキューは残っているのに画面には何も出ない。記録ごと消えたと思う。

トークンが変わったのは送り先の話で、記録の話ではない。初期設定の画面に「未送信の記録が N 件あります」と出す。

### D-084 前回との差分バッジを出さない

`前回 91kg → 今日 102.5kg「+11.5kg」` は**伸びではない**。前回と今日でレーンが違えば重量が違うのは当然。差分を出すと「増えた＝良い」という誤った要約を押し付けることになる。

伸びているかは推定1RMの推移でしか答えられない（レップ数が違う日どうしを比べられるのはそちらだけ）。**要約しすぎない。**判断の材料を出して、判断は人に残す。RIR は止め時の指示でレップは結果、というのと同じ形。

同じ役割の前回と比べる案もあったが、`SetLog` に役割を持たせることになり、実績が「その日の計画」に依存し始める。実績は起きたことだけを持つべきなので採らない。

### D-092 セットごとの重量を畳まない

`sets[0].weight_kg` を代表にすると、途中で重量を変えたときに**もう片方の重量が画面から消える**（105kg と 101kg のセットが「101kg × 5, 5」と表示された）。同じ重量が続くならまとめ、変わったら区切る。`LastPerformance` にはセットごとの `Weights` を持たせ、`WeightKg` は「次に何kgから入るか」の目安なのでその日の最重量にする。

### D-091 訂正しても同じIDを使う

並び順は ID 由来（`performed_on` は日付のみで実施順を記録していない）なので、別IDで入れ直すと**1セット目を直すと3セット目になって出てくる**。先に消してから入れ直すので、同じIDでも衝突にはならない。

### D-102 予定を超えたセットも画面に出す

枠を `planned.sets` ぶんしか描かないと、予定より多く記録したぶんが画面から消え、取り消すこともできない。記録の数が予定を超えたら、その数だけ枠を出す。

### D-103 今日やったものは今日の画面に残す

予定に入っていないが今日の記録があるものを「今日やったもの」として出す。履歴には残っていても、今日の画面から消えれば記録が飛んだように見える。

予定として出すと「これからやる」と読めるので、重量やRIRは出さず「今日やった Nセット」とだけ書く。設定を変えて種目が外れた場合も同じ。

### D-105 記録が1回しか無いときに増減を出さない

比べる相手がまだ無いだけなのに、伸びていないように読める。スパークラインを3点未満で出さないのと同じ理屈。**無い情報があるように見せない。**

### D-093 alert() を使わない

ダイアログを閉じるまでページ全体が止まり、直したい入力欄そのものが隠れる。その場に出す。破壊的操作の確認（トークン削除）だけ `confirm` を残している。

### D-095 圏外で開いたときに画面を出す

読み込みが失敗して例外で飛び越すと、起動直後は全ての画面が hidden なので真っ白になる。圏外でも画面を出し、なぜメニューが出せないかを書く。古いメニューをキャッシュして出さない理由（前回の重量が今日の重量として出ると記録が壊れる）も、その場に書いてある。圏外でも体重は入力できてキューに溜まる。

### D-096 Service Worker は自分のところのファイルだけ扱う

`fetch` ハンドラが全ての GET を通すと、**Google Fonts の woff2 が殻キャッシュに溜まる**。日本語フォントは100以上のサブセットに分かれて配られるので、文字が出るたびに増える。上限は無い。

あわせて、失敗の応答を殻に保存しない。500 のエラーページを掴むと、次に圏外で開いたときそれが画面として出続ける。

### D-120 体重の入力は最初から要る

**体重は自重種目の処方と推定に使われる**（`EffectiveLoad` / `AddedWeight`）。しかも落とし穴がある——体重が一件も無い間は既定値で動くが、**数週間ぶん記録したあとに体重を入れ始めると**、それ以前の自重種目が推定から除外される。SetLog は残るので記録は消えないが、**その種目の推移は事実上失われる**。

**Service Worker の登録は `main.tsx` で行う。**画面の中の部品から登録すると、その部品が描かれるまで登録されない（実機で数えて、初回訪問の登録が0だったことがある）。

**`registerType: 'prompt'` のまま `skipWaiting` を呼ばない。**待機中の新版は全てのクライアントが閉じたときに有効になる。記録の途中で画面が差し替わらないほうを取る。

### D-127 設定は1フィールドずつの口を叩く

`PUT /api/program/{frequency,declared,focus,selected,target,split}`。**全置換の `PUT /api/program` はクライアントから呼ばない。**

全置換に戻そうとして、まさにその事故が起きた。旧実装は `per_week` / `weekly_target` / `selected_exercises` の3つしか送っておらず、あとから足された `declared_exercises` と `focus_exercise` を落とす。**`DisallowUnknownFields` が弾くのは余分なフィールドだけで、欠落は素通りする**——返るのは 400 ではなく 204 で、足されたばかりの設定だけが黙って初期値に戻る。

**読む画面は経路を増やさない。**履歴は `GET /api/stats` を1本足すだけで、記録が消える経路は1本も増えない（D-119 の懸念は書き込みにしか掛からない）。

**部品は props だけで描けるようにする。**`History` は `stats` と `days` を props で受け取り、自分では取りに行かない。取りに行くのは `useStats`。呼び出し側が「いつ取るか」を決められる。

**`useStats` には `enabled` を持たせた。**トークンが無いまま叩くと 401 が返り、`api/client` はそれを「トークンが通らなかった」とみなして端末から消す。まだ入れていないだけなのに、入れた直後の再読み込みまで巻き込む。

**色を直書きしない。**Sparkline の `#e0a82e` は `currentColor` に変えた。`@theme` のトークンを変えたときにここだけ取り残される。

## 検証のやり方

### D-007 テストは変異で検出力を確かめる

`d.AddDays(i).DaysSince(d)` のような自己整合的な式は、両辺が同じ壊れた算術を使うため常に通る。**通るテストを書くことと、壊れたら落ちるテストを書くことは別物。**

**変異は「守ったつもりの性質」ではなく「壊れたら困る性質」から選ぶ。**表記規約を壊す変異を検出できても、値の改名を検出できなければ列挙型のテストとしては無内容（D-008）。検出しやすい変異（bool・剰余・防御的コピー・ゴールデン値）に偏りやすい。

**粒度は「条件の各項を1つずつ」。**「条件を1つ落とす」では、両側同時に潰したときだけ検出できる状態を見逃す。

**ベースラインが緑であることを先に確かめる。**終了コードだけで判定すると、もともと失敗しているテストのせいで全変異が「検出」と報告される。**壊れた計測器で測った値を根拠として提示するのは、測らないより悪い。**

### D-100 実際に直したバグを、テストで留める

手で直したバグをあとから戻してみたら、**半分はテストが緑のまま**だった。

| 入れた変異 | 最初 | 対処後 |
|---|---|---|
| メインの推定に当日を混ぜる | 見逃し | 検知 |
| 補助の並びを固定しない | 見逃し | 検知 |

1つ目が見逃されたのは、既存のテストが**同じ重量**で当日のセットを記録していたため。当日を混ぜても推定が動かない。2つ目は、その場の並びがたまたま整っていたため差が出なかった。

**直したときに「テストが緑だから大丈夫」ではなく、壊し直して赤くなるかを見る。**頭の中で「これは守っている」と判断すると外す。

### D-089 見つけ方には段階がある

1. **テスト**（緑でも壊れているものがある）
2. **本物の環境**（D-072 の Neon、D-073 の Cloud Run）
3. **実際に触る**（真っ白な画面、セッション中に動くリスト）

3で見つかった4件は、どれもテストが緑で API も正しい応答を返していた。**セッションを最後まで消化する**という当たり前の使い方を、テストが一度もしていなかったのが共通の原因。以後、通しで消化する検証をテストに置いている。

### D-085 画面を見ないと分からないものがある

テストは全部緑、API も正しい応答を返していたのに、**画面は真っ白だった**。同時に、動かして初めて分かったものが他に4つあった（差分バッジが誤解を生む、筋区分が英語のまま、週目標が21区分すべて並んで長すぎる、点が2つしかないのに面グラフが描かれる）。

いずれも構文検査でも API のテストでも出てこない。**出力を見るまで存在しない情報**がある。いまは `web/scripts/*-check.mjs` がヘッドレスブラウザで実際の画面を操作する。

**単体テストは配線を見ていない。**判断が正しいかしか見ておらず、依存配列の漏れや props の付け替えミスは緑のまま通る。画面を触ったら回す。

### D-057 契約テストは実装間で共有する

保存の契約を `repositorytest` に切り出し、インメモリ実装と Postgres 実装の両方に同じコードを流す。実装ごとに書き直すと、片方だけが契約を満たす状態に気づけない。

実際、Postgres 側から**契約の穴が6つ**見つかった。取得順は「毎回同じ」では足りない（`ORDER BY` を外しても小さなテーブルなら挿入順で返る。挿入順と辞書順をずらしたうえで昇順を要求する）、並行時の衝突も同じセンチネルで返ること、同一呼び出し内の合成は「後勝ち」まで見る、小数がそのまま往復すること（D-059）、同じ内容の並行再送は全部成功すること（D-060）、同じバッチの二重送信が詰まらないこと。

### D-063 CI で Postgres のテストを必ず走らせる

`TEST_DATABASE_URL` が無いとテストは `t.Skip` し、パッケージは `ok` と表示される。検証で、`Save` の本体を丸ごと no-op に潰しても **CI は緑のまま**だった。D-057 が言う「露呈の場」が存在しなかった。設定を消してもテストは緑になるので、**走ったこと自体を検査する。**

### D-072 本物のマネージド Postgres でしか出ないものがある

実際の Neon に契約テストを流したら、**全テストが同じスキーマを共有していた**。原因は `?search_path=` が **libpq のパラメータではない**こと。pgx は独自に起動パラメータとして送るのでローカルの Postgres には素通しで届き、**ローカルでは緑のまま**だった。Neon のプロキシは通さないので全部が `public` に落ちていた。標準の `options=-c search_path=...` なら両方で効く。

**これはローカルの Docker では絶対に見つからなかった。**

### D-110 実環境の検証は、本番に触らずに使い捨てで行う

Cloud Run 上でしか出ないバグは、マージを待たないと確かめられない——と考えていたが、そうではない。Neon に期限つきの検証用ブランチを切り、別サービス名でデプロイし、確かめたら消す。**本番サービスに対しては読み取りだけ。**

同じことが CI の認証経路にも言える。読み取りしかしない一時ワークフローをブランチに置けば、マージせずに Workload Identity の経路を確かめられる。**そのとき「成功したこと自体が問題」と気づいた**——main 以外のブランチから本番デプロイ用のサービスアカウントが取れていた（D-112）。

デプロイに関わる変更は、このやり方で確かめてからマージする。

### D-108 長期運用を通しで回す

「数週間使うと壊れるのではないか」は、実際に回して確かめる。クライアントと同じ順序（計画を取る → 提示どおり記録する）で実サーバーに流す。12週・36回で、1回あたりのセット数が0になる回が無いこと、メインの重量が単調に増加すること。

### D-028 シードと週目標は通し検証で担保する

シードは「値が入っていること」を確かめても意味がない。週目標と刺激係数はセッション生成器を通してはじめて挙動になる。当初のテストは変異15種のうち**3種しか検出できなかった**——**全種目の主働筋寄与を 1.0 → 0.3 に潰す**変異すら緑で、これは刺激係数という中核データを丸ごと無意味にする。

`seed/simulation_test.go` を常設のテストとして置いてある。シードや週目標を触ったら回し、数字が動いたら理由を確かめる。**動かないはずのものが動いたら、想定外の依存が残っている。**

**実シードで回すのは、テストが自前のデータだけで完結している罠を避けるため。**派生だけ付けてシードに入れ忘れると、単体テストは緑のまま本番で機能が丸ごと無効になる。

**`TestSimulation_Report` は重点種目を指定していないので、バリエーションレーンが一度も発火しない。**あのレポートでバリエーションの変更を検証してはいけない。都度プローブを書いて測る。

### D-124 デロード（停滞判定と重量の自動引き下げ）

`DeloadPolicy` / `DeloadProposal` とテスト592行、`PlanRequest.DeloadAccepted`、API の `deload_proposal` と `?deload_accepted=`、PWA の型をまとめて削除した。

**いま要らない。**「それが無いといま壊れるか」に対して、壊れない。停滞したときに重量を落とすのは本人ができる。アプリが答えるべき問いに「進めるか落とすか」を挙げていたが、**提案が出ても承認の操作が要る**ので、結局そこで本人が判断していた。**判断を取り上げきれていない機能だった。**

**`ConditionAnalyzer` は残した。**睡眠不足で目標RIRを上げる機能で、デロードとは別物。

**承知の上で捨てた限界。**体重の減量判定（-0.1kg/週）は推定量のノイズ床（σ0.5kg・21日窓で標準偏差0.13kg/週）より小さく、体重計のノイズだけで提案の有無が反転していた。ロバスト推定（D-019）は外れ値には効くが、ガウスノイズ下の分布は最小二乗法とほぼ同じなのでこの問題は解決しない。**閾値が分解能より細かいなら、その判定は存在しないのと同じ。**

### D-034 / D-065 `FindAll` が全件を返す設計は据え置く

### D-136 認証は OAuth。ミドルウェアがセッションから「誰か」を決める

GitHub / Google でログインし、サーバーがセッショントークンを発行する。
D-068 が「OAuth へはミドルウェアの差し替えで移れる」と書いていたとおりになった。

**所有者は引数で渡す。context に入れない。**リポジトリの口を見ても「誰のデータか」が
読めなくなり、渡し忘れがコンパイルで落ちず**実行時に他人のデータを返す**形で出る。
例外はミドルウェアからハンドラへの1ホップだけで、他に渡す手段が無いため。
ハンドラが取り出したらそこで終わり。

**主キーに所有者を含める。**`set_logs.id` はクライアントが採番するので、列を足すだけ
では (a) 他人と同じIDで衝突が返り「その記録が存在する」ことが漏れる (b) 他人のIDを
消せる。`(user_id, id)` にすれば SQL の形として塞がる。

**セッションは Bearer と localStorage のまま。**画面は `*.workers.dev`、API は Cloud Run で
別オリジン。API が出す Cookie は SPA から見てサードパーティで、Safari が落とす。
保存するのはトークンではなく **SHA-256 のハッシュ**。DBが漏れてもセッションは漏れない。
ハッシュで引くので定数時間比較も要らない。

**トークンはフラグメントで渡す。**`#token=...`。クエリだと Referer とアクセスログに残り、
90日効くトークンなので残った時点でそれを読める全員が本人になれる。

**戻り先は `WEB_ORIGIN` 1つ。**`redirect_uri` を要求から受け取ると open redirect になる。

**`state` が合わなければ、コードを交換する前に止める。**交換してからセッションを作らない
だけでは足りない。攻撃者のコードを本人のブラウザ経由で使わせている時点で、その先の
副作用は止められない。

**認証を通さない経路は1つずつ並べる。**ヘルスチェックとログインの入口・戻りだけ。
`/auth` でまとめて除外すると、ログアウト（`DELETE /auth/session`）が誰でも叩ける口として
静かに開く。

**開発用セッションは `DATABASE_URL` が無いときだけ効く。**画面の検査スクリプトは固定の
トークンでログイン済みの状態を作る。フラグで守ると、そのフラグが本番で立った瞬間に
穴になる。インメモリは再起動で記録が消える構成で、そもそも本番では使えない。
**使える状況が構造的に限られているほうが、設定の書き間違いで破られない。**

**既存の記録は既定ユーザーに寄せ、初回ログインの前に手で結ぶ**（手順は `deploy.md`）。
「最初にログインした人が引き継ぐ」にはしない。デプロイ直後に見知らぬ人が先にログイン
しただけで記録を持っていかれる。

### D-137 プロバイダをまたぐ名寄せは、確認済みメールアドレスだけで行う

GitHub と Google でログインすると**別のアカウントになっていた**。`accounts` の主キーが
`(provider, subject)` で、GitHub の数値IDと Google の `sub` は別の名前空間だから。
本人から見れば「Google を押したら記録が消えた」で、原因は分からない。

D-136 の時点では「名寄せは要るときに作る」としていた。**要るようになったので作った。**

**結ぶ材料は確認済みメールアドレスだけ。**他に「同じ人だ」と言える情報が無い。
GitHub は `GET /user/emails` の `primary` かつ `verified` の1件、Google は
`email_verified` が true のときだけ。`GET /user` が返す `email` は使わない
（公開設定次第で null になり、確認済みかどうかも分からない）。

**未確認のアドレスで結ぶと、名寄せがそのまま乗っ取りの経路になる。**他人のアドレスを
登録したアカウントを作ってログインするだけで、その人の記録に入れる。どちらの
プロバイダも確認の済んだものだけを verified として返すので、そこを通った値だけを使う。

**結ぶのはアカウントを作るときの1回だけ。**既にあるアカウントの `user_id` は決して
書き換えない。書き換える経路があると、認可先のメールアドレスを他人のものに変えて
入り直すだけで他人の記録に入れる。

**結べないときは結ばない。失敗にはしない。**アドレスが無い・一致する人がいない・
同じアドレスに複数の利用者がいる。どれも「分からない」であって「壊れている」ではない
ので、新しい利用者を採番して先へ進む。**複数いるときに片方を選ばない**のが要点で、
選び方次第で他人の記録に結びつく。

**引きが壊れたときだけ失敗させる。**保存先に届かなかったのを「見つからなかった」と
同じ扱いにすると、DBが一瞬応えなかっただけで**本人の記録から切り離された利用者が
黙って生まれる**。あとから直すには、どの行が誤ってできたかを人が突き合わせるしかない。

**連携画面は作らない。**「ログイン済みの状態で、もう一方のプロバイダを追加で接続する」
という手順を踏ませれば確実だが、それは**決めることを増やす**（CLAUDE.md）。
ジムで考えずに済ませるアプリに、アカウント連携の画面は要らない。

### D-139 週目標は利用者の設定ではない。1回の量から導き、欠けている割合で埋める

**週目標を利用者に決めさせていた。**設定画面に21区分の数値入力があった。ところがこの数字は
好みではなく**補助の選択器の制御パラメータ**で、種目マスタの刺激プロファイルと対になっている。
三頭外側が12.5なのは「三頭を鍛えたいから」ではなく、ベンチと各種プレスが副次刺激で注ぎ込む量を

変えるたびに既定で上書きされ、手で直した値は保持されていなかった。**編集の口ごと消した。**

**1日の上限が実質無かった。**補助の枠が `maxSlots = 8` という定数で、軸を足した9種目27セットが
全頻度・全セッションで出ていた（通し検証で週1〜3回は例外なく27）。週7回なら週189セット。
「1セッション9〜36セット」の検査は週の合計を見ておらず、通っていた。上から消して好きなところで
やめてよいキュー（D-116）のつもりでも、9種目並べば全部やれという圧になる。

**1回の量（種目数2〜6 × セット数2〜6）を利用者に選ばせる。**CLAUDE.md の表で言えば、
「1回にどれだけ時間を取れるか」は本人にしか分からない問いで、頻度と同じ棚に置く。「何セットが
適切か」（本人に答えられない）とは別物。選択肢にして自由入力にしないのは、分割法をプリセットから
選ぶだけにしたのと同じ理由。既定は4種目×3セット。

**週目標は設定から導く。**

```
週の総セット数 = 頻度 × 種目数 × セット数
週の刺激総量   = 週の総セット数 × 1セットあたりの平均寄与（いまは約1.77）
区分の週目標   = 週の刺激総量 × その区分の割合
```

平均寄与は種目カタログの性質なので、定数に書き写さずカタログから数える。配分表（`regionShare`）は
**比だけが意味を持つ**。以前の表は絶対数の顔をしていたが、合計152.5は週3回の実供給
（81セット × 1.77 ≒ 143）に後から合わせた線だった。割合として持てば供給が変わっても表は動かない。

**補助の区分は「欠けている割合」（残り ÷ 目標）の大きい順に埋める。**以前は「最後に刺激して
からの日数」が第1キーで、どの区分にもほぼ均等に順番が回り、配分表は同点処理にしか効いて
いなかった。1日4種目では達成率が 54〜168% に開き、52週平均でも縮まなかった（偏りであって
ばらつきではない）。配分表を実測に合わせ込むのも試したが、選択が週目標を見ているので合わせた
瞬間に実測が動き、収束しなかった。日数を第1キーにしていた本来の理由（残りの絶対値で並べると
小さい区分が飢える）は、割合なら目標の大小が打ち消されるので起きない。**一度も刺激していない
区分を最優先にする番兵は残し、日数は同点処理に下げた。**

**残差は4週（28日）の窓で数える。**1週の窓だと、週目標が1種目ぶん（3セット）より小さい区分が
抑えられない。週3回のカーフは目標1.7セット/週だが、1回選ばれると3セット入り、7日経つと窓から
消えて「10割欠け」に戻り、すぐまた選ばれる（179%に張り付く）。4週なら目標も4週ぶんになり、
1回ぶんの刻みより十分大きい。画面の充足も同じ窓で数え、週あたりに直して見せる。

| 既定 4種目×3セット | 日数が第1キー・7日窓 | 割合が第1キー・7日窓 | 割合が第1キー・28日窓 |
|---|---|---|---|
| 週2回 | 67〜168% | 64〜202% | **79〜134%** |
| 週3回 | 72〜157% | 68〜179% | **90〜127%** |
| 週5回 | 78〜167% | 86〜140% | **94〜129%** |
| 週7回 | 78〜137% | 93〜137% | **96〜128%** |

**週1回は対象外。**4週で48セットを21区分に配ることになり、小さい区分の4週ぶんの目標（約2.4）が
1種目ぶん（3）より小さい。窓をどう取っても回りきらない。選ぶことは妨げないが、配分の質は
保証しない（通し検証も週2回からしか見ない）。

**計画と画面は、保存された週目標を使わず設定から組み直す**（`seed.WithDerivedTarget`）。
保存値を信用すると、導き方を変えたときに頻度も量も触っていない既存の行だけが古い目標で動き
続ける。保存列はまだ残っているが、書かれるだけで読まれない。消すのは別の変更。

**今日の計画が一日中変わらない（D-116）の例外は、設定を変えたときだけ。**1回の量や頻度を
変えれば今日のリストも変わる。記録では動かない。

**採らなかったもの。**「今日は何分？」を毎回聞く案は、決めることを毎日1つ増やす。配分表を
手で調整する案は、上のとおり追いかけっこになる。平均を取る期間を延ばす案は、偏りには効かない。
