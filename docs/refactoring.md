## 推定の入口が3つに散らばっている

**症状。**「記録から推定1RMを出す」経路が3つあり、**うち2つが自重を織り込んでいない**。

| 場所 | 実効負荷への変換 |
|---|---|
| `SessionPlanner.Plan`（重量の処方） | 通っている |
| `DeloadPolicy.sessionValues`（停滞の判定） | **通っていない** |
| `query.Stats.Trends`（推移グラフ） | **通っていない** |

結果として、**自重でやる種目は停滞判定にも推移グラフにも乗らない**。懸垂を自重で3年続けても、グラフに線が引かれず、停滞していても提案が出ない。

**原因。**変換（`effectiveHistory`）を呼び出し側に置いたこと。3箇所が同じことを覚えていなければならず、2箇所が覚えていない。

**境界ははっきりしている。**

```
推定する            → 変換した履歴
数える・日付・表示   → 生の履歴
```

生の履歴が要るのは `CoverageBetween`（セット数を数える）、`sessionIndexInWeek`（日付を数える）、`AccessorySelector` の回復判定（いつやったか）、`query.History`（記録した加重をそのまま見せる）。**どれも重量を見ていない**か、**記録そのものを見せたい**。

つまり**呼び出し側が選ぶ必要がない**。「推定する」という操作に変換がくっついているだけ。

**案。**

- **A：`Plan` の中だけ閉じる。**`planMain` / `planAccessory` に履歴ではなく「推定する能力」（クロージャ）を渡す。小さいが、デロードと推移グラフは直らない
- **B：変換を推定器の内側へ入れる（推奨）。**呼び出し側は常に生の履歴を渡す。呼び忘れが原理的に起きない
- **C：型を分ける。**`EffectiveHistory` を作り、生の履歴を渡すとコンパイルが通らないようにする。保証は最強だが、いま無い問題まで防ごうとしている

**Bの厄介な点。**`DeloadPolicy` と `query.Stats` は推定器を経由せず `TrainingSession.MedianOneRepMax()` を直接呼んでいる。このメソッドは引数を取らないので、Bをやるには**3箇所が同じ入口を通るように整理する**必要がある。

**着手するときの注意。**デロードと推移グラフに自重種目が乗ると、**過去の記録が遡って効く**。移行直後にいきなりデロードが提案されうるので、独立に検証する。

## `AccessorySelector.Select` の中のソートが上流と重複している

`usablePool`（`session_planner.go:191`）が既に ID 昇順に並べたものを渡しているのに、`Select`（`accessory_selector.go:102`）がもう一度並べ直している。**production の経路では常に no-op。**

同じ不変条件を2箇所で守っている状態。どちらかに寄せる。

`usablePool` 側のソートは「同じ入力から同じ計画が出る」という全体の決定性を支えていて根が深いので、**`Select` 側を消して「並んだプールを渡すのは呼び出し側の責任」と契約に書く**ほうが素直。`Select` の単体テストは並べて渡すよう直すことになる。

出力の並びには関わらない（`Select` が並べているのは候補プールであって結果ではない）ので、急がない。

**変異で確かめた（2026-09-07）。**両方のソートを逆順にしても、補助の並びを見ているテストは全部緑のまま通る。**出力の並びに影響しないという読みは正しかった。**

同時に、テスト側が「補助はIDの昇順で返る」を検査していたことが分かった。これは実装の契約ではなく偶然で、当日の記録を見ていた頃の手当て（着手済みが先頭に寄るのを防ぐ）の名残。**偽の契約なので消した。**優先度の付け方を変えたときに理由の無い赤が出る。

## 週の頻度の上限が4に固定されている

`maxFrequencyPerWeek = 4`。理由は「毎セッションで BIG3 すべてにスロットを割り当てる設計だから」で、上げるとデッドリフトを週27セットやる前提になる。

**D-117 で解決する見込み。**ヘビー枠が1セッション1つになれば、週6でも各種目は週1〜2回。既存の強度表がそのまま使える。

コメントにある「それより多く通う場合は補助種目の日を自分で足す」は、週6で通う人をアプリの外に追い出す案内になっている。分割の導入で正面から扱う。

## 週の窓が暦週になっている

残差は「週の始まり〜前日」で数えている（`CoverageBetween(req.History, pool, req.Date.WeekStart(), ...)`）。
暦週だと**月曜にリセットされる**ので、週の後半に残差が積み上がって山が来る。
直近7日のローリング窓なら、残差が週目標で上界され、どこで区切っても投与量が爆発しない。

いま壊れてはいない。週の頻度が上がる（分割法・仕様D）と効いてくる。

## 残差をそのまま処方している

週目標14セットの区分に対して、週の最初のセッションで残差14を全部出そうとする。
本来は「今日の投与量 = 週目標 ÷ その区分が週に何回アクティブか」で割るべき。

週4回・全身法では1セッションの上限で頭打ちになるので表面化していない。
**分割が入って「その区分がアクティブな日」が絞られると効いてくる。**仕様Dで扱う。

## 分割スロットが暦で進んでいる

`sessionIndexInWeek` は日付から求めている。休んだ日にスロットが飛ぶので、
週4回の設定で週2回しか通わないと先頭2つしか使われない（`slot.go` のコメントが
この破綻を認めていて、標準スロットを先頭に置くという回避策を取っている）。

**「セットが記録された日の数」で進めれば回避策が要らなくなる。**
D-117 で `SlotCatalog.Select` を「その種目にとって何本目か」に変えるので、そのとき一緒に見る。

## センチネルの名前がパッケージ名と重なっている

**症状。**集約でパッケージを割った（D-122）結果、`exercise.ErrExerciseNotFound`・`program.ErrProgramNotConfigured`・`setlog.ErrConflictingSetLog` のように、パッケージ名が名前の中で二度出る。

**やらなかった理由。**D-122 は機械的な移動で、「全テストが緑のまま」が検収だった。改名を混ぜるとその検収が効かなくなる。

**やるなら。**`exercise.ErrNotFound`・`program.ErrNotConfigured`・`setlog.ErrConflict` の形。呼び出し側は `errors.Is` の引数だけなので影響範囲は小さい。同時に `exercise.ExerciseID` → `exercise.ID`、`setlog.SetLogID` → `setlog.ID`、`condition.ConditionLog` → `condition.Log` も揃うかを見る。

**やらないと決める理由もありうる。**`ExerciseID` は presentation 層まで名前が届いていて、そこでは `exercise.` が付かない文脈もある。短くして曖昧になるなら、重なったままのほうがいい。
