## 推定の入口が2つに分かれている

**症状。**「記録から推定1RMを出す」経路が2つあり、**片方が自重を織り込んでいない**。

| 場所 | 実効負荷への変換 |
|---|---|
| `SessionPlanner.Plan`（重量の処方） | 通っている |
| `query.Stats.Trends`（推移グラフ） | **通っていない** |

結果として、**自重でやる種目は推移グラフに乗らない**。懸垂を自重で3年続けても、グラフに線が引かれない。

**原因。**変換（`effectiveHistory`）を呼び出し側に置いたこと。呼び出し側が覚えていなければならず、片方が覚えていない。

**境界ははっきりしている。**

```
推定する            → 変換した履歴
数える・日付・表示   → 生の履歴
```

生の履歴が要るのは `CoverageBetween`（セット数を数える）、`AccessorySelector` の回復判定（いつやったか）、`query.History`（記録した加重をそのまま見せる）。**どれも重量を見ていない**か、**記録そのものを見せたい**。つまり**呼び出し側が選ぶ必要がない**。

**案。**

- **A：`Plan` の中だけ閉じる。**小さいが、推移グラフは直らない
- **B：変換を推定器の内側へ入れる（推奨）。**呼び出し側は常に生の履歴を渡す。呼び忘れが原理的に起きない
- **C：型を分ける。**`EffectiveHistory` を作り、生の履歴を渡すとコンパイルが通らないようにする。保証は最強だが、いま無い問題まで防ごうとしている

**Bの厄介な点。**`query.Stats` は推定器を経由せず `TrainingSession.MedianOneRepMax()` を直接呼んでいる。このメソッドは引数を取らないので、Bをやるには**両方が同じ入口を通るように整理する**必要がある。仕様の後段として `docs/specs/2026-08-30-unify-estimation-entry.md` に書いてある。

**着手するときの注意。**推移グラフに自重種目が乗ると、**過去の記録が遡って効く**ので、独立に検証する。

## `AccessorySelector.Select` の中のソートが上流と重複している

`usablePool` が既に ID 昇順に並べたものを渡しているのに、`Select` がもう一度並べ直している。**production の経路では常に no-op。**

同じ不変条件を2箇所で守っている状態。`usablePool` 側のソートは「同じ入力から同じ計画が出る」という全体の決定性を支えていて根が深いので、**`Select` 側を消して「並んだプールを渡すのは呼び出し側の責任」と契約に書く**ほうが素直。`Select` の単体テストは並べて渡すよう直すことになる。

**変異で確かめた（2026-09-07）。**両方のソートを逆順にしても、補助の並びを見ているテストは全部緑のまま通る。**出力の並びに影響しないという読みは正しかった。**同時に、テスト側が「補助はIDの昇順で返る」という**偽の契約**を検査していたことが分かったので、そちらは消した。

## センチネルの名前がパッケージ名と重なっている

`exercise.ErrExerciseNotFound`・`program.ErrProgramNotConfigured`・`setlog.ErrConflictingSetLog` のように、パッケージ名が名前の中で二度出る（D-122 の副産物）。

**やらなかった理由。**D-122 は機械的な移動で、「全テストが緑のまま」が検収だった。改名を混ぜるとその検収が効かなくなる。

**やるなら。**`exercise.ErrNotFound`・`program.ErrNotConfigured`・`setlog.ErrConflict` の形。呼び出し側は `errors.Is` の引数だけなので影響範囲は小さい。同時に `exercise.ExerciseID` → `exercise.ID`、`setlog.SetLogID` → `setlog.ID`、`condition.ConditionLog` → `condition.Log` も揃うかを見る。

**やらないと決める理由もありうる。**`ExerciseID` は presentation 層まで名前が届いていて、そこでは `exercise.` が付かない文脈もある。短くして曖昧になるなら、重なったままのほうがいい。

## 宣言が1つだと、バリエーションが一度も出ない

軸が系統に含まれる日はバリエーションを出さない（D-125）。宣言が1つだけだと
**毎回その種目が軸になる**ので、バリエーションレーンが永久に空になる。

```
宣言 = {bench}、週3回
  → 軸は毎回ベンチ
  → 系統に軸が含まれる → バリエーションは出ない
  → 週3回とも同じ種目・同じ強度
```

**軸が1つでもバリエーションが出る形にしたい。**門を「軸が系統に含まれるか」
から「今日その系統を2回やることになるか」に読み替えることになる。軸が
ベンチの日にラーセンも出す、という判断を入れるかどうか。

いま壊れてはいない。シードの既定は宣言3つで、本人は4つ。**来てから直す**。

## userinfo の応答を無制限に読んでいる

`internal/infrastructure/oauth` の `fetchUserInfo` が `io.ReadAll` で応答を
最後まで読む。相手は GitHub と Google なので**いま壊れてはいない**。

信頼境界の1行なので、`io.LimitReader` を1枚挟むだけで塞がる。サーバーは
Cloud Run で、1リクエストあたりの確保が既に大きい（D-134）。

**来てから直す**でよいが、直すなら1行。
