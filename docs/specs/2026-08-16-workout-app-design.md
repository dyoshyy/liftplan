# 筋トレ管理アプリ 設計

## 出発点

既存の「筋トレメモ」（他人製・非常にシンプル）を使っていて感じた実際のペイン。

1. 疲労管理や重量を上げるタイミングの判断が難しい
2. 全身法をやりたいが、メニューを設定するのが面倒。未来の分まで事前に置いておきたい
3. 体重・食事・睡眠と連携していない（← 対話の中で「今のアプリの一番の問題点」と特定された）

1 と 2 は分離できない。事前に組んだプログラムが実績に応じて自動で書き換わる、という一つのエンジンになる。

## 立ち位置

- **まず自分専用**。良ければ後で公開を検討する
- 自分専用なので、種目マスタも理論も「自分に効くもの」だけでよい

## 体験の芯

アプリを開くと**今日のセッションがすでに確定して並んでいる**。種目・重量・セット数まで。選択肢は出さない。ジムで考えることは何もない。

各セットを終えたら実績レップと RIR を入れる。これがこのアプリで唯一の入力。重量は原則アプリの出した値をそのまま使う（変更は例外操作扱い）。

セッションを終えると次回以降の全予定が裏で書き換わる。ユーザーは何もしない。

未来の予定は閲覧できるが「これは現時点の予測」という性質を明示する。カレンダーの予定ではなく**天気予報に近い見え方**にする。約束に見えると、ズレたときに裏切られた感じが出るため。

初期設定は2つだけ。**週にジムへ行く回数**と、**同梱された種目マスタから自分が使う種目にチェックを入れる**こと。それ以外はすべてプリセットが埋める。

## 技術スタック

| 層 | 選択 | 理由 |
|---|---|---|
| 進行エンジン | Go（サーバー） | ロジックの定数は使いながら何度も調整することになる。サーバーにあればデプロイだけで反映される |
| API | Go（DDD + Onion Architecture） | 学習と兼ねる。エンジンを持つのでドメイン層に実体がある |
| クラウドDB | Neon Postgres | 分析クエリを SQL で自由に書ける |
| クライアント | Kotlin + Jetpack Compose | Health Connect の公式SDKがKotlin前提。Androidアプリを作る経験自体が目的の一つ |
| ローカルDB | Room | 記録の書き込みを失わないためのローカルバッファ兼キャッシュ |
| ヘルスデータ | Health Connect（読み取りのみ） | 体重・睡眠・栄養。書き戻しはしない |

PWA は途中まで候補だったが却下。Health Connect は Web から読めず、「Androidアプリを作ってみたい」という動機を迂回する理由もない。

## アーキテクチャ

### エンジンはサーバーに置く

中心にあるのは一つの純粋関数。

```
plan(実績ログ, 種目プール, 週目標, コンディション, 日付) → セッション
```

**未来のセッションはどこにも保存しない。** 保存するのは確定した実績と設定だけ。今日のメニューも来週のメニューも、この関数を対象日で呼んだ結果。だから予定と実績が食い違う状態が原理的に発生しない。「常に再計算される予測」という決定はこう畳まれる。

この関数を **Go のサーバー側**に置く。理由は2つ。

1. **ロジックの定数は使いながら何度も調整することになる。** 強度帯の76/81/88%、デロードの閾値、EWMAのalpha、寄与度テーブル。クライアントにあると調整のたびにビルドとインストールが要るが、サーバーにあればデプロイするだけで次にアプリを開いた瞬間から反映される
2. **通信は「今日のセッションを寄越せ」の1回だけ。** 来館あたり1リクエストで、操作のたびに判断が要るタイプのアプリではない。サーバーに置いても重くならない

当初はジムの電波を理由にクライアントへ置く設計だったが、通うジムには WiFi があるためこの前提は外れた。

### データとルールは分けて考える

オフライン性の議論で混ざりやすいが、この2つは別の話。

- **ルール（重量をいくつにするか）** — サーバーでよい。結果はクライアントがキャッシュする
- **データ（セットの記録）** — 必ずローカルへ先に書き、非同期で送る。ネットワーク対策ではなく、**通信待ちでUIが固まるのを防ぎ、書き込みを失わないため**

### サーバー（Onion Architecture）

依存は常に内向き。外側の層は内側を知るが、内側は外側を一切知らない。

- **Domain** — エンティティ・値オブジェクト・ドメインサービス。推定1RM、スロット配分、残差計算、デロード判定はすべてここ。Postgres も HTTP も知らない
- **Application** — ユースケース。リポジトリのインターフェースを定義し、ドメインを組み立てて結果を返す
- **Infrastructure** — Neon Postgres によるリポジトリ実装
- **Presentation** — HTTP ハンドラ。DTO とドメインモデルの変換を担う

**ドメイン層は単体で殴れる形に隔離する。** このアプリで唯一複雑な場所なので、DBもHTTPも立てずにテストできることが重要。

### クライアント

- 今日のセッションを API から取得して表示する。取得結果は Room にキャッシュし、次に開いたときは即座に出してから裏で更新する
- セットの記録は Room に先に書き、非同期で API へ送る
- Health Connect から日次スナップショットを読み、同じく非同期で送る

## RIR の位置づけ

RIR は操作するパラメータではない。重量とレップを決めた時点で RIR は結果として決まる。だから「同じ重量・同じレップで RIR だけ下げる」は不可能。

正しくは **RIR は「止め時の指示」**。レップ数は指示しない。

```
指示：ベンチ 85kg、RIR2 で止める
実行：上げられるだけ上げて、あと2回いけると感じたところで置く
記録：9レップだった
```

レップ数はその日の状態が決める。調子が良ければ10レップ出るし、寝不足なら7レップで RIR2 に到達する。**RIR を止め時にすると、強度が自動でその日のコンディションに追従する。** これが RIR を使う理由。

進行の判定軸は「RIR を下げる」ではなく、**RIR を固定したまま、同じ重量で出るレップ数が伸びたかどうか**。

推定1RM は Epley 系で算出する。

```
限界までの推定レップ = 実績レップ + RIR
推定1RM = 重量 × (1 + 限界までの推定レップ / 30)
```

RIR を全セット入力すると決めたのがここで効く。「8レップ上げた」だけでは限界まで何レップ残っていたか分からず強度が測れない。**RIR があると毎セットが1RM測定になる。**

### 推定1RMの平滑化

単発の記録で全スロットの重量が動くと不安定なので、

- **直近数セッションの指数移動平均**を使う
- 明らかな外れ値（極端に高い・低い1発）は除外する
- **ヒステリシス**：平均が 2% 以上動いたときだけ実際の重量を変更する

これがないと、たまたま調子が良かった日の1セットで全スロットが跳ね上がり、翌週それを引きずって潰れる。停滞判定もこの平滑後の値で見る。

## メイン種目：スロット構成

### 現状のトレーニング実態（設計の前提）

ベンチは週3回、**RIR2 を保ったまま重量とバリエーションで刺激を変えている**。パワーリフティングでは標準的な形。

| スロット | 重量 | 内容 |
|---|---|---|
| バリエーション日 | 80kg | ラーセン・テンポなど。RIR2 維持 |
| 標準日 | 85kg | 通常フォーム。RIR2 目標 |
| 高強度日 | 90〜95kg | RIR1〜2 目標 |

つまり **RIR は調整ダイヤルではなく常に守るガードレール**。動かしているのは週内スロットごとの役割と重量帯。同じ「ベンチ」でも中身が3種類あり、**種目単位ではなくスロット単位**で管理されている。

### 自動生成の仕方

**スロット構成ごと自動生成する。** 週何回やるかを決めたら、強度配分もバリエーション選択もアプリが組む。

推定1RM を基準に各スロットへ **強度帯（%1RM）** を割り当てる。ベンチ1RM を仮に105kgとすれば現状は概ね 76% / 81% / 86〜90% の3点に散っている。この配分をアプリが持ち、1RMが上がれば全スロットの重量が自動追随する。RIR2 は動かさない。

バリエーション種目には「通常フォームより何%下がるか」の**対メイン係数**を持たせ、同じ物差しに乗せる。

## 補助種目：残差を埋める

補助種目は「部位」ではなく**筋区分**で選んでいる。ベンチが大胸筋中部を担当するから、上部はインクライン、下部はディップス／デクラインで埋め、最後にアイソレートで仕上げる。

これはアプリにとって好都合で、**メインのスロットが既にどの筋区分をカバーしているかを計算できるので、残りの穴だけを補助で埋めればいい**。補助の選択は「自分で設計する」から「メインの残差を解く」に変わる。

### 筋区分の解像度

**細かい筋区分（20〜25）を持つ。** 大胸筋上部/中部/下部、広背筋/僧帽筋中部/脊柱起立筋、といった粒度。粗い部位（胸・背・脚）では「胸の上部が足りない」をアプリが見抜けず、今の思考と噛み合わない。

胸だけ細かくて他が雑、という歪みを避けるため、全身を同じ解像度で持つ。

### 割り当てアルゴリズム

1. メインのスロットが各筋区分に与える刺激量を計算する
2. 週目標から差し引いて、**残差**を出す
3. 残差の大きい筋区分から順に、プール内の種目で埋める
4. 同一筋区分を48時間以内に再度当てない制約を先に効かせる
5. 同点なら、前回使ってから最も間隔が空いている種目を選ぶ（バリエーションが自動で回る）

全身法は「全部位を毎回やる」ではなく「週の目標を頻度で割って配る」と捉えると、この単純な貪欲法でほぼ破綻しない。

## 初期データ（登録の面倒を発生させない）

「メニュー設定が面倒」から始まったのに、自動化を強くするほど初期登録という別の面倒が生まれる。ここを潰すのが要点。

- **種目マスタ（種目 × 筋区分 × 寄与度）はアプリ同梱のシード**として最初から入れる。ラーセンプレスもテンポも、対メイン係数のデフォルト値ごと入っている
- ユーザーがやるのは**使う種目にチェックを入れるだけ**。ゼロから作る作業は発生しない
- **対メイン係数は実績から自動で上書きされる**。ラーセンの初期係数が 0.85 でも、3セッションこなせば実測値に置き換わる。シードは「最初の一歩のための仮の値」でよく、正確である必要がない
- **筋区分ごとの週目標セット数もプリセット同梱**（パワーリフティング寄りの推奨ボリューム）。不満が出た区分だけ後から調整する

## 周期とデロード

**無期限に積み上げ、調子で抜く。** 固定ブロック（4週周期など）は組まない。強度帯は一定に保ち、停滞や疲労を検知したときだけデロードを入れる。試合からの逆算ピーキングも当面持たない。

### デロードの中身

**強度を落とす。セット数は維持する。** 推定1RMに対する強度帯を一律で下げるだけで済み、スロット構成もセット数も触らなくていい。

### 発火

**アプリが提案し、ユーザーが承認する。** 完全自動は思想には忠実だが、デロードは重量が目に見えて下がるので、黙って適用されると「なんで今日軽いんだ」となってアプリへの信頼が壊れる。ここだけは判断を一つ残す。

提案時には根拠を必ず表示する（例：「推定1RMが3セッション停滞、体重横ばい、睡眠5.5h平均」）。

### 判定条件

- 体重トレンド横ばい以上で、平滑後の推定1RMが数セッション連続で更新されない → 真の停滞
- 体重トレンドが下降中（減量期）→ 推定1RMの停滞を異常と判定しない。**デロードを発火させない**

## コンディション補正（Health Connect を繋ぐ理由そのもの）

- 睡眠が普段より大幅に短い → その日の負荷を自動で軽くする
- 体重トレンド下降中 → 停滞判定を抑制する（上記）
- 真の停滞と判定 → デロード提案（種目差し替えはMVPに含めない。停滞への対処はデロード一本に絞る）

**減量中の停滞とオーバーリーチによる停滞は、トレーニング記録だけ見ると同じ形をしている。体重と睡眠がないとこの2つを絶対に見分けられない。** ここが既存アプリの最大の欠落であり、このアプリの存在理由。

## 分析・可視化

**MVPには分析UIを作らない。** 見たい軸（推定1RMと体重の重ね書き、睡眠とパフォーマンスの相関、筋区分ごとの週ボリューム実績、カロリー・PFCと強さの関係）はいずれも数ヶ月分のデータがないと線が引けず、今作っても空のグラフになる。

ただし**データの取得と同期はMVPに入れる**。後から「あのときの睡眠も記録しておけばよかった」は取り返せない。UIだけ作らない。

溜まるまでの間、分析が必要になったら Neon に直接 SQL を投げる。自分専用なのでそれで足りる。

## 同期の設計

単一ユーザー・単一端末が前提なので、コンフリクト解決は要らない。

- ログに ULID を振る（採番はクライアント。オフラインでも記録できるようにするため）
- 追記のみ
- 同じ ID を二度送っても壊れない冪等なエンドポイント

これで足りる。

## 検討して却下した案

| 案 | 却下理由 |
|---|---|
| PWA | Health Connect が Web から読めない。学習動機とも合わない |
| Expo (React Native) | 立ち上がりは速いが「Androidを学ぶ」目的に応えない |
| Supabase | 学びが少ない。SQL分析の自由度も自前APIの方が高い |
| ローカルのみ（クラウド後回し） | 後から取り返せないデータがある。同期だけは最初から要る |
| エンジンをクライアント（Kotlin）に置く | ジムに WiFi があり、オフラインが絶対条件ではなかった。定数の調整のたびにアプリを配り直すコストが重い |
| エンジンをクライアントとサーバーの両方に置く | 二重実装の整合を取り続けるコストが永続的にかかる |
| 既存プログラムを1本実装して重量だけ自動進行 | 「自分の組み方でやりたい」を満たさず既存アプリと大差ない |
| 週単位で締めて次週を再生成 | 「常に再計算される予測」を選んだため不要 |
| 目標レップを指示し RIR は実績入力 | RIR を止め時の指示にする方が、コンディションへの追従が自動になる |
| 目標RIRを 3→2→1 と下げて重量を上げる | RIR は結果であって操作できない。また実際の運用は RIR2 固定で重量とバリエーションを動かす形 |
| 粗い部位（8〜10）で管理 | 「大胸筋上部が足りない」を検出できず、実際の思考と噛み合わない |
| デロードを完全自動適用 | 重量が黙って下がるとアプリへの信頼が壊れる |
| 分析UIをMVPに含める | データが溜まるまで意味がない。データ取得だけ先に走らせる |

## MVPスコープ

**入れる**

**サーバー（先に作る）**

- 種目マスタ・週目標のシードと、週頻度・使用種目の設定
- 推定1RMの算出・平滑化・進行
- メインのスロット自動生成（強度帯配分・バリエーション選択）
- 補助種目の残差ベース自動割り当て
- コンディション補正（睡眠・体重トレンド）
- デロード判定と提案
- セッション取得API・ログ受信API・コンディション受信API

**クライアント（サーバーの後）**

- セッション画面（重量・RIR指示の表示、実績レップとRIRの入力）
- Room によるローカルバッファとキャッシュ
- Health Connect からの日次スナップショット取得
- API への非同期同期
- デロード提案の表示と承認

**入れない**

- 分析・可視化UI
- 試合からの逆算ピーキング
- 固定ブロック周期
- 複数端末・複数ユーザー対応
- Health Connect への書き戻し
