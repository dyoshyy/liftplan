**この文書は最初の設計。**いま効いているのは「なぜ作るか」「体験の芯」「エンジンの置き場所」「RIR の位置づけ」「筋区分と残差」で、以下は後続で覆した。

| この仕様の記述 | いま | どこで |

## 出発点

既存の「筋トレメモ」（他人製・非常にシンプル）を使っていて感じた実際のペイン。

1. 疲労管理や重量を上げるタイミングの判断が難しい
2. 全身法をやりたいが、メニューを設定するのが面倒。未来の分まで事前に置いておきたい
3. 体重・食事・睡眠と連携していない（← 対話の中で「今のアプリの一番の問題点」と特定された）

## 立ち位置

- **まず自分専用**。良ければ後で公開を検討する
- 自分専用なので、種目マスタも理論も「自分に効くもの」だけでよい

## 体験の芯

アプリを開くと**今日のセッションがすでに確定して並んでいる**。種目・重量・セット数まで。選択肢は出さない。ジムで考えることは何もない。

各セットを終えたら実績レップと RIR を入れる。これがこのアプリで唯一の入力。重量は原則アプリの出した値をそのまま使う。

初期設定は2つだけ。**週にジムへ行く回数**と、**同梱された種目マスタから自分が使う種目にチェックを入れる**こと。それ以外はすべてプリセットが埋める。

> 未来の予定を「天気予報に近い見え方」で閲覧させる案は、結局作っていない。今日のリストは**ノルマではなく、上から消していって好きなところでやめられるキュー**になった（D-116）。

## エンジンはサーバーに置く

中心にあるのは一つの純粋関数。

```
plan(実績ログ, 種目プール, 週目標, コンディション, 日付) → セッション
```

**未来のセッションはどこにも保存しない。** 保存するのは確定した実績と設定だけ。今日のメニューも来週のメニューも、この関数を対象日で呼んだ結果。だから予定と実績が食い違う状態が原理的に発生しない。

この関数を **Go のサーバー側**に置く。理由は2つ。

1. **ロジックの定数は使いながら何度も調整することになる。** 強度帯、EWMAのalpha、寄与度テーブル。クライアントにあると調整のたびにビルドとインストールが要るが、サーバーにあればデプロイするだけで次に開いた瞬間から反映される
2. **通信は「今日のセッションを寄越せ」の1回だけ。** 来館あたり1リクエストで、操作のたびに判断が要るタイプのアプリではない

当初はジムの電波を理由にクライアントへ置く設計だったが、通うジムには WiFi があるためこの前提は外れた。

## データとルールは分けて考える

オフライン性の議論で混ざりやすいが、この2つは別の話。

- **ルール（重量をいくつにするか）** — サーバーでよい
- **データ（セットの記録）** — 必ずローカルへ先に書き、非同期で送る。ネットワーク対策ではなく、**通信待ちでUIが固まるのを防ぎ、書き込みを失わないため**

## サーバー（Onion Architecture）

依存は常に内向き。外側の層は内側を知るが、内側は外側を一切知らない。

- **Domain** — エンティティ・値オブジェクト・ドメインサービス。推定1RM、残差計算、レーンの組み立てはすべてここ。Postgres も HTTP も知らない
- **Application** — ユースケース。ドメインを組み立てて結果を返す
- **Infrastructure** — Neon Postgres によるリポジトリ実装
- **Presentation** — HTTP ハンドラ。DTO とドメインモデルの変換を担う

**ドメイン層は単体で殴れる形に隔離する。** このアプリで唯一複雑な場所なので、DBもHTTPも立てずにテストできることが重要。

## RIR の位置づけ

RIR は操作するパラメータではない。重量とレップを決めた時点で RIR は結果として決まる。だから「同じ重量・同じレップで RIR だけ下げる」は不可能。

正しくは **RIR は「止め時の指示」**。レップ数は指示しない。

```
指示：ベンチ 85kg、RIR2 で止める
実行：上げられるだけ上げて、あと2回いけると感じたところで置く
記録：9レップだった
```

レップ数はその日の状態が決める。調子が良ければ10レップ出るし、寝不足なら7レップで RIR2 に到達する。**RIR を止め時にすると、強度が自動でその日のコンディションに追従する。**

進行の判定軸は「RIR を下げる」ではなく、**RIR を固定したまま、同じ重量で出るレップ数が伸びたかどうか**。

推定1RM は Epley 系で算出する。

```
限界までの推定レップ = 実績レップ + RIR
推定1RM = 重量 × (1 + 限界までの推定レップ / 30)
```

RIR を全セット入力すると決めたのがここで効く。「8レップ上げた」だけでは限界まで何レップ残っていたか分からず強度が測れない。**RIR があると毎セットが1RM測定になる。**

単発の記録で重量が動くと不安定なので、直近数セッションの指数移動平均を使い、外れ値は中央値で落とす。

## 補助種目：残差を埋める

補助種目は「部位」ではなく**筋区分**で選んでいる。ベンチが大胸筋中部を担当するから、上部はインクライン、下部はディップス／デクラインで埋め、最後にアイソレートで仕上げる。

これはアプリにとって好都合で、**メインが既にどの筋区分をカバーしているかを計算できるので、残りの穴だけを補助で埋めればいい**。補助の選択は「自分で設計する」から「残差を解く」に変わる。

### 筋区分の解像度

**細かい筋区分（20〜25）を持つ。** 大胸筋上部/中部/下部、広背筋/僧帽筋中部/脊柱起立筋、といった粒度。粗い部位（胸・背・脚）では「胸の上部が足りない」をアプリが見抜けず、今の思考と噛み合わない。

胸だけ細かくて他が雑、という歪みを避けるため、全身を同じ解像度で持つ。

### 割り当てアルゴリズム

1. メインが各筋区分に与える刺激量を計算する
2. 週目標から差し引いて、**残差**を出す
3. 残差の大きい筋区分から順に、プール内の種目で埋める
4. 同一筋区分を48時間以内に再度当てない制約を先に効かせる
5. 同点なら、前回使ってから最も間隔が空いている種目を選ぶ

全身法は「全部位を毎回やる」ではなく「週の目標を頻度で割って配る」と捉えると、この単純な貪欲法でほぼ破綻しない。

> 3の順位は「残差の大きい区分から」ではなく「最も長く放置している区分から」になった。残差順だと小さい区分が飢える（D-018）。

## 初期データ（登録の面倒を発生させない）

「メニュー設定が面倒」から始まったのに、自動化を強くするほど初期登録という別の面倒が生まれる。ここを潰すのが要点。

- **種目マスタ（種目 × 筋区分 × 寄与度）はアプリ同梱のシード**として最初から入れる
- ユーザーがやるのは**使う種目にチェックを入れるだけ**。ゼロから作る作業は発生しない
- **筋区分ごとの週目標セット数もプリセット同梱**。不満が出た区分だけ後から調整する

## コンディションを取り込む理由

**減量中の停滞とオーバーリーチによる停滞は、トレーニング記録だけ見ると同じ形をしている。体重と睡眠がないとこの2つを絶対に見分けられない。** ここが既存アプリの最大の欠落であり、このアプリの存在理由。

いま効いているのは睡眠→目標RIRの補正と、体重→自重種目の実効負荷（D-019）。停滞判定そのものはやめた（D-124）。

## 同期の設計

単一ユーザー・単一端末が前提なので、コンフリクト解決は要らない。

- ログに ULID を振る（採番はクライアント。オフラインでも記録できるようにするため）
- 追記のみ
- 同じ ID を二度送っても壊れない冪等なエンドポイント

## 検討して却下した案

| 案 | 却下理由 |
|---|---|
| Supabase | 学びが少ない。SQL分析の自由度も自前APIの方が高い |
| ローカルのみ（クラウド後回し） | 後から取り返せないデータがある。同期だけは最初から要る |
| エンジンをクライアントに置く | ジムに WiFi があり、オフラインが絶対条件ではなかった。定数の調整のたびにアプリを配り直すコストが重い |
| エンジンをクライアントとサーバーの両方に置く | 二重実装の整合を取り続けるコストが永続的にかかる |
| 既存プログラムを1本実装して重量だけ自動進行 | 「自分の組み方でやりたい」を満たさず既存アプリと大差ない |
| 週単位で締めて次週を再生成 | 「常に再計算される予測」を選んだため不要 |
| 目標レップを指示し RIR は実績入力 | RIR を止め時の指示にする方が、コンディションへの追従が自動になる |
| 目標RIRを 3→2→1 と下げて重量を上げる | RIR は結果であって操作できない |
| 粗い部位（8〜10）で管理 | 「大胸筋上部が足りない」を検出できず、実際の思考と噛み合わない |

> **PWA と Expo を「Health Connect が読めない／Android を学ぶ目的に応えない」として却下していたが、覆した。**「使い始める」と「Android を学ぶ」は別の目的で最短路が違い、サーバーが完成しているのに一度も使われていない状態のほうが損失が大きかった（`2026-09-07-pwa-client-design.md`）。
