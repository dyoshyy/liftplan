# 実効負荷の変換を失敗しない形にする

`docs/refactoring.md` の「推定の入口が3つに散らばっている」に着手するので、ここに切り出す。

**この仕様は2段階に分かれる。**先に「変換が失敗しうる」という前提を潰し、入口の一本化そのものは後段に置く。理由は後述するが、一本化はいま検収が作れない。

## 負債の本体

同じ `History` 型が、生の重量を運ぶ経路と実効負荷を運ぶ経路の2つに使われている。型が同じなので、どちらを渡すべきかを呼び出し側が覚えていなければならない。

なぜ2つに分かれているのか。生の履歴を使う経路が重量を読んでいるからではない。計算に使う3経路は重量を一切見ていない。

| 経路 | 重量を読むか |
|---|---|
| `CoverageBetween` | 読まない（`coverage.Plus(e.Stimulus(), one)` で1セットとして数えるだけ） |
| `AccessorySelector` | 読まない（`Weight` の参照がファイル内にゼロ） |
| `sessionIndexInWeek` | 読まない（日付だけ） |
| `query.History` | 読む。ただし記録をそのまま見せる表示 |

分かれている本当の理由は、**`effectiveHistory` が体重を引けないセットを間引くこと**にある。

```go
effectiveWeight, ok := EffectiveLoad(l, findExercise(pool, l.ExerciseID()), c)
if !ok {
    continue   // ここで件数が変わる
}
```

重量の値が変わることは、数える経路に何の影響も与えない。**件数が変わることが影響する。** やったはずのセットが消え、同じ区分の補助が何度でも提示される。

そしてこの `continue` は、下流が既に守っているものを手前でもう一度守っていた。`NewOneRepMax` の下限は `smallestPositive`（`one_rep_max.go:35`）なので、0kg のセットは `EstimatedOneRepMax()` が `false` を返し、`MedianOneRepMax()` が除外し、`smooth()` が飛ばす。

**「別の層が既に守っているなら作らない」がそのまま当てはまる。**

## 決めたこと

### 1. 変換を全域関数にする。失敗したら 0kg に倒す

`EffectiveLoad` が体重を引けないとき、セットを落とさずに **0kg** として残す。0kg は下流が自動で除外するので、推定の結果は現在と一致する。件数は変わらない。

**生の加重をそのまま残してはいけない。** 体重未記録で加重10kgのチンニングを 10kg のまま残すと、`EstimatedOneRepMax` が `true` を返す。実際は 85kg 相当なのに 10kg として推定が通り、極端に軽い重量が処方される。「自分で決める」にすらならない。0kg に倒すことで、下流の「推定できない」判定に正しく載る。

**なぜ出力が変わらないか。** いまは落とされて `LastPerformed` に入らず `isStale` が `true` になり推定なし。変更後は 0kg で残るので `isStale` は `false` になるが、`smooth()` が全セッションを飛ばして `started == false` を返すので、やはり推定なし。経路は違うが結論は同じ。

この「0kg は負荷不明を表す」という約束は、`smooth()` のコメントが既に警告している依存（`NewOneRepMax` が0を弾くことに依存すると、将来1RMの下限を変えたときに静かに壊れる）に乗る。**下限を変えたら赤くなる変異テストを1本置いて閉じる。**

### 2. 前方外挿はしない（却下）

当初は `BodyWeightAsOf` を「date 以前に無ければ最古の体重を使う」に変え、`ConfigureProgram` で体重1件を保証することで、変換が失敗する条件そのものを無くす計画だった。**敵対的レビューで破れたので却下する。**

**却下の理由は3つある。**

**危険側に振れる。** 3ヶ月離脱して体重が 73→88kg になった人が過去ログを取り込むと、推定1RMが 95.05 → 104.36kg になり、`AddedWeight` の出力が「自重（0kg）」から「+8.9kg」に変わる。正しい答えが「自重でやれ」なのに加重を処方する。これは `defaultMaxStaleDays = 42` のコメントが名指しで防ごうとしていた事故そのもので、しかも **`isStale` は履歴の新しい端を見て外挿は古い端に効くので、42日判定は原理的にこれを防げない。**

**誤差が打ち消されない。** 推定側は `log.PerformedOn()`、処方側（`AddedWeight`）は `req.Date` で体重を引く。この2つは同じ値ではなく、外挿が仕事をしている場面とはまさに両者が食い違う場面のこと。さらに `added = orm × I − k·bw` は引き算なので、1RM の誤差 9.8% が加重では 0kg → 8.9kg になる。**仕様 §5 の「相対値だから一貫していれば足りる」は、この引き算があるので転用できない。**あれは係数が定数であることに依存した主張で、時変の加法バイアスには効かない。

**自己修復しない。** 後方参照の古さは体重計に乗った瞬間に治る。前方外挿の誤差は「記録中最古の体重」に固定され、データが増えても永久に治らない。加えて、最も検証されていないデータ点（最初の1件）を最も影響範囲の広いデータ点に昇格させる。

### 3. 体重の「1件保証」も置かない（却下）

`ConfigureProgram`（`PUT /api/program`）に保証を置く案も却下する。**このアプリは `ConfigureProgram` を通らずに使えるように作ってある。**

```go
// cmd/api/main.go:307 seedProgramIfMissing
// 空のデータベースから始めたユーザーが、PUT /api/program を叩かないと
// 何も使えない状態を避ける。
```

新規ユーザーは起動しただけで program 行ができ、`daily_conditions` は0件のまま `GET /api/sessions` が通る。これは例外ではなく既定の経路。インメモリモード（`DATABASE_URL` 無し）に至っては再起動のたびに体重0件から始まる。

仮に置いたとしても穴が残る。`WithBodyWeight` は範囲外の値を黙って捨てる（`condition.go:138`）ので、検査を書かなければ「保証を通ったのに体重0件」が無検知で残る。さらに `PUT /api/program` は初期セットアップ専用ではなく設定編集にも使われるので、週の頻度を変えるたびに当日の実測体重が上書きされる。`ConditionRepository` の「項目ごとに上書き」という規則と正面から衝突する。

**1で変換が全域になれば、保証はそもそも要らない。**

### 4. 入口の一本化は後段に回す

`MedianOneRepMax` に `LoadContext` 引数を足して3経路を強制的に揃える案は、**いま実施しない。**

**検収が作れないため。**実験で確認した事実として、3箇所すべてにゼロ値 `LoadContext{}` を渡しても全パッケージが緑になる。コンパイラが強制するのは「渡すこと」であって「正しく渡すこと」ではない。「全テストが緑」「`git grep effectiveHistory` が空」「`SetLog` の複製がゼロ」という検収は、3つとも null 実装で満たせてしまう。CLAUDE.md の「変異を入れて赤くなるか確認する」が通らない。

**そして観測できるデータが存在しない。**`Trends` は `e.Kind() != KindMain` で絞り（`stats.go:71`）、`Propose` に渡るのは `mainIDs` だけで（`session_planner.go:118`）、BIG3 の自重係数は 0。変換の有無が出力に現れる経路がない。テストを先に書いて赤くすることが原理的にできない。

**別の層が既に到達を防いでいる。**これは1で `continue` を消す根拠に使ったのと同じ基準であり、同じ基準を適用すれば「いまは作らない」になる。

着手のトリガーは**仕様D §8 で `KindMain` の絞り込みが軸参照に置き換わるとき**。そこで初めて自重種目が停滞判定と推移グラフに到達し、変換が通っていないことが失敗するテストとして現れる。そのとき一緒に直す。

なお、そのときには**もう一つの不一致**も揃える必要がある。`SessionPlanner` は `usablePool`（選択された種目だけ）を、`query.Stats` は全 pool を変換に使っている。同じログが2経路で違う実効負荷になりうる。

## 手順

### 1. `EffectiveLoad` を全域にする

**先に書くテスト。** 体重が一件も無い `ConditionLog` で、係数を持つ種目の加重10kgのセットを変換すると、**0kg** が返る（生の10kgではない）。

`EffectiveLoad` のシグネチャから `bool` を落とし、体重が引けなければ `Weight{}` を返す。doc に「0 は負荷不明を表す」と明記する。

`e == nil` / `log == nil` も同じく 0kg。ただし**種目が pool に無い場合は体重とは無関係に起こる**（選択から外した種目の過去ログなど）。ここも 0kg に倒すことを doc に書く。

### 2. `effectiveHistory` の `continue` を消す

全セットを `append` する。件数が入力と一致することをテストで固定する。

### 3. 変異テストを置く

`NewOneRepMax` の下限（`smallestPositive`）を変えたら赤くなるテストを1本。「0kg が下流で除外される」という前提に依存していることを明示的に守る。

### 4. `AddedWeight` の扱いを決める

**`bool` は残す。** `AddedWeight` が `false` を返すのは「加重が計算できない → 自分で決める」を出すため。体重0件で `bw = 0` にフォールバックすると `added = total - 0 = total` になり、**自重種目に実効負荷そのものを加重として処方する**（チンニングで「70kg 付けろ」）。`EffectiveLoad` と逆関数の関係にあるので同じ扱いにしたくなるが、**失敗時の意味が違う。**推定側の0kgは「この記録は推定に使えない」、処方側の失敗は「本人に返す」。

## 検証

- **全テストが緑のままであること。** 1〜2で出力は変わらない。捏造を入れないので、今度はこれが本当の検収になる
- 変換前後で履歴の件数が一致すること
- 変異テスト（3）が、下限を戻したときに赤くなること

## やらないこと

- 前方外挿（決めたこと 2）
- 体重の1件保証・`ConfigureProgram` への `ConditionRepository` 注入（決めたこと 3）
- `LoadContext` による入口の一本化・`effectiveHistory` の削除（決めたこと 4。仕様D §8 と一緒にやる）

この仕様で `History` の2経路が完全に消えるわけではない。`effectiveHistory` は残り、変換済みの `History` も流通し続ける。**変わるのは「間違った方を渡すと壊れる」が「間違った方を渡しても壊れない」になること。**完全な一本化は後段に置く。
