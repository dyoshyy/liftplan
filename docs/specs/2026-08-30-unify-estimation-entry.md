# 実効負荷の変換を失敗しない形にする

`docs/refactoring.md` の「推定の入口が3つに散らばっている」に着手するので、ここに切り出す。

**この仕様は2段階に分かれる。**先に「変換が失敗しうる」という前提を潰し、入口の一本化そのものは後段に置く。一本化はいま検収が作れない（後述）。

## 負債の本体

同じ `History` 型が、生の重量を運ぶ経路と実効負荷を運ぶ経路の2つに使われている。型が同じなので、どちらを渡すべきかを呼び出し側が覚えていなければならない。

なぜ2つに分かれているのか。生の履歴を使う経路が重量を読んでいるからではない。計算に使う3経路は重量を一切見ていない。

| 経路 | 重量を読むか |
|---|---|
| `CoverageBetween` | 読まない（1セットとして数えるだけ） |
| `AccessorySelector` | 読まない（`Weight` の参照がファイル内にゼロ） |
| `sessionIndexInWeek` | 読まない（日付だけ） |
| `query.History` | 読む。ただし記録をそのまま見せる表示 |

分かれている本当の理由は、**`effectiveHistory` が体重を引けないセットを間引くこと**にある。

```go
effectiveWeight, ok := EffectiveLoad(l, findExercise(pool, l.ExerciseID()), c)
if !ok {
    continue   // ここで件数が変わる
}
```

重量の値が変わることは、数える経路に何の影響も与えない。**件数が変わることが影響する。** やったはずのセットが消え、同じ区分の補助が何度でも提示される。

## 決めたこと

### 1. 体重を一度も記録していないなら、既定値 70kg で計算する

`EffectiveLoad` と `AddedWeight` から `bool` を落とし、全域関数にする。体重の記録が**一件も無い**利用者には `defaultBodyWeightKg = 70` を使う。

**なぜ既定値でも変な数字にならないか。**処方の式を展開すると、使う体重 `B` がほぼ約分される。

```
added = 1.333 × (w + k·B) × I − k·B
      = 1.333·I·w + k·B·(1.333·I − 1)
```

補助種目（`I = 0.71`）なら `B` の係数は **−0.054**。**`B` が 20kg ずれても処方は 1kg しか動かない。**推定と処方の**両側で同じ `B` を使う**からで、これが効いている。

**「自重種目に総負荷をそのまま処方する」事故が起きない。**体重を 0 と見なすと `added = total − 0 = total` になり、チンニングに「70kg 付けろ」が出る。既定値なら引き算が生きるので、この形の破綻が原理的に起きない。

**係数と同じ性質の割り切り。**仕様 §5 は自重係数について「力学的な正確さを狙っていない。時間を通じて一貫していれば足りる」と決めた。既定体重も同じで、推定の内部パラメータであり、一貫している限り推移は正しく出る。そして**利用者が体重を一度記録すれば実測に切り替わる**ので、誤差は自己修復する。

### 2. 実測があるのに引けない日は、既定値ではなく 0kg

既定値を使うのは**体重が一件も記録されていない場合だけ**。実測が一件でもあるなら、既定値には倒さない。

問題は「実測はあるが、そのセットの日付より前には無い」場合（セットアップ後に過去日付のログを入れたときに起きる）。ここは **0kg** にして推定から落とす。

**0kg が安全に効く理由。**`NewOneRepMax` の下限は `smallestPositive`（`one_rep_max.go:35`）なので、0kg のセットは `EstimatedOneRepMax()` が `false` を返し、`MedianOneRepMax()` が除外し、`smooth()` が飛ばす。**下流が既に守っている。**セットは落とさず 0kg で残すので、件数は変わらない。

**生の加重をそのまま残してはいけない。**体重未記録で加重10kgのチンニングを 10kg のまま残すと `EstimatedOneRepMax` が `true` を返し、実際は 85kg 相当なのに 10kg として推定が通る。

**処方側にこの分岐は要らない。**`AddedWeight` は `req.Date`（今日）で体重を引く。実測が一件でもあれば必ず過去なので、必ず引ける。よって `AddedWeight` は「一件も無ければ既定値、あれば実測」の2択で閉じる。

### 3. 前方外挿はしない（却下）

当初は `BodyWeightAsOf` を「date 以前に無ければ最古の体重を使う」に変える計画だった。**敵対的レビューで破れたので却下する。**

**危険側に振れる。** 3ヶ月離脱して体重が 73→88kg になった人の過去ログに 88kg を投影すると、推定1RMが 95.05 → 104.36kg になり、処方が「自重」から「+8.9kg」に変わる。正解が「自重でやれ」なのに加重を処方する。これは `defaultMaxStaleDays` のコメントが名指しで防ごうとしていた事故で、しかも **`isStale` は履歴の新しい端を見て外挿は古い端に効くので、42日判定は原理的にこれを防げない。**

**誤差が打ち消されない。**推定側は `log.PerformedOn()`、処方側は `req.Date` で体重を引く。外挿が働く場面とはまさに両者が食い違う場面のことで、`B` の係数が既定値方式の −0.054 に対し **0.9** と 17 倍になる。

**自己修復しない。**外挿の誤差は「記録中最古の体重」に固定され、データが増えても治らない。既定値は体重を一度記録すれば消える。

同じシナリオを既定値で再計算すると、**正解（自重）が出る**。既定値は体重変化に引きずられないため。

### 4. 体重の「1件保証」は置かない（却下）

`ConfigureProgram`（`PUT /api/program`）に保証を置く案も却下する。**このアプリは `ConfigureProgram` を通らずに使えるように作ってある**（`cmd/api/main.go:307` の `seedProgramIfMissing`）。新規利用者は起動しただけで program 行ができ、`daily_conditions` は0件のまま `GET /api/sessions` が通る。インメモリモードは再起動のたびに0件から始まる。

1で既定値を持てば、保証はそもそも要らない。

### 5. 入口の一本化は後段に回す

`MedianOneRepMax` に `LoadContext` 引数を足して3経路を強制的に揃える案は、**いま実施しない。**

**検収が作れない。**実験で確認した事実として、3箇所すべてにゼロ値 `LoadContext{}` を渡しても全パッケージが緑になる。コンパイラが強制するのは「渡すこと」であって「正しく渡すこと」ではない。CLAUDE.md の「変異を入れて赤くなるか確認する」が通らない。

**観測できるデータが存在しない。**`Trends` は `KindMain` で絞り（`stats.go:71`）、`Propose` に渡るのは `mainIDs` だけで（`session_planner.go:118`）、BIG3 の自重係数は 0。変換の有無が出力に現れる経路がない。

**別の層が既に到達を防いでいる。**これは1〜2で `continue` を消す根拠に使ったのと同じ基準であり、同じ基準を適用すれば「いまは作らない」になる。

着手のトリガーは**仕様D §8 で `KindMain` の絞り込みが軸参照に置き換わるとき**。そこで初めて変換漏れが失敗するテストとして現れる。そのとき、`SessionPlanner` が `usablePool`・`query.Stats` が全 pool を変換に使っている不一致も揃える。

## これは挙動の変更である

**リファクタではない。**体重を一度も記録していない利用者のチンニングとディップスに、いま「自分で決める」が出ているところへ**数字が出るようになる**。「全テストが緑」は検収にならない。

CLAUDE.md の2つの原則がぶつかる。「**何kgでやるか**はアプリが答える」と「数字を捏造しない」。前者を採る。42日判定が拒否しているのは「実測はあるが古い」という**本人の実力が不明**なケースで、既定体重は推定の内部パラメータであり性質が違う。加えて、上の計算のとおり出力への影響が構造的に小さい。

## 手順

### 1. 既定値を入れる

**先に書くテスト。** 体重が一件も無い `ConditionLog` で、係数0.95の種目・加重0kgのセットから**重量が決まる**こと。いまは `false` が返って赤くなる。

`defaultBodyWeightKg = 70` を `condition.go` に置く。`EffectiveLoad` / `AddedWeight` から `bool` を落とす。

### 2. 実測があるのに引けない日を 0kg にする

**先に書くテスト。** 体重を1件記録し、それより**前の日付**のセットを変換すると 0kg（既定値70ではない）。

`ConditionLog` に「体重が一件でもあるか」を答えるものが要る。

### 3. `effectiveHistory` の `continue` を消す

全セットを `append` する。**変換前後で件数が一致すること**をテストで固定する。

### 4. 既存テストを反転させる

`TestSessionPlanner_BodyweightExerciseNeedsABodyWeight` は「体重が無いと自分で決める」を検査している。**削除せず、「体重が無ければ既定値で処方する」に反転させる。**

`seed/simulation_test.go:118` は `Conditions: NewConditionLog(nil)` で回している。自重種目に重量が出るようになるので、影響を確認する。

### 5. 変異テストを置く

`NewOneRepMax` の下限（`smallestPositive`）を変えたら赤くなるテストを1本。手順2の「0kg は下流が除外する」という前提に依存していることを明示的に守る。

## 検証

- 変換前後で**履歴の件数が一致**すること
- 体重ゼロの利用者で、自重種目に既定値ベースの重量が出ること
- 体重を記録すると、既定値ではなく実測が使われること
- 変異テスト（5）が、下限を戻したときに赤くなること

## やらないこと

- 前方外挿（決めたこと 3）
- 体重の1件保証・`ConfigureProgram` への注入（決めたこと 4）
- `LoadContext` による入口の一本化・`effectiveHistory` の削除（決めたこと 5。仕様D §8 と一緒に）

この仕様で `History` の2経路が完全に消えるわけではない。`effectiveHistory` は残る。**変わるのは「間違った方を渡すと壊れる」が「間違った方を渡しても壊れない」になること。**

## 積み残し

`defaultMaxStaleDays = 42`（ブランク明けの推定を拒否する判定）を消す案が出ている。本番コードは `one_rep_max_estimator.go` の1ファイルに閉じており、テストは2本。消すと `isStale` が丸ごと消える（「履歴が無い」判定も `smooth()` が `started == false` で守っている）。

**この仕様には含めない。**独立した判断であり、コードベース全体の棚卸しと一緒に扱う。
