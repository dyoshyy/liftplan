# 目標は2種類ある — 軸の再設計

`2026-08-23-axis-lifts-and-bodyweight-design.md` の §1〜§4（軸の枠）を破棄して置き換える。
自重・種目ごとの推定1RM・`ExerciseKind` の廃止はそのまま継承する。

> **実装済み。**この設計のあと、重点種目のバリエーションを
> 独立したレーンにする変更が入っている（`2026-09-10-focus-lift-variations-design.md`）。
> 「宣言も補助を埋める」はそこで覆した。

## なぜ書き直したか

旧仕様は軸を**筋肉群の枠**として設計していた。胸・背中・前腿・後腿の4枠に種目を1つずつ割り当てる。
実装の手前まで進めて、2つの症状が出た。

**症状1：枠の数が決まらない。**前腿と後腿は1つの枠か2つか。これを決める根拠がドメインに無い。
3枠か4枠かで長く止まった。

**症状2：どの枠にも属さない区分が出る。**`ADDUCTOR` はスクワットで使うのに前腿ではない。
`CALF` は脚なのに脚の枠に入らない。三角筋・腕・腹も同様。仕様に「どの枠にも属さない」と
書かざるを得なかった。

**モデルが答えの無い問いを立てさせるときは、モデルが間違っている。**

## 決めたこと

### 1. 目標は2種類あり、独立に設定する

|  | ボリューム側 | 強度側 |
|---|---|---|
| 目標の対象 | **筋区分**（胸に週14セット） | **種目**（ベンチプレスの1RM） |
| 種目の位置づけ | **手段**。等価なら入れ替えてよい | **目的そのもの**。入れ替えられない |
| 処方 | 残差を埋めるセット数 | 推定1RM × 強度% |
| 動機 | 筋肥大 | パワーリフティング的な意識 |

ダンベルフライがケーブルフライに変わっても胸の目標は達成できる。
**ベンチプレスがダンベルプレスに変わったら、ベンチを伸ばす目標は達成できない。**

この非対称性が「軸」の正体である。

### 2. 「軸」は枠ではなく、宣言である

軸とは「**この種目自体を伸ばしたい**」という本人の宣言。順序も回数も持たない、ただの集合。

```
伸ばしたい種目: {ベンチプレス, チンニング, スクワット, ルーマニアンデッドリフト}
```

そう置くと、旧仕様で説明できなかったことが落ちる。

- **なぜ必ず出るのか** — 伸ばすには定期的にやらないと推定1RMが古くなる。
  「必ず出す」は規則ではなく、目標の帰結
- **なぜ強度%で処方するのか** — 1RM目標だから。ボリューム種目に強度表が要らないのはこのため
- **なぜ床引きデッドリフトが要らないのか** — 伸ばしたくないから。RDL も伸ばしたいなら両方入る
  （枠だと片方を補助に落とすしかなかった）
- **`ADDUCTOR` と `CALF` はどの枠か** — **問いが消える**。枠が無いので

**`ExerciseKind`（`MAIN` / `ACCESSORY`）は種目マスタの属性ではなく、利用者の目標だった。**
マスタから消えて `Program` に移る。旧仕様 §8 の結論と一致する。

### 3. ヘビー枠は1セッション1つ。誰がなるかは記録が決める

宣言は集合なので順序を持たない。では脚の日にスクワットと RDL が両方浮上したら、どちらをやるのか。

**最終実施日が古いほうを取る。**同点はマスタ順。

- 本人に順序を並べさせない（ノブが増えない）
- **頻度が創発する。**脚の日が週2回で宣言が2種目なら各週1回。宣言を増やせば各種目の頻度が下がる
- **閾値を置かない。**「N日より古くなったら出す」は書かない。書いた瞬間、却下した
  「種目ごとの週N回」に戻る。**比較（どちらが古いか）だけを使い、判定（何日で古いか）は置かない**

ヘビー枠は**キューの先頭**に置く。「上から消して好きなところでやめる」運用でも1RMの更新が必ず起きる。

「1セッション1つ」は設定ではなく定数。壊れるとすれば「今日は2種目ともヘビーでやりたい」と
言い出したときで、そのときノブが戻る。**壊れるならここ**と分かっているのが重要。

### 4. どの日に出るかは、種目自身が知っている

分割は筋区分だけを扱い、種目を知らない。ではベンチをいつやるかは誰が決めるのか。

**依存は一方向で足りる。**

```
分割 ──知らない──> 種目
種目 ──知っている──> 筋区分（刺激係数を持っているので）
```

**宣言した種目は、その支配区分（刺激係数の最大値を持つ区分）が今日アクティブな日に候補になる。**
回数を指定する必要がない。上下分割なら脚の日は週2〜3回、そのまま候補の回数になる。

支配区分の同点は実在する（`deadlift` と `deficit_deadlift` が `HAMSTRING` と `ERECTOR` で
1.0 に並んでいる）。**係数を動かして潰すのは症状の手当て**で、デッドリフトが両方を同程度に
刺激するのは事実だから、係数はその事実を書いている。**支配区分を実際に使う仕様D で、
「デッドリフトは脚か背中か」という答えのある問いとして扱う。**

### 5. セット数と強度は定数。「その種目にとって何回目か」で引く

宣言が決めるのは「出るかどうか」だけ。**何セットやるかは `SlotCatalog` の定数が決める。**

`slotsByFrequency` は現在「週の何本目か → 強度・セット数・RIR」を返す。
これを「**その種目にとって何本目か**」に読み替える。

**`maxFrequencyPerWeek = 4` の理由が消える。**

```go
// 4に抑えているのは、毎セッションで BIG3 すべてにスロットを割り当てる設計だから。
```

ヘビー枠が1つになれば、週6でも各種目は週1〜2回。既存の表がそのまま使える。
`docs/refactoring.md` の「週の頻度の上限が4に固定されている」はこの変更で解決する。

**ボリューム側から借りない。**「支配区分の今日の投与量をそのままヘビーのセット数にする」案は却下した。
胸の週目標を14→18に上げるとベンチのヘビーセット数が増える。
**「ボリュームを増やしたい」が「強度セッションを重くする」に化ける。**
2つの目標を独立に保つという骨格に反する。

### 6. 宣言は検証する（分割が入ってから）

**「チンニングを伸ばしたい」と宣言したのに `LAT` の週目標が0だと、チンニングは永久に出ない。**
エラーも出ない。沈黙して壊れる。

ただし**これは分割が入ってから起きる。**全身法では全区分が常にアクティブなので、
宣言した種目は必ず出る。週目標は補助の選択にしか効かない。

この仕様で検証するのは **「宣言 ⊂ 選択」だけ。**宣言した種目が選択に入っていないと
`usablePool` から落ち、ヘビー枠が空になる。

### 7. 交わるのは消化のときだけ

```
[強度側] ベンチを伸ばす ──> ベンチを処方（1RM × 強度%、定数セット数）──┐
                                                                  ├─> 台帳
[区分側] 胸に週14セット ──> 残差から補助を選ぶ ────────────────────┘
```

処方の順序は、強度側が先。それが消化した分を引いてから、残差が正の区分にだけ補助を出す。

**不足は埋まり、超過は起きうる。**スクワットと RDL を両方宣言すれば脚のボリュームは週目標を
超えうる。超過を止めるには宣言した種目のセット数を削ることになり、それは強度目標を犠牲にする。
**週目標は下限であって上限ではない**と解釈し、超過は放置する。

なお、複合種目がある限り副次区分の超過は宣言と無関係に起きる（係数モデルの性質）。
2つの目標の衝突ではない。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| **枠**（胸・背中・前腿・後腿に1種目ずつ） | 枠の数がドメインから決まらない。`ADDUCTOR` / `CALF` の帰属問題 |
| **順序つきレパートリー**（種目を優先度順に並べ、アクティブ区分と交わった先頭が軸） | 「伸ばしたい種目」と「区分を埋める手段」が1つのリストに混ざり、境界がどこか誰も知らない。順序に意味を持たせすぎる（下位2つの前後関係には意味が無い） |
| **種目ごとの週N回**（ベンチ週2回） | `胸=14セット` と `ベンチ=週2` の数値のノブが2つになり、互いに矛盾しうる |
| **ヘビーのセット数を区分の投与量から借りる** | 週目標の変更が強度セッションに漏れる（§5） |

順序つきレパートリーは、却下案の中では最も近い。受け入れ条件はすべて通る。
分岐点は「宣言の集合なら、手段側の種目をリストに並べる必要すらない」こと。**設定はむしろ減る。**

## 受け入れ条件

- スクワットと RDL の**両方**を宣言でき、脚の日に交互に出る
- 背中の宣言はチンニング。ラットプルダウンは手段として残差から選ばれる
- 床引きデッドリフトは宣言しなければ出ない
- `ADDUCTOR` / `CALF` の帰属を問われる箇所が仕様にもコードにも無い
- 週5〜6回を扱える

## モデルの変更

### 追加

- `Program.declared []ExerciseID`（順序なしの集合として扱う）— 伸ばしたい種目
- 「宣言した種目のうち、最終実施日が最も古いもの」を返す導出（ヘビー枠）

`Exercise.PrimaryRegion()`（刺激係数の argmax）は**この仕様では作らない。**支配区分が
要るのは「その種目がどの日に出るか」を決めるためで、それを決めるのは分割。全身法では
一度も参照されない。`CLAUDE.md`「必要になるまで作らない」。

### 変更

- `mainExercises(pool)` を廃止。`Program.declared` を参照する形に置き換える
- `usablePool` の ID 昇順ソートは残す（決定性のため）。宣言の順序は使わないので衝突しない
- 補助の候補を「`KindAccessory` の種目」から「今日のヘビー枠を除いた全種目」に変える
- `query/stats.go` の推移グラフは宣言した種目で絞る
- `SlotCatalog.Select` の `sessionIndex` を「週の何本目か」から「その種目にとって何本目か」に変える
- `maxFrequencyPerWeek` を上げる
- 「メイン種目が1つも無い」の検査は `Program.declared` が空かどうかで行う

### 削除

- `ExerciseKind` 列挙と `Exercise.Kind`
- `mainExercises()`

## 今回やらないこと

**分割法（仕様D）。**この仕様は「宣言した種目は毎回1つ、最終実施日が古い順に出る」までを決める。
全身法（＝全区分が常にアクティブ）を既定と見れば、分割なしで成立する。

分割と同時に入れるもの：`Exercise.PrimaryRegion()`、支配区分の同点の解決、
「支配区分の週目標が正であること」の検証。**どれも分割が無いと参照されない。**

**週の窓をローリング7日にする。**現在は暦週。暦週だと月曜にリセットされて週末に山が来る、
という指摘は正しいが、いま壊れてはいない。`docs/refactoring.md` へ。

**分割スロットを出席回数で進める。**同上。仕様Dで正面から扱う。

**投与量の平準化**（残差をそのまま処方せず、週の残り回数で割る）。同上。
