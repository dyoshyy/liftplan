# 補助の割り振り（1週ぶんをまとめて損失を減らす）

**日付**：2026-09-26

補助種目の決め方を、「区分ごとの残差を出して、並べて、埋める」から
「1週ぶんの回にまとめて割り振り、目標からのずれ（損失）を最小にする」へ置き換える。
今日の分だけを確定し、毎回前日までの記録から作り直す。

## 何が問題だったか

### 1. 1つの数字に「優先度」と「量」を背負わせていた

いまの `SessionResidual` は区分ごとに `share = min(4週の不足, 1回の上限)` を出し、
`nextRegion` はそれを「欠けている割合」`share ÷ (4 × 週目標)` で並べる。

分割があると上限 `週目標 ÷ n − 今日の軸の分`（n はその区分が1週に出る日数）が
ほぼいつも効く。4週の不足は1回ぶんよりずっと大きいからだ。すると

```
割合 = (週目標 / n) / (4 × 週目標) = 1 / (4n)
```

となり、**実際にどれだけ遅れているかと無関係に n だけで決まる。**
週目標10・週2日の区分は、実績0%でも75%でも残差は5で同じ。
順番は放置日数と区分名の同点処理で決まっていた。

上限は「上下2分割の最初の下半身の日が週の目標を使い切る（実測38.1、次の下半身の日が6セット）」
を止める当て物だった。量を止めるために入れた上限が、優先度まで潰した。

### 2. 分割を回した通し検証（PR #107）の赤

| 症状 | 仕組み |
|---|---|
| 肩・腕・胸の日にフロントスクワットが出る（18/42組合せ） | 腹はどの日にも属さないので毎日残差が活きる。`front_squat` の腹0.4で腹を埋めに来る。日の外の区分に効くことが罰されない |
| 週1回で腹・腹斜が 218〜260% | 補助は3セット単位でしか入らない。クランチとサイドベンドが互いに副次寄与を持ち、ほぼ毎回選ばれる。超過を罰する項が無い |
| 1回が6セットまで落ちる | 分割と回復の二重の制約で候補が尽きる |
| 5分割・週1回で 44〜60% | 1区分が5週に1回しか来ない。構造的に届かない |

## 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 目的 | 目標からのずれの損失を最小にする | 遅れも超過も同じ枠組みで扱える。いまは超過を罰する項が無い |
| 何日先まで見るか | これからの1週ぶんをまとめて考え、今日の分だけ確定する | 分割の有無を場合分けせずに済む。分割なしは「どの区分も毎回出られる」特殊な場合になる。上限の当て物が要らなくなる |
| 損失の形 | 遅れを重く、超過を軽く罰する（非対称） | 足りないほうが害が大きい。超過も罰するので腹の積み上がりが止まる。対称だと目標ちょうどを避けて枠がよく空く |
| 分割の日の種目 | 主に使う区分（寄与1.0以上）が、今日の区分か、どの日にも属さない区分に入る種目だけ（ハード制約） | 軸の選び方・回復の判定と同じ線の引き方。罰の係数を足すと「決めることを増やさない」に反する |
| 先の回の中身 | いまの軸・バリエーションの決め方で予測する | 予測と実際の決め方がずれようがない |
| 先の回の日付 | 頻度から等間隔を仮定する | 新しい設定が要らない。毎回作り直すので、外れても誤差は1回ぶんで止まる |
| 多様性 | 損失の減り幅がほぼ同じ候補の中で、最終実施日が一番古い種目を取る | 損失を主にし、その中で入れ替える |
| 解き方 | 1週ぶんの枠全体を、まとめて貪欲に埋める | 今日から順に埋めると今日が取りすぎる。厳密解はこの規模では貪欲と差が出ない |

### 採らなかったもの

- **一番遅れている区分を底上げする（max-min）。**超過を見ないので腹の問題が残る
- **帯（60〜145%）に収まれば良しとする。**帯の中で何を選ぶかが別の問いとして残る
- **今日だけを見て、区分ごとの取り分を別の規則で決める。**いまの構造と同じで、優先度と量が1つの数字に戻る
- **周期全体の固定の型を作る。**記録（休んだ日、サボった区分）に追従しない
- **日の外の区分への刺激を損失で罰する。**係数が1つ増え、弱ければ漏れ、強ければハード制約と同じになる
- **直近の種目に罰を足して多様性を出す。**係数が損失の最小化と競合する
- **区分を先に決めて、区分の中で古い種目を取る。**1種目が複数区分に効くことを損失で評価する利点が薄れる
- **損失の最小化だけで選ぶ。**寄与がまったく同じ組（インクラインのダンベルとバーベル）は ID 順で毎回同じ種目になる。似た組（ラットプルダウンとチンニング）も、副次の区分が超えたときにしか入れ替わらない
- **通う曜日を設定させる。**設定が増える
- **直近の実績から間隔を推定する。**毎回作り直すので、等間隔の仮定で追従は足りる
- **horizon（先の回の予測回数）を分割の周期長まで伸ばす（PR 3 で試した）。**
  five_way・週2〜3回の未達が「先の回の見通しが1週に足りず、周期を1周
  見渡せていないタイミングの問題」ではないか、という仮説で、
  `ProjectHorizon` の回数を `max(頻度, 周期長)` にする実験をした。
  結果、容量が足りない区分（TRAP_UPPER・SIDE_DELT）の達成率は指数3の
  ときと**まったく変わらなかった**（週2回で54%のまま）。CALF だけ
  54%→108%に動いたが、これは脚の日の枠の奪い合いでCALFが勝つように
  なっただけで、脚の日自体の容量（37%）は変わっていないので、他の
  脚区分を犠牲にしている。さらに、周期長が頻度を超える低頻度では
  評価日 E が数週間先まで飛び、upper_lower・ppl のようなそれまで
  健全だった構成まで新たに壊れた（ABS=0%・OBLIQUE=0%・FOREARM=146%・
  CALF=179%等）。`Plan()` の所要時間も約4.2倍に増えた。容量の問題は
  見通しの長さでは解けないと判断し、採らなかった。

## 構成

### `Plan` の流れ

```
1. history = req.History.Before(req.Date)                      // いまのまま（D-116）
2. 今日の分割の日、軸、バリエーション                            // いまのまま
3. 先の回を予測する（horizon_projector.go）                     // 新設
     回数：今日を含めて f 回（f = 頻度）
     日付：今日から 7/f 日ごとの等間隔を整数に丸める
     回 k の分割の日：SplitOn(出席回数 + k)
     回 k の軸・バリエーション：いまと同じ関数。前の回の軸をやったものとして
       履歴を仮に進めたものを入力にする
4. 割り振り器が1週ぶんの補助の枠をまとめて埋める（accessory_allocator.go）  // 新設
5. 回0（今日）に入った補助だけを採用し、重量を付ける               // いまのまま
```

### 割り振り器（`AccessoryAllocator`）の入出力

**入力**

- 週目標
- 評価日 E 時点の4週の窓に入る、前日までの実際の記録の刺激
- 回ごと：日付、許される区分、軸・バリエーションがすでに入れる刺激、空き枠の数、1種目あたりのセット数
- 候補プール（除外を引いたもの）
- 種目ごとの最終実施日

**出力**：回ごとの補助種目の列。`Plan` は回0だけを使う。

### 消えるもの

`SessionResidual`（1回の上限を含む）、`ActiveCount`、`nextRegion`、`trackable`、
`AccessorySelector.Select` の中身。

## 損失

評価日 E は予測の最後の回の日。窓は [E−27日, E]。

区分 r（週目標 T_r > 0 のものだけ）について

```
C_r = 前日までの記録のうち窓に入るもの
    + 1週ぶんの軸・バリエーションの刺激（予測）
    + 割り振った補助の刺激（寄与 × セット数）

ρ_r = C_r / (4 × T_r)

loss_r = T_r × |1 − ρ_r|³           C_r < 4T_r
       = T_r × α × |ρ_r − 1|³       C_r ≥ 4T_r     （0 < α < 1）

L = Σ_r loss_r
```

週目標 T_r で重み付けし、遅れの指数は3（**どちらも PR 3 の実装で修正。
最初の版は重み無し・指数2の `loss_r=(1−ρ_r)²` だった**）。実装は ρ を
経由せず C_r・T_r から直接計算する（展開すると `|4T_r−C_r|³/(64T_r²)` /
`α|C_r−4T_r|³/(64T_r²)` になる）。

E までに窓から落ちる古い記録は C_r に入らない。

**式から出てくる性質**（別の規則として書かない）

- **遅れの大きい区分ほど先に埋まる。**指数が3なので、遅れが大きいほど1セットあたりの減り方が急に大きくなる
- **1つの区分に偏らない。**遅れが縮むと減り方も縮み、次の区分へ移る。
  「1週間休んだ翌日に1区分が枠を食い尽くす」を止める当て物が要らない
- **副次の寄与も数える。**種目の減り方は効く全区分の変化の合計
- **目標0の区分は分母にしない。**T_r > 0 の区分だけを和に入れる

**最初の版の誤り①：重みが無かった（PR 3 で見つかった）。**「達成率（ρ）に
した時点で目標の大小は打ち消される」と考えて、重み無しの `loss_r=(1−ρ_r)²`
で出発した。これは損失の**値**については正しいが、**1手あたりの変化**
については正しくない。重み無しだと ρ=0 付近の1手あたりの ΔL は
およそ `−(寄与×セット数)/(2T_r)` になり、週目標 T_r にほぼ反比例する。
達成率がまったく同じでも、週目標の大きい区分（僧帽筋中部・臀筋など）は
1手の効きが薄く見え、貪欲法が系統的に後回しにする。実測：臀筋は
デッドリフト・スクワットの副次寄与だけで達成率100%を超えるのに、
ヒップスラストが（週目標が大きいという理由だけで）どの構成でも一度も
選ばれなかった（`TestSimulation_EveryAccessoryGetsUsedInSomeSetup`）。
T_r で重み付けすると、1手あたりの ΔL の主要項が T_r に依存しなくなり、
旧 `nextRegion`（「欠けている割合」で並べる、スケール不変）と同じ発想に
戻る。回帰検査は `TestAccessoryAllocator_DeltaLossIsNotBiasedByTargetSize`。

**最初の版の誤り②：指数が2だった（PR 3 で見つかった。①を直したあとに
残っていた）。**T_r で重み付けしても、「複数区分にそこそこ効く種目」が
「1区分に大きく効く種目」に、後者の区分の方がずっと遅れているのに
勝ってしまうケースが残っていた。指数2の損失は下がり方が遅れの大きさに
比例して急になるが、急峻さが2乗どまりだと、複数区分ぶんのそこそこの
改善を**足し合わせた**値が、1区分の大きな改善に追いついてしまう。

週目標 T=10 で揃えた例（孤立種目＝区分Aのみ・達成率0%、複合種目＝区分
B・Cにそれぞれ効く・達成率30%、どちらも寄与1.0を3セット追加）：

| 指数 | 孤立の ΔL | 複合の ΔL（B+C合計） | 勝つ方 |
|---|---|---|---|
| 2 | −1.44375 | −1.9875 | 複合（誤り。区分Aの方がずっと遅れている） |
| 3 | −2.08547 | −1.97719 | 孤立（正しい） |

分割の通し検証で実際に起きていた症状：five_way の肩の日、`side_raise`
（SideDeltのみ、達成率がほぼ0%）が `barbell_row`・`rear_delt_fly` のような
複数区分の種目に負け続け、TRAP_UPPER・CALF・SIDE_DELTが約54%に張り付いて
いた（`TestSimulation_SplitWeeklyTargetIsAttainable`）。指数を3に直すと
upper_lower・ppl は全頻度で緑になり、five_way も週4回以降が緑になった
（週2・3回は構造的な理由が別に残っている。PR 本文）。回帰検査は
`TestAccessoryAllocator_CubedLossFavorsTheMostBehindRegion`。

## 割り振りの手順

### 候補の組（回 k, 種目 e）の条件

1. **予算**：回 k に空き枠がある。同じ回に同じ種目は入れない
2. **分割**：e の主働（寄与1.0以上）の区分がすべて、回 k の区分か、どの日にも属さない区分に入っている。分割が無ければ全区分を許す
3. **回復**：e の主働の区分を、回 k の**前後** `recoveryDays` 以内に、**主働として**
   刺激していない。刺激源の側も寄与1.0以上（候補側の主働の閾値と同じ）だけを
   数える。実際の記録・予測した軸とバリエーション・割り振り済みの補助のいずれも、
   主働かどうかで判定する。副次の寄与まで刺激源に数えると、隣接する日の候補が
   互いを締め出す（PR 3 で見つかった。次の段落）。割り振りは日付順に進まないので、
   前だけ見ると後ろの回の割り振りが条件を破る
4. **除外**：いまと同じ（宣言種目、重点種目の系統、プールに無い種目）

**刺激源も主働だけに絞る理由（PR 3 で見つかった、最初の版の誤り）。**
最初の版は「候補の主働」だけ主働で縛り、刺激源の側は寄与のレベルを
問わず「触れていれば回復中」としていた（`AccessorySelector.recovering`
から引き継いだ規則）。これが非対称で、隣接する日の候補どうしを
相互に締め出す症状を生んだ。5分割の「背中」「肩」は隣接日で、
バーベルロウ（僧帽筋中部が主働1.0、後部三角筋が副次0.4）が背中の日に
選ばれると、副次の後部三角筋まで刺激源に数えたことで肩の日の後部三角筋が
「回復中」になり、リアデルトフライ（後部三角筋が主働1.0、僧帽筋中部が
副次0.3）を締め出す。逆にリアデルトフライが肩の日に選ばれると、副次の
僧帽筋中部が背中の日を締め出してバーベルロウ・シーテッドロウを締め出す。
どちらが先に選ばれても、もう一方が翌日以降ずっと出られなくなる。
通し検証で REAR_DELT・TRAP_MID の未達として実際に出た
（`TestSimulation_SplitWeeklyTargetIsAttainable`）。刺激源も主働
（候補側と同じ寄与1.0以上）だけに絞ると、この相互ブロックは起きない。
回帰検査は `TestAccessoryAllocator_RecoverySourceCountsOnlyPrimaryMovers`。

### 1手

```
1. 全候補の組について ΔL（足したときの損失の変化）を出す
2. 最良の ΔL* ≥ 0 なら止める
3. ΔL ≤ β × ΔL* の組を「ほぼ同じ」として残す（0 < β < 1。減り幅が最良の β 倍以上）
4. 次の順で1つに絞る
   a. 最終実施日が一番古い種目（未実施が最優先。予測の中で先の回に割り振ったものは
      その日にやったとして数える）
   b. 空き枠が一番多い回
   c. 日付が早い回
   d. 種目 ID の昇順
5. 確定して1へ
```

損失が減らなくなるか、候補が尽きたら止まる。**枠が残っていても止まる**
（1回の量は上限であってノルマではない）。

**「最初の下半身の日が使い切る」が起きない理由。**1回の予算（#175）が1回に入る量の
上限になっている（旧来は9種目の固定枠だった）。同じくらい効く組なら空き枠の多い回が
選ばれるので、不足は同じ区分が出る回どうしで分け合う。

**受け入れた挙動：対称な区分は今日だけ見ると偏ることがある（PR 3）。**
2つの区分の週目標・候補数・現在の達成率が完全に対称だと、ΔL がどちらも
一致し続け、手順4b（空き枠が一番多い回）が空き枠差を追いかけて一方の
区分を回0に、もう一方を回1以降に振り分けることがある（同じ回に同じ
種目は入れないので、対称な2区分はどちらも「未実施」のまま手順4a では
決着しない）。1週間全体で見れば両区分とも均等に埋まるが、**今日
（回0）だけを切り出すと、たまたま片方に偏って見える。**

採らなかったものに書いたとおり「直近の種目に罰を足して多様性を出す」は
損失の最小化と競合するため入れない。**今日だけを見て公平にする追加規則も
同じ理由で入れない。**毎日作り直す設計（「先の回の日付」の決定）なので、
翌日には対称性が崩れて（今日どちらかが実施済みになるので）解消する。
実際、通し検証（分割）の全身法版
`TestSimulation_WeeklyTargetIsAttainableAtEveryFrequency` は
この偏りの影響を受けず、全頻度で帯（60〜145%）に収まる。

### 調整する値

| 値 | 意味 | 決め方 |
|---|---|---|
| α | 超過の重み | 通し検証で測る。1/4 から始める |
| β | 「ほぼ同じ」の幅 | 通し検証で測る。0.9 から始める |

どちらも定数。利用者の設定にしない。

PR 3 で α∈{1/8,1/4,1/2}×β∈{0.8,0.9,0.95} の9通りを2回測った。1回目は
損失の T 重み付け・回復の主働限定を反映したあと（指数はまだ2）で
α=1/8・β=0.8 を選んだが、指数を3に直したあと測り直したところ
α=1/4・β=0.9（設計書の初期値）が最良になった。いまの実装はこの値。
測定結果と、残った分割の達成率の未達（僧帽筋上部・カーフなど、候補が
1種目しかなく軸の副次寄与も無い区分）は PR 本文にある。

## 既知の難所

**履歴を仮に進める。**軸を決める関数（`axis`、`variationLift`、`focusCyclePosition` など）は
`History` を受け取るが、仮の記録には重量・回数が要る。軸の決定に要るのは最終実施日と
出席回数だけなので、次のどちらかにする（予測器の PR で決める）。

- 仮の記録を組み立てて `History` に足す
- 軸を決める関数を「最終実施日の辞書と出席回数」を受け取る形に割る

## 受け入れない構成

**5分割を週1回で回す。**1区分が5週に1回しか来ないので、どの解き方でも4週の窓で届かない。
通し検証の達成率の帯から外し、対象外であることを検査に書く（帯を広げて緑にしない）。

**5分割を週4回未満で回す（PR 3 で見つかった。別PRで対応）。**5分割（five_way）の
各日が持つ区分の週目標合計に対して、その日に4週間で配れる枠容量
（種目数×セット数×出現回数）の比を測ると

| 日 | 胸 | 背中 | 肩 | 腕 | 脚 |
|---|---|---|---|---|---|
| 枠容量÷週目標合計 | 0.88 | 0.52 | 1.04 | 0.63 | 0.37 |

背中・腕・脚は、その日の枠を100%の効率で使い切っても目標に届かない
（脚は37%しか配れない）。頻度によらず比は変わらないので（1回あたりの
出現回数も枠も同じ比率で増減する）、**週2〜3回に限らず、5分割そのものが
この3日について構造的に容量不足**。実測では頻度4回以上になると帯（60〜
145%）に収まる（1回あたりの出現回数が増えて絶対量が足りるようになる
ため）。これは「割り振り方」の問題ではなく「配れる量」の問題なので、
割り振り器の側（損失・タイブレーク・回復条件）をどう変えても解けない。
通し検証は週2・3回をこの区分から外した（`TestSimulation_SplitWeeklyTargetIsAttainable`。
帯を広げて緑にしない）。5分割を選べる頻度の下限を4回にする対応は、
この PR では行わず別PRで扱う。
