# 自分の種目（ジムにある器具を自分で足す）

**日付**：2026-09-26

種目マスタは全員共通でバイナリに同梱している（README「種目マスタだけは常に
バイナリ同梱」）。そこに、**利用者ごとの種目**を画面から足し、消せるようにする。

## なぜ要るか

ジムにある器具は人によって違う。Hammer Strength のアイソラテラル系のように、
置いてあるジムが限られるマシンを共通の一覧に入れると、他の人の一覧にも出る。
入れなければ、その器具でやった記録はつけられない。どちらにしても、器具が
1つ増えるたびにコードの変更が要る。

**アプリの外に追い出さない**（CLAUDE.md）。「この器具は無いので、記録は
つけずにやってください」は、答えるべき問いから逃げている。

## 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 誰の種目か | 利用者ごと。共通の一覧はそのまま残し、各人の種目を足す | ジム固有の器具を他人の一覧に出さない |
| 効き方の入れ方 | 「主に効く」「少し効く」の部位を21区分から選ぶ。寄与は1.0と0.5に固定 | 計画は刺激プロファイルだけを見て補助を選ぶので、効き方が無いと計画に出ない。数値を入れさせると、本人に答えられない問いが増える |
| 主に効く部位 | 1つ以上を必須にする | 寄与1.0の区分が無い種目は、分割のどの日にも入らない（`split_lane.go` の `isPrimaryIn`） |
| 部位の数 | 主と少しを合わせて8区分まで。同じ区分を両方には入れられない | `NewStimulusProfile` の上限と同じ |
| 刻み | 入力する。初期値は2.5kg | プレート式マシンとケーブルスタックで違う。共通の種目と同じく `Increment` で検証する |
| 自重・派生 | 持たない（`BodyweightFactor` は0、`DerivedFrom` は空） | ジムの器具はほぼ自重種目ではない。必要になってから足す |
| 名前の重複 | 共通の種目、自分のまだ消していない種目と同じ名前は弾く | 一覧で見分けられなくなる。二度押しで同じ種目が2つできるのも、ここで止まる |
| 足したとき | 「使う種目」に自動で入る | 足すのは使うため。チェックを入れ直す手間を残さない |
| 編集 | 作らない。間違えたら消して足し直す | 依頼は追加と削除。必要になってから足す |
| 消すとき | 論理削除（`deleted_at`）。一覧と計画から消え、記録と履歴の名前は残る | 記録は種目IDで種目を指しており、物理削除すると履歴から名前が消える |
| 消すと「使う種目」は | 外れる | 計画は選ばれた種目しか見ないので、外せば計画には一切出てこない |
| 伸ばしたい種目に入っている種目 | 消せない。先に伸ばしたい種目から外してもらう | 伸ばしたい種目が0個になりうる。黙って外すと軸の顔ぶれが変わって気づけない（`WithSelected` が黙って宣言を削らないのと同じ） |
| 共通の種目 | 消せない。外すなら今どおりチェックを外す | 依頼は「自分のジムの器具を足す」。共通の一覧を削る機能は求められていない |
| 週目標 | 共通の一覧だけから計算する。自分の種目は入れない | 週目標は種目カタログの性質として固定している（`averageStimulusPerSet` のコメント）。足した種目で週目標が動くと、達成率の読み方がずれる |
| 自分の種目を入れたときの計画 | 開発用シミュレーションに自分の種目を渡せるようにし、そこで確かめる（PR 4） | 下の「自分の種目が計画をどう動かすか」 |
| 消した種目の記録 | 受け付ける | 古い画面から記録したときに、やったセットを失わせない。計画の残差にも数える（実際にやった刺激なので） |

### 採らなかったもの

- **近い種目を1つ選んで効き方を引き継ぐ。**決めることは少ないが、近い種目が無い器具を表せない。部位を選ぶほうを本人が選んだ
- **寄与を数値で入れさせる。**1.0と0.5の違いを本人は答えられない
- **自分の種目を別の集約・別の取得口にする。**種目を使う約8箇所それぞれで2つの一覧を合わせることになり、1箇所合わせ忘れるとその画面にだけ種目が出ない
- **`Program` の中に jsonb で持つ。**設定と種目の定義が混ざり、消した種目の名前を置く場所に困る
- **消したら記録ごと消す／記録があれば消せない。**本人が論理削除を選んだ

### 自分の種目が計画をどう動かすか

`TestSimulation` も開発用シミュレーションも共通の一覧だけで回るので、
「自分の種目が計画に漏れない」ことは確かめられても、**自分の種目を入れた
利用者の計画が妥当か**は何も見ていない。確かめたいことが2つある。

- **副次を0.5に固定すると、共通の種目より1セットの刺激が大きくなる。**
  アイソラテラル・ロー（主1＋副3×0.5＝2.5）は、シーテッドロウ（1.9）や
  ラットプルダウン（1.6）より大きい。損失を最小にする割り振りでは、
  自分の種目が選ばれやすくなるかもしれない（まだ仮説）
- **広背筋が主の種目が一度に5つ増える。**背中の日の候補が偏るかもしれない

開発用シミュレーションは全部の設定を画面とURLから変えられる前提なので、
自分の種目もそこから渡せるようにする（PR 4）。偏りが出たら、そのとき
寄与の固定値か割り振りを見直す。先に見直しはしない。

## 構造

### 種目の取得口を利用者ごとにする

```go
// exercise パッケージ
type Reader interface {
	FindAll(ctx context.Context, user account.UserID) ([]*Exercise, error)
}
type Writer interface {
	Save(ctx context.Context, user account.UserID, e *Exercise) error
}
```

`FindAll` は「共通の一覧＋その人の種目（消したものを含む）」を返す。
**合わせる場所は取得口の1箇所だけ**にして、使う側は今までどおり1つの
スライスを受け取る。使う側の変更は、引数に `user` を足すことだけになる。

`program.Reader` など他の取得口がすでに所有者を引数で受けている。それと
同じ形にする。

消したものを返すのは、名前を引く側（履歴・推移・画面の `nameOf`）が
消した種目の記録にも名前を出すため。計画は `Program.Includes` で選ばれた
種目だけを使うので、消した種目は「使う種目」から外れた時点で計画に出ない。
**計画の導出には手を入れない。**

（main の `session_planner.go` で確かめた。補助の候補は「マスタ全件から
選ばれていないものを除いた」もの、軸とバリエーションは `usablePool` の中から
選ばれる。マスタ全件は記録から刺激を数える辞書にしか使われない。）

### `Exercise` に足すもの

- `custom bool`：その人が足した種目か。共通の種目を消させない判定に使う
- `deleted bool`：消したか
- `NewCustomExercise(id, name, primary, secondary []MuscleRegion, incrementKg)`：
  「主は1.0・少しは0.5」「主は1つ以上」「主と少しは重ならない」をここで守る。
  1.0と0.5の対応をドメインに置き、画面やユースケースに散らさない
- `Delete() *Exercise`：消した状態の新しい値を返す

### ID

サーバーが採番する。形は `u-` ＋ランダム（16進16文字）。共通の種目のIDは
英小文字と `_` だけなので衝突しない。これはシードのテストで守る
（シードのIDは `u-` で始まらない）。

記録のIDのようにクライアントで採番しないのは、種目を足すのは設定画面で、
圏外で足す必要が無いから。二度押しは名前の重複チェックで止まる。

### DB

```sql
CREATE TABLE custom_exercises (
  user_id      uuid        NOT NULL,
  id           text        NOT NULL,
  name         text        NOT NULL,
  primary_regions   jsonb NOT NULL,  -- ["LAT"]
  secondary_regions jsonb NOT NULL,  -- ["TRAP_MID", "BICEPS"]
  increment_kg numeric     NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  deleted_at   timestamptz,
  PRIMARY KEY (user_id, id)
);
CREATE UNIQUE INDEX custom_exercises_alive_name
  ON custom_exercises (user_id, name) WHERE deleted_at IS NULL;
```

寄与の数値ではなく「主に効く・少し効く」の区分を保存する。読み出しのたびに
`NewCustomExercise` を通すので、1.0と0.5の対応がドメインの外に漏れない。
後で固定値を見直しても、保存済みの種目は新しい値で読まれる。

`user_id` に外部キーを張らないのは `set_logs` などと同じ（利用者の表が無く、
`accounts` の `user_id` は一意でない。0008 のコメント）。
名前の一意は、アプリで弾いたうえで索引でも守る。共通の種目との重複は
DB では見られないので、アプリだけで見る。

インメモリ実装も同じことをする（シード＋利用者ごとの map）。

### ユースケース

**足す**（`AddCustomExercise`）
1. 入力から `NewCustomExercise` を作る（不正なら 400）
2. 取得口の一覧で、消していない種目に同じ名前があれば弾く（409）
3. `Writer.Save`
4. `Program.WithSelected(今の選択＋新しいID)` を保存する

3と4の間で落ちたら、種目はあるが選ばれていない状態になる。設定画面で
チェックを入れれば済むので、トランザクションは張らない。

**消す**（`DeleteCustomExercise`）
1. 一覧から探す。無い、または共通の種目なら 404（他人の種目は一覧に
   無いので、ここで 404 になる）
2. 伸ばしたい種目に入っていれば弾く（409）
3. `Program.WithSelected(今の選択−そのID)` を保存する
4. `Writer.Save(e.Delete())`

**プログラムを先に、種目を後に書く。**逆順で3の前に落ちると、消した種目が
「使う種目」に残る。そうなると `verifySelection` が消した種目を弾くので、
次に選択を保存しようとして失敗し続ける。この順なら、途中で落ちても
「チェックが外れただけ」で、もう一度消せば終わる。すでに消した種目を
消しても成功にする（冪等）。

**使う種目を保存する**（`verifySelection`）：消した種目を選ぼうとしたら
弾く。

### エラー

| 状況 | 分類 | HTTP |
|---|---|---|
| 入力が不正（主なし・重なり・名前が空や長すぎる・刻みが範囲外） | `ErrInvalidInput` | 400 |
| 名前が重複 | `ErrDuplicateName`（新設） | 409 |
| 種目が無い・共通の種目・他人の種目 | `ErrExerciseNotFound`（新設） | 404 |
| 伸ばしたい種目に入っている | `ErrStillDeclared`（新設） | 409 |

既存の `ErrNotFound` と `ErrConflict` は文言が「プログラムが未設定」
「記録が衝突」なので流用しない。

### API

| メソッド | パス | 本文・応答 |
|---|---|---|
| `GET` | `/api/exercises` | 今までの項目に `custom`・`deleted` を足す。消したものも返す |
| `POST` | `/api/exercises` | `{name, primary: [区分], secondary: [区分], increment_kg}` → 作った種目 |
| `DELETE` | `/api/exercises/{id}` | 204 |

### 画面

設定の「種目」節で行う。

- 部位ごとのチップ一覧に、自分の種目も混ぜて出す（部位は刺激から導く
  `parts.ts` のまま）。消した種目は出さない
- 自分の種目のチップには、見分けがつく印と「消す」をつける
- 節の末尾に「種目を足す」。名前・主に効く部位・少し効く部位・刻みを入れる
- 入力の検査（主が1つ以上、重なり、8区分まで）は純粋関数の `.ts` に置き、
  テストする（画面のコードは3層に割る）

## PR の分け方

1. **共通の一覧に2種目を足す**（#211。この設計とは独立）
   - ダンベルショルダープレスとケーブルサイドレイズ
   - ケーブルサイドレイズで平均寄与が下がり、通し検証が帯の粒度で落ちたので、
     先に #210 で帯を「補助1本ぶんより細かいずれは問わない」に直した
2. **ドメイン・DB・API**：`Exercise` の `custom`/`deleted`、取得口の利用者化、
   `custom_exercises`、足す／消すのユースケースと API
   - README の「種目マスタだけは常にバイナリ同梱で、DB には置かない」と、
     `exercise_repository.go` の「書き手が居ないので Writer は無い」が
     事実でなくなるので書き直す
3. **画面**：設定の「種目を足す」と「消す」
4. **開発用シミュレーション**：自分の種目を渡せるようにする。アイソラテラル
   9種目を入れた状態で、補助の割り振りが偏らないか見る

2は、取得口に `user` を足す機械的な変更と、足す／消すの動作を分けられるなら
分ける（動作の変更と機械的な移動は混ぜない）。

## 検収

- **ドメイン**：`NewCustomExercise` が主なし・重なり・9区分以上を弾くこと、
  主が1.0・少しが0.5になること
- **取得口**：他人の種目が見えないこと。消した種目も返ること
- **足す**：共通の種目と同名・自分の消していない種目と同名を弾くこと、
  自分の消した種目と同名は通ること、足すと使う種目に入ること
- **消す**：共通の種目・他人の種目は 404、伸ばしたい種目は 409、消すと
  使う種目から外れること、二度消しても成功すること、消したあとも履歴に
  名前が出ること
- **選択**：消した種目は選べないこと
- **計画**：PR 2 で `TestSimulation` の数字が動かないこと
  （動いたら、自分の種目が週目標か計画に漏れている）。
  `TestSessionPlanner_PlanIsFixedForTheWholeDay` が緑のまま
- **DB**：旧版で DB を作ってから新版のマイグレーションを当てる
- **画面**：`web/scripts/*-check.mjs` を回す

どれも変異を入れて赤くなることを確かめる（writing-tests）。
