# 種目の管理（その人の種目一覧を足す・直す・消す）

**日付**：2026-09-26（改訂 2026-09-27）

種目は**利用者ごとの一覧**として持つ。アプリ同梱のプリセットは、その一覧の
**初期値**でしかない。プリセット由来の種目も、本人が足した種目も同じデータで、
同じように直せて、消せる。

## なぜ要るか

ジムにある器具は人によって違う（Hammer Strength のアイソラテラル系など）。
逆に、プリセットにあってもジムに無い器具や、やらない種目もある。名前の呼び方も
ジムや人で違い、効き方の感じ方も違う。

**アプリの外に追い出さない**（CLAUDE.md）。「一覧に無い器具は記録できない」
「要らない種目が一覧に居座る」は、答えるべき問いから逃げている。

## 改訂の経緯（2026-09-27）

最初の設計（PR #220・#221 の初版）は「共通の種目はバイナリ同梱で全員共通、
本人が足した種目だけを別に持つ」だった。本人の要望で次のように変えた。

- 種目管理は設定の中ではなく**別ページ**にする
- **プリセットと自分の種目を同じデータとして扱い、プリセットも消せる**
- **名前と効き方を直せる**

初版は #219〜#221 としてマージされ本番に出ている（0013 の `custom_exercises` が当たっている）。
0013 は書き換えず、0014 で `user_exercises` を足し、旧版の行は初回の読み出しで取り込む。

## 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 誰の種目か | 利用者ごと。プリセットは初期値としてコピーし、以後は本人のもの | 本人が選んだ（アプリ側でプリセットを足しても、既存の利用者には届かない。届けるならデータ移行） |
| いつコピーするか | 種目一覧を読んだとき、その人の行が1件も無ければプリセットを入れる | 新規・既存の利用者を1つの経路で揃える。SQL のマイグレーションはシード（Go）を読めない |
| ID | プリセット由来はそのまま（`bench` など）、足した種目は `u-`＋16進16文字 | 記録・使う種目・伸ばしたい種目は ID で指す。プリセットの ID を保てば既存のデータがそのまま通る |
| 直せるもの | 名前、効き方（区分ごとの寄与）、刻み | 依頼どおり |
| 直せないもの | 自重係数、派生元（バリエーションの親） | プリセットからコピーしたまま保つ。画面で答えさせる問いではない。必要になってから |
| 効き方の入れ方 | 部位のチップを押すと 主（1.0）→ 少し（0.5）→ 外す と回り、選んだ部位は数値（0.1〜1.0）でも直せる。足すときも直すときも同じ | 本人が選んだ（数値も入れられる）。プリセットの 0.7 や 0.4 を表せる。よく使う2値はチップで決まる |
| 効き方の制約 | 寄与1.0の区分が1つ以上、合わせて8区分まで、各区分 0.1〜1.0 | 寄与1.0の区分が無い種目は分割のどの日にも入らない（`split_lane.go` の `isPrimaryIn`）。プリセット38種目はすべて満たしているので、全種目に共通の規則として `NewExercise` に置く |
| 名前 | 前後の空白を落として1〜40文字。消していない種目の中で重複しない | 一覧で見分けられなくなる。二度押しで同じ種目が2つできるのもここで止まる |
| 足したとき | 使う種目に入る | 足すのは使うため |
| 消すとき | 論理削除。一覧・使う種目から消え、記録と履歴の名前は残る。プリセット由来も消せる | 記録は ID で種目を指している |
| 伸ばしたい種目に入っている種目 | 消せない（409）。先に外してもらう | 伸ばしたい種目が0個になりうる。黙って外すと軸の顔ぶれが変わって気づけない |
| 使う種目のチェック | 残す。「消す」はもう使わない、「チェックを外す」は一時的に外す | 本人が選んだ |
| 効き方を直したときの過去の記録 | 新しい効き方で数え直す | 記録ごとに当時の効き方を持たせる仕組みは、必要になってから |
| 週目標 | 種目の一覧からは計算しない。頻度と1回の量だけで決まる（2026-10-02 改訂。当初はプリセット全種目の平均から計算していた） | 目標の大きさがプリセットの構成で動くと、プリセットを足すだけで全員の目標が動く。本人の編集で目標が動くと達成率の読み方がずれる、も同じ理由 |
| 消した種目の記録 | 受け付ける | 古い画面から記録したときに、やったセットを失わせない |

### 採らなかったもの

- **プリセットは同梱のまま、本人の変更（消した・直した）だけを上書きとして持つ。**
  アプリで種目を足せば全員に届く利点があるが、本人がコピー方式を選んだ
- **新しいプリセットを本人に確認してから入れる。**同上
- **「使う種目」のチェックを「消す」に一本化する。**本人が両方残すことを選んだ
- **効き方は主／少しの2値だけ。**プリセットの細かい値を直すと潰れる。本人が数値入力を選んだ
- **部位（胸・背中…）を種目の項目として持つ。**計画が見るのは区分ごとの寄与だけで、
  部位の項目を別に持つと寄与と食い違ったときにどちらが正しいか決められない。画面の
  見出しは寄与の一番大きい区分から導く（`web/src/domain/parts.ts`）

## 構造

### 種目の取得口

```go
type Reader interface {
	FindAll(ctx context.Context, user account.UserID) ([]*Exercise, error)
}
type Writer interface {
	Save(ctx context.Context, user account.UserID, e *Exercise) error
}
```

`FindAll` はその人の種目（消したものを含む）を返す。**その人の行が1件も無ければ、
先にプリセットを入れてから返す。**入れるのは「無ければ入れる」（Postgres は
`ON CONFLICT DO NOTHING`）で、同時に読まれても二重にならない。

消したものも返すのは、名前を引く側（履歴・推移・画面）が消した種目の記録にも名前を
出すため。計画は `Program.Includes` で選ばれた種目だけを使うので、消した種目は
「使う種目」から外れた時点で計画に出ない。**計画の導出には手を入れない。**

### `Exercise`

- `NewExercise` に「寄与1.0の区分が1つ以上」と「名前は40文字まで」を足す
- `custom` は持たない（プリセット由来かどうかで扱いを変えない）
- `deleted` と `Delete()` は残す
- 直した値を返すメソッドを1つにまとめ、`Edit(ExerciseEdit{Name, Stimulus, IncrementKg}) (*Exercise, error)`
  とする。自重係数と派生元は元のまま引き継ぐ

### DB

```sql
CREATE TABLE user_exercises (
  user_id           uuid        NOT NULL,
  id                text        NOT NULL,
  name              text        NOT NULL,
  stimulus          jsonb       NOT NULL,  -- {"QUAD": 1.0, "GLUTE": 0.7}
  increment_kg      numeric     NOT NULL,
  bodyweight_factor numeric     NOT NULL DEFAULT 0,
  derived_from      text,
  created_at        timestamptz NOT NULL DEFAULT now(),
  deleted_at        timestamptz,
  PRIMARY KEY (user_id, id)
);
CREATE UNIQUE INDEX user_exercises_alive_name
  ON user_exercises (user_id, name) WHERE deleted_at IS NULL;
```

0014 として足す。**0013（`custom_exercises`）は初版とともに本番へ出た**ので書き換えない。
旧版で足した種目は、その人の行が0件のとき（プリセットをコピーするのと同じ
トランザクション）に取り込む。主は1.0、少しは0.5の寄与に直し、消した印と足した
時刻も引き継ぐ。`custom_exercises` は全員が取り込み終えたことを確かめてから、別の
マイグレーションで消す。読み出しのたびに `NewExercise` を通す（保存済みの値も検証する）。

### ユースケース

- **足す**（`AddExercise`）：ID を採番 → `NewExercise` → 名前の重複を見る → 保存 → 使う種目に入れる
- **直す**（`EditExercise`）：一覧から探す（無い・消した種目は 404）→ `Edit` → 名前の重複を見る（自分自身は除く）→ 保存
- **消す**（`DeleteExercise`）：一覧から探す（無ければ 404）→ 伸ばしたい種目なら 409 → **使う種目から外す（プログラムを先に保存）→ 論理削除**。途中で落ちても「消したのに選ばれている」を残さない

### API

| メソッド | パス | 本文・応答 |
|---|---|---|
| `GET` | `/api/exercises` | `{id, name, increment_kg, stimulus, deleted}`。消したものも返す |
| `POST` | `/api/exercises` | `{name, stimulus: {区分: 寄与}, increment_kg}` → 201、作った種目 |
| `PUT` | `/api/exercises/{id}` | 同じ本文 → 200、直した種目 |
| `DELETE` | `/api/exercises/{id}` | 204 |

エラー：入力不正は 400、名前の重複は 409（`DUPLICATE_NAME`）、無い種目は 404
（`EXERCISE_NOT_FOUND`）、伸ばしたい種目は 409（`STILL_DECLARED`）。

### 画面

- 新しいページ「種目」。設定の「種目」の節から入る
- 部位ごとの見出しの下に、種目を1行ずつ並べる。各行に名前・効き方の要約
  （例：`大腿四頭筋 1.0・臀筋 0.7・…`）・「直す」「消す」
- 先頭に「種目を足す」。足す・直すは同じ編集フォーム（名前・効き方・刻み）
- 使う種目・伸ばしたい種目・重点種目の選択は設定に残す
- 判断（送れるか・本文・消せるか・要約）は純粋関数の `.ts` に置く（3層）

## 足した種目が計画をどう動かすか

### 確かめること

開発用シミュレーションで、アイソラテラル9種目を入れた状態の割り振りを見る
（PR 4）。開発用シミュレーションは全部の設定を画面と URL から変えられる前提なので、
種目の追加も `custom=` で渡す。

### 確かめた結果（初版で測定）

アイソラテラル9種目（付録の効き方）を渡し、分割（なし・上下・PPL）×頻度
（週3〜5回）を12週・実力一定（growth=0）で回した。

- **足した種目全体には偏らない。**補助の枠に占める割合は15〜20%で、一覧に
  占める割合（47種目中9種目＝19%）とほぼ同じ
- **1セットの刺激の合計が大きい種目に集中する。**広背筋が主の7種目では、
  ハイ・ロー（主1＋少し3＝2.5）が12週で6〜14回を取り、ロー・ロー、ワイド・
  プルダウン、DY・ロー、フロント・プルダウン（合計1.5〜2.0）は0〜2回
- **足した種目に固有の性質ではない。**プリセットだけでも、バーベルロウ（2.4）が
  シーテッドロウ（1.9）をほぼ締め出している

決めたとおり、ここでは見直さない（#223）。

## 改訂（2026-10-01）：消さずに、使う・使わないで決める

**種目は消せなくなった。**使わない種目は「使う種目」から外して非表示にする。
効き方（寄与の数値）を正しく入れるのは難しいので、足す・直すは最終手段にして、
プリセットを網羅してそこから選ぶ形へ寄せていく（本人の方針）。

| 論点 | 決定 | 理由 |
|---|---|---|
| 表示/非表示のデータ | 既存の `selected_exercises`（使う種目）をそのまま使う。別のフラグは持たない | 判断が2つに増えると、消したかった「決めること」が戻る |
| 非表示の種目 | 計画に出ない。「種目を選んで記録」にも出ない。記録と履歴は残る | 使わない種目が一覧に居座らない |
| どこで入れ替えるか | 種目ページ（使う／使わない・効き方の調整・足す）。設定のトップからは外した | 使わない種目が設定のトップに並ぶのを避ける |
| 伸ばしたい種目 | 使わないにできない（先に伸ばしたい種目から外す） | 従来どおり |
| API | `DELETE /api/exercises/{id}` を削除（405）。入れ替えは `PUT /api/program/selected` | 新しい口は作らない |
| 新規の利用者の既定 | 使う種目は `seed.DefaultSelected()` の20種目だけ（BIG3＋補助。シュラッグ・ナローベンチは入れない）。カタログの残りは非表示で始まる。既存の利用者の設定は変わらない | 全部を使う状態で始めると使わない種目が並び、プリセットを足すたびに新規の計画が動く。減らしすぎると、five_way で0セットの日が出て周期が止まる（11種目では33日）ので、全構成で帯の外と空の日が0になる最小の組を、貪欲に足して決めた（`TestDefaultSelected_PlansEveryShippedSetup`） |
| 消した行 | 0015 で、消していない同名が無い行を非表示として戻す | 戻す口が無いまま見えなくならないように |

`deleted_at` 列と `Exercise.IsDeleted` はまだ残っている（消せる口が無いので、
0015 のあとは新しく付かない）。取り除くのは別の PR。

上の決定表の「消すとき」「伸ばしたい種目に入っている種目」「使う種目のチェック」の行、
`DELETE /api/exercises/{id}` の行、「消す」の画面の記述、`DeleteExercise` は、この改訂で置き換わった。
