# 初回の案内（オンボーディング）

## 目的

初めてログインした人が、**通い方を自分のものにしてから**「今日」の画面に入り、
**最初の1セットを迷わず記録できる**ようにする。

いまは初回ログインで既定のプログラム（週3回・4種目×3セット・全身法・伸ばしたい
種目はBIG3）が入り、そのまま「今日」に着地する。通い方は歯車の奥にあり、
推定1RMが無いので全カードが「自分で決める」と出る。何を押せば記録になるかの
説明もない。

## 誰が何を答えるか

CLAUDE.md の表に照らす。

- **週に通う回数・1回の量**は本人の生活の事実で、アプリには答えられない。聞く
- **分割・伸ばしたい種目**は本人の好みで、既定のまま「次へ」で進めるようにする。
  聞くが、決めなくても進める
- **何kgでやるか**はアプリが答える。ただし初回は記録が無く答えられないので、
  そのことを説明する（「軽めから。記録すれば次から出る」）

## 範囲

やること：

1. サーバーが「初回の案内を済ませたか」を利用者ごとに持つ
2. 済ませていない利用者には「今日」の代わりに設定画面（4段階）を出す
3. 設定を保存したら、同じ流れで「今日」の画面にコーチマークを1回だけ流す

やらないこと：

- 設定画面に「案内をもう一度見る」を置く（必要になってから）
- 曜日の設定（製品に曜日の概念が無い）
- 「今日」の空状態の作り直し

## サーバー

### 保存

```sql
-- 0021_onboarding.sql
CREATE TABLE onboarding (
  user_id      uuid PRIMARY KEY,
  completed_at timestamptz NOT NULL
);
-- 既存の利用者は済んだものとして扱う。program は初回ログインで必ず作られる
INSERT INTO onboarding (user_id, completed_at)
SELECT user_id, now() FROM program;
```

**行が無い＝まだ**。初回ログインで行を作る必要はない。

`program` の列にしない。`Program` は訓練の設定を持つ集約で、画面の進み具合は
訓練の判断に一切効かない。混ぜると、計画の導出を読む人が「この値はどこで効くのか」
を探すことになる。

### ドメイン

`internal/domain/account` に置く。利用者に紐づく状態で、訓練の集約ではない。

```go
// OnboardingReader は初回の案内を済ませたかを読む。
type OnboardingReader interface {
    OnboardingCompleted(ctx context.Context, user UserID) (bool, error)
}

// OnboardingWriter は初回の案内を済ませたことを記録する。何度呼んでも同じ結果になる。
type OnboardingWriter interface {
    CompleteOnboarding(ctx context.Context, user UserID, at time.Time) error
}
```

`CompleteOnboarding` は冪等（`ON CONFLICT DO NOTHING`）。2回目は最初の時刻を保つ。

実装は Postgres とインメモリの両方。

### API

| メソッド | パス                        | 応答                     |
| -------- | --------------------------- | ------------------------ |
| GET      | `/api/onboarding`           | `{"completed": bool}`    |
| PUT      | `/api/onboarding/completed` | 204。本文なし。冪等      |

### 開発用の利用者

インメモリ構成の開発用利用者（`DEV_SESSION_TOKEN`）は**済んだ状態で始める**。
既存の `web/scripts/*-check.mjs` が設定画面に阻まれないようにするため。

`DEV_ONBOARDING_PENDING=1` のときだけ未完了で始める。`DEV_SESSION_TOKEN` と同じく
`DATABASE_URL` があるときは無視する。

## 画面

### 出す条件

`loadAll` で `GET /api/onboarding` も取る。

- `completed: false` → 設定画面を出す。ルートは変えない（`App.tsx` で `today` の
  代わりに描く）。ヘッダーと下のナビは出さない
- 取得に失敗した（オフラインなど）→ **済んだものとして扱う**。案内のためにアプリを
  止めない。次に取れたときに出る
- 初回の読み込み中は今のスケルトンのまま

### 設定画面（4段階）

| 段階 | 聞くこと       | 選び方                                            | 既定        |
| ---- | -------------- | ------------------------------------------------- | ----------- |
| 1    | 週に通う回数   | 1〜7                                              | 3           |
| 2    | 分割           | 全身法＋プリセット。回数に足りないものは出さない | 全身法      |
| 3    | 1回の量        | 種目数2〜6 × セット数2〜6                         | 4 × 3       |
| 4    | 伸ばしたい種目 | 設定画面と同じ選び方（使う種目から選ぶ）          | BIG3        |

- 初期値はサーバーの現在値（`GET /api/program`）。「次へ」を押し続けるだけで終われる
- 「戻る」で前の段階に戻れる。戻っても入力は消えない
- 段階1で回数を下げて、段階2で選んでいた分割が選べなくなったら全身法に戻す
  （`isSplitSelectable` を使う）
- 各段階に1〜2行の説明を付ける。例：段階1「迷ったら、実際に通えている回数に。
  あとで変えられます」

### 保存

**最後の段階で「はじめる」を押したときにまとめて送る。**途中では送らない。
途中で送ると、閉じたときに半端な設定が残り、しかも「済んだ」にはならない。

送る順：

1. 回数と分割（順序は下の規則で決める）
2. 1回の量
3. 伸ばしたい種目
4. `PUT /api/onboarding/completed`

**回数と分割の順序。**サーバーは両方向で検査している（`set_frequency.go`：
今の分割に足りない回数は拒否、`set_split_cycle.go`：今の回数で選べない分割は拒否）。

- 新しい分割の下限 ≤ 今の回数 なら、分割を先に送る
- そうでなければ回数を先に送る

どちらかは必ず通る。両方が通らないとすると、今の下限 m0 ≤ 今の回数 f0 < 新しい
下限 m1 ≤ 新しい回数 f1 < m0 となり矛盾する。新規の利用者は全身法（下限なし）から
始まるので普段は気にならないが、途中で失敗して選び直したときに効く。

**分割と伸ばしたい種目。**こちらも両方向で検査される（`verifyDeclaredHaveADay`）が、プリセットはどれも全区分を日に持つので、選べる組み合わせで落ちることはない。順序は分割→種目で固定する。

**変わっていない項目も送る。**差分だけ送る判断を足しても、失敗時の再送で
「どれが済んだか」を持つ必要が出るだけで得がない。どれも冪等。

**失敗したら。**設定画面に留まり、`describePutFailure` の文言を出す。もう一度
「はじめる」で最初から送り直す。オフラインは設定画面と同じ
「つながらないので変えられません」。

送る順と本文は `onboarding.ts` の純粋関数が決める（下のテストで固定する）。

成功したら `reload()` で計画を取り直し、コーチマークへ進む。

### コーチマーク

「今日」の画面を暗くし、1か所だけ切り抜いて吹き出しで説明する。

| 順 | 指す場所                      | 文言（案）                                                                                   |
| -- | ----------------------------- | -------------------------------------------------------------------------------------------- |
| 1  | 最初のカードの目標（重さ）    | 重さはアプリが決めます。初めての種目は「自分で決める」と出るので、軽めから。記録すれば次から出ます |
| 2  | 最初のカードの「1セット目」   | セットが終わったらここを押して、重さ・回数・RIR（あと何回できたか）を記録します              |
| 3  | 最初の区分の見出し            | 上から順にやって、好きなところでやめて大丈夫です                                             |
| 4  | 「休憩を始める」              | 休憩の時間を計れます。記録すると自動で始まります                                             |
| 5  | 歯車                          | 通い方はここでいつでも変えられます                                                           |

- 指す場所は既存の要素に `data-coach="target|slot|lane|rest|settings"` を付けて探す
- **指す要素が無い段階は飛ばす**（休みの日でカードが無い、など）。全部無ければ出さない
- 吹き出しに「次へ」と「スキップ」。最後は「はじめる」
- 指す要素は `scrollIntoView` で見える位置に寄せてから切り抜く
- `role="dialog"` `aria-modal="true"`、開いたら吹き出しにフォーカスを移す
- 暗い部分を押しても進まない（誤タップで読み飛ばさない）
- **状態はメモリだけ。**再読み込みで消え、二度と出ない。「済んだ」は設定の保存で
  既に記録されている。コーチマークのために保存を足さない

どの段階を出すか（要素の有無から飛ばす・次へ・終わり）は `coach.ts` の純粋関数が
決める。位置の測定と描画は `.tsx`。

### ファイル

```
web/src/features/onboarding/
  onboarding.ts          送る順と本文、段階の進み方、回数変更時の分割の戻し
  onboarding.test.ts
  useOnboarding.ts       現在値の取得、送信、失敗時の文言
  Onboarding.tsx         4段階の描画
  coach.ts               コーチマークの段階の決定
  coach.test.ts
  CoachMarks.tsx         切り抜きと吹き出し
web/scripts/onboarding-check.mjs
```

伸ばしたい種目の選び方は `ProgramSettings.tsx` の部品をそのまま使う。部品として
切り出す必要があれば切り出す（機械的な移動なので別コミットにする）。

## テスト

### Go

- `OnboardingReader/Writer` の契約テストをインメモリと Postgres の両方に当てる
  - 行が無ければ `false`
  - `CompleteOnboarding` のあとは `true`
  - 2回呼んでもエラーにならず、最初の時刻が残る
  - 別の利用者には影響しない
- HTTP：GET が `completed` を返す。PUT のあと GET が `true`。未認証は 401
- マイグレーション：0020 までで `program` に行を入れてから 0021 を当て、その利用者が
  `true` になること。行の無い利用者は `false`
- `seedDevSession`：既定で済み、`DEV_ONBOARDING_PENDING=1` で未完了

### 画面（vitest）

- 回数と分割の順序：下限なし→5分割（回数を先）、5分割→全身法で回数を下げる（分割を先）
- 送る列の最後が必ず `PUT /api/onboarding/completed`
- 回数を下げて分割が選べなくなったら全身法に戻る
- コーチマーク：要素が無い段階を飛ばす、全部無ければ出さない、最後で終わる

変異は `onboarding.ts` の順序の条件を逆にする、`completed` を列から抜く、
`coach.ts` の飛ばしを外す、の3つを入れて赤くなることを確かめる。

### 実画面（`onboarding-check.mjs`）

`DEV_ONBOARDING_PENDING=1` でサーバーを立てて：

1. 設定画面が出て、「今日」が出ていない
2. 回数を5、分割を5分割にして「はじめる」→ `GET /api/program` に反映されている
3. コーチマークが出る。「次へ」で最後まで進み、閉じる
4. 再読み込みで設定画面もコーチマークも出ない

加えて既存の `*-check.mjs` が全部通ること（開発用利用者が済んだ状態で始まることの確認）。
