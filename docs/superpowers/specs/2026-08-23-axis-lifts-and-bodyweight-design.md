# 軸種目の可変化と自重の扱い

## 背景

実際に使ってみて、**「BIG3が軸」という前提が本人の実態と合っていない**ことが2回続けて出た。

1. **ルーマニアンデッドリフト**をハムの種目としてやっており、床引きデッドリフトはほぼやらない。RDLはデッドリフトの「バリエーション」として登録されていて、重量は `床引きの1RM × 0.70` で出る。床引きをやらなければ推定は42日で古くなり、**RDLの重量が永久に「自分で決める」になる**。しかも床引きは毎回メニューに出続けて、毎回飛ばすことになる
2. **背中の日の軸は懸垂**。懸垂は「補助種目」として登録されており、しかも自重（0kg）のセットは推定から除外されるので、**推定するものが何も残らない**

どちらも例外ではなく、モデルの中心にある固定を突いている。`ExerciseKind` が `KindMain` を持ち、それが BIG3 に固定されていることが原因。

あわせて、「今日の画面が使いにくい」という話の出発点もここに繋がっていた。今日のリストは11種目36セットで、本人には**どれから始めるかが決まらない**。軸が置けないと、その日の起点が定まらない。

## 決めたこと

### 1. 軸の枠は筋肉群で固定、中身は選べる

枠は **胸・背中・脚 の3つ**。それぞれに種目マスタから1つ選ぶ。枠の数はユーザーが決めない。「決めなくていい」から遠ざからないため。

軸は `Program` 側の設定にする。種目マスタを書き換えずに、補助として登録済みの懸垂をそのまま軸に置ける。

既定値：

| 枠 | 既定 | 理由 |
|---|---|---|
| 胸 | ベンチプレス | 変更なし |
| 背中 | チンニング | 今の BIG3 には背中の軸が無い。新設なので既定を決める必要がある |
| 脚 | スクワット | 大腿四頭は最大の筋群 |

**デッドリフトは軸から外れる。**軸を外れた種目は補助と同じ扱いになり、**毎回は出ない**。残差から選ばれるので、ハムの枠を `leg_curl` や RDL と奪い合い、日によって入れ替わる。毎回やりたければ脚枠をその種目にする。

**脚が1枠なので、スクワットとRDLの片方は必ず補助に落ちる。**前腿と後腿を別枠にする案（4枠）も検討したが、枠を増やさない方を選んだ。

### 2. 軸に選べる種目の絞り込み

主働区分（`Stimulus` が最大の区分）が、その筋肉群に属する種目だけを候補に出す。

| 筋肉群 | 含む区分 |
|---|---|
| 胸 | `CHEST_UPPER` `CHEST_MID` `CHEST_LOWER` |
| 背中 | `LAT` `TRAP_MID` `TRAP_UPPER` `ERECTOR` |
| 脚 | `QUAD` `HAMSTRING` `GLUTE` `ADDUCTOR` `CALF` |

三角筋・腕・腹の9区分はどの筋肉群にも属さない。軸は大きい筋肉群だけに置き、残りは補助で埋める。

主働が同点の種目は**両方の候補に出る**。デッドリフトは `Hamstring 1.0` と `Erector 1.0` が同点なので、脚と背中の両方に出る。背中の日にデッドリフトを置く人がいるので、これは都合がよい。

軸に指定できるのは `Program.selected` に含まれる種目だけ。

**同じ種目を複数の枠の軸にはできない。**デッドリフトは脚と背中の両方の候補に出るので、両方に設定できてしまう。そうすると同じ種目が1日に2枚出る。バリデーションで弾く。

### 3. 軸に指定された種目は種目選択から外せない

外そうとしたらエラーにする。「軸を先に別の種目に変えてください」という順序を強制する。

外した瞬間に軸を既定へ戻す案はやめた。ユーザーが意図していない軸の入れ替わりが黙って起きるうえ、既定に戻った結果また選択に無い種目が軸になるという循環が起きうる。エラーで止める方が短い。

**この規則があるので、軸の候補が0件になることは起きない。**各枠の軸は必ず選択に含まれており、それ自身が常に候補として残るため。

### 4. 軸の種目は補助の候補から外す

補助の候補は `Kind` で絞っていたが、軸に指定できる種目に制限が無くなるので、**「軸に指定されている3種目を除いた全種目」**が補助の候補になる。

外さないと、チンニングのように補助として登録されている種目を軸にしたとき、**同じ種目が「軸」と「補助」で2枚出る**。

### 5. 自重は「体重 × 係数 + 加重」で扱う

```
負荷 = 体重 × 係数 + 加重
```

種目に `BodyweightFactor`（0.0〜1.0）を持たせる。0 は「自重が乗らない」。

| 種目 | 係数 |
|---|---|
| チンニング (`pull_up`) | 0.95 |
| ディップス (`dip`) | 0.93 |
| バックエクステンション (`back_extension`) | 0.55 |
| 上記以外 | 0 |

**係数は力学的な正確さを狙っていない。**推定1RMは伸びを測るための相対値なので、**時間を通じて一貫していれば足りる**。絶対値がずれても、同じ係数で測り続ける限り推移は正しく出る。

**記録は加重のまま。**`SetLog` に入るのは「プレートを何kg付けたか」。体重を足すのは推定するときだけ。こうしないと「あの日は何kg付けたか」が記録から読めなくなる。

**処方も加重で出す。**

```
表示する加重 = 目標負荷 − 体重 × 係数
```

画面には `+5kg` と出る。体重込みの `82.5kg` と言われても何をすればいいか分からないため。差が0以下なら「自重」と出す。

**引いたあとの数字は刻みに乗らない。**丸めは総負荷に対してかかるので、体重を引くと `82.5 − 71.25 = 11.25kg` のような値が出る。**これは丸めない。**受け取った側が手元のプレートに合わせて調整する。丸め直すと総負荷が目標からずれ、どちらを信じる数字なのかが分からなくなる。

**体重の探し方は推定でも処方でも同じ規則にする。**対象日以前で最も新しい体重を使い、対象日から42日より古ければ使わない。42日は推定1RMが「古すぎる」と判定される既存の値で、新しい定数を増やさない。

処方だけ「当日の体重が必要」にすると、**毎日体重を測らない限り軸がほぼ毎日「自分で決める」になり**、この変更の目的そのものが消える。

体重が42日以内に一つも無い場合は、推定ではそのセットを除外し、処方では「自分で決める」を出す。

**過去のデータが遡って推定に入る。**今まで0kgの自重セットは捨てられていた。係数が入ると、その日の体重が記録されていれば推定できる。推移グラフの過去に点が増える。

### 6. 落とせない種目にデロードを提案しない

過去の自重記録が遡って推定に入ると、**移行直後にチンニングの停滞が8セッションぶん一度に成立し、初回起動でデロードが提案されうる**。

しかも自重種目のデロードは適用できない。目標負荷を10%落とすと体重×係数を下回り、加重が負になって「自重」になるだけで、実質何も変わらない。

**目標負荷が体重×係数を下回る種目は、デロードの提案対象から外す。**落とせないものを提案しても、承認できる操作が無い。

### 7. 推定1RMは種目ごとに持つ。係数換算をやめる

**バリエーションの重量を「メインの1RM × 係数」で出すのをやめる。**各種目が自分の記録から自分の1RMを持つ。

やめる理由：

- `variation_ratio.go` 145行 + テスト460行、**合わせて605行**を要する
- 対象は**バリエーション7種目だけ**
- 実測係数が効くには「同じ日に土台とバリエーションの両方をやる」を3セッション必要とする。それ未満はシードの固定値のままなので、ほとんどの場面で**汎用の定数を掛けているだけ**
- そして背景に書いた RDL の破綻は、**この仕組みがあるから起きていた**

RDLはRDLの記録から出す。それが一番正確で、土台が消える構造そのものが無くなる。

**一度もやったことがない種目の初回は「自分で決める」。**記録が無いので推定できない。初回1回ぶんの手入力と、605行および「係数」という概念を交換する取引。以降は自分の記録で自動になる。推測より記録、というこのアプリの筋にも合う。

### 8. `MainLift` と `ExerciseKind` をやめる

係数を消すと、`MainLift` に残る役目は「バリエーションの日にベンチをラーセンプレスへ差し替える」置換の対応表だけになる。これもやめる。

**バリエーションの日は「同じ軸を軽くやる日」になる。**スロットの役割（強度0.76、4セット、RIR2）はそのまま残り、差し替えだけが無くなる。

やめると得られるもの：

- **バリエーション7種目が補助の候補に入る。**今は `KindVariation` なので補助として選ばれない。RDL・デフィシット・フロントスクワットなどが残差を埋められるようになり、後述する**ハムと脊柱起立筋の供給不足がここで埋まる**
- 軸がどのリフト系統にも属さないとき（チンニングなど）に**何へ差し替えるのかという問いが発生しない**

`ExerciseKind` も道連れに消える。`KindMain` は `mainExercises()` だけが使っており、それが軸参照に置き換わる。`KindVariation` は差し替えのためにあった。残るのは `KindAccessory` だけで、値が1つしかない列挙に意味は無い。

**種目は種目になる。**違いは「軸に選ばれているかどうか」だけで、それは `Program` が持つ。

**スロットの役割 `VARIATION` は名前を `LIGHT` に変える。**差し替えが無くなるので、バリエーションを指す名前が実態と合わなくなる。強度・セット数・RIR の値は変えない。

**バリエーション7種目を種目選択に入れる必要がある。**今は `usablePool` が `Kind() == KindVariation` を見て「選択されていなくても使う」という抜け道を持っている。`Kind` を消すとこの抜け道が無くなるので、**明示的に選択されていない限り出てこなくなる**。移行で選択に追加しないと、供給を広げるどころか7種目が消える。設定画面の種目一覧にも出す（今は「バリエーションはメインに付随して自動で回るので、ここには出ません」と書いてある注記を消す）。

## 週目標を測り直す

シードの週目標には `「厚くしたい区分」ではなく「その頻度で実際に供給できる量」を置いている。数字は通し検証（simulation_test.go）で実測して決めた` と書いてある。**この実測は BIG3 が毎回出る前提で取られている。**軸を入れ替えると供給が変わるので、数字が合わなくなる。

週3回・既定の軸で計算すると：

| 区分 | 週目標 | 変化 | 結果 |
|---|---|---|---|
| 広背 | 12 | **+12**（チンニング4セット×3回） | 軸だけで満杯になり、ラットプルダウン・ロウ類の残差が0になる |
| ハム | 14 | **−12**（デッドリフトが軸から外れる） | 補助で埋める必要がある |
| 脊柱起立筋 | 18 | **−12** | 同上 |
| 臀筋 | 18 | −9.6 | 同上 |

やることは3つ。

**(a) 既定の軸構成でシミュレーションを回し、`baseProfile` を取り直す。**元の数字を決めたときと同じ作業をもう一度行う。到達できない区分とセッション長を見て調整する。

**(b) `TestSimulation_EveryAccessoryGetsUsedInSomeSetup` の粒度を変える。**今は単一の構成で「全補助種目が使われる」を見ている。軸が可変になったら**代表的な軸構成をいくつか**回して「どこかの構成で使われればOK」にする。ラットプルダウンは軸がチンニングだと出ないが、軸をバーベルロウにすれば出る。それで足りる。

**(c) 供給の幅は §8 で広がる。**バリエーション7種目が補助の候補に入るので、ハム（`leg_curl` / RDL / デッドリフト）と脊柱起立筋（`back_extension` / デッドリフト / RDL）の供給元が増える。(a) の調整幅はこれで小さくなる見込み。

## モデルの変更

### 追加

- `MuscleGroup`（`CHEST` / `BACK` / `LEG`）— 軸の枠を表す新しい列挙。各グループが含む `MuscleRegion` の対応表を持つ
- `Program.axes map[MuscleGroup]ExerciseID` — 3枠すべて必須。既定値があるので入力の手間は無い。軸が無い状態を許すと「今日何も出ない」が起こりうるため
- `Exercise.BodyweightFactor float64` — 0.0〜1.0。0 は自重が乗らない
- `EffectiveLoad(log *SetLog, e *Exercise, c ConditionLog) (Weight, bool)` — 記録された加重と体重から実効負荷を返すドメイン関数。係数が0の種目は記録された重量をそのまま返し、常に `true`。係数が0でない種目は、実施日以前で最も新しい体重を探す。見つからない、または実施日から42日より古いときは `false` を返し、そのセットは推定から除外される（従来の自重除外と同じ扱いになる）

### 変更

- `mainExercises(pool)` を廃止し、`Program.axes` が指す3種目を参照する形に置き換える
- 補助の候補を「`KindAccessory` の種目」から「軸の3種目を除いた全種目」に変える
- `OneRepMaxEstimator` は生の記録ではなく `EffectiveLoad` を通した負荷で推定する。そのために**種目マスタと体調ログを受け取れるようにする配線が要る**。今は `(History, ExerciseID, Date)` しか見ておらず、係数も体重も手元に無い。推定器そのものに引数を足すか、実効負荷に変換済みの履歴を渡すかは実装時に決める（どちらでも外から見た振る舞いは同じ）
- `SessionPlanner` は自重係数を持つ種目について、処方を加重に変換して返す。変換できない場合は重量なし（「自分で決める」）
- 軽い日は軸の種目を差し替えず、`LIGHT` スロットの強度・セット数・RIR をそのまま軸に適用する
- 「メイン種目が1つも無い」の検査は `Program.axes` が空かどうかで行う
- デロードの提案対象から、目標負荷が体重×係数を下回る種目を外す
- シードの `baseProfile` を測り直した値に置き換える

### 削除

- `internal/domain/training/variation_ratio.go` と対応するテスト
- `Exercise.DefaultRatioToMain` とシードの係数値
- `Exercise.MainLift` と `MainLift` 列挙
- `ExerciseKind` 列挙（`KindMain` / `KindVariation` / `KindAccessory`）と `Exercise.Kind`
- `SessionPlanner` から `VariationRatioResolver` への依存
- スロットの役割名 `RoleVariation`（`LIGHT` へ改名）
- シードの `mainLift()` / `variation()` / `accessory()` ヘルパを1つに統合
- `TestExercises_ContainsBigThree` / `TestExercises_VariationsBelongToAMainLift` / `TestExercises_EveryMainLiftHasAVariation`

## 移行

- `program` テーブルに軸3枠の列を足すマイグレーションを書く
- 既存レコードには既定値（胸=ベンチ、背中=チンニング、脚=スクワット）を入れる
- **バリエーション7種目を種目選択に追加する。**追加しないと `Kind` の抜け道が消えた時点で出てこなくなる
- **週目標を測り直した新しい既定に置き換える。**`baseProfile` を直しても、既存のプログラムは自分の週目標を保存して持っているので、置き換えないと古い数字のまま動く。BIG3前提で測った数字が残り、広背が満杯・ハムが赤字のまま固定される。手で調整していた場合は上書きになるが、単一利用者で未調整なので実害は無い
- 頻度は変わらない

**出てくるメニューは大きく変わる。**デッドリフトが軸から外れ、チンニングが軸に入り、補助の顔ぶれも週目標の測り直しで入れ替わる。「設定が変わらない」ことと「メニューが変わらない」ことは別なので、移行テストで担保するのは前者だけ。

**推定1RMは種目ごとに独立するので、ベンチとスクワットの提示重量は変わらない。**そこは移行テストで確かめる。

## テスト方針

- 軸の設定とバリデーション（選択にない種目を軸にできない、軸に指定された種目を選択から外せない、3枠すべて埋まっている、同じ種目を2つの枠に置けない）
- 既定の軸3種目がシードに存在すること（`ContainsBigThree` の置き換え）
- 移行後、バリエーション7種目が種目選択に入っていて補助として選ばれうること
- 軸候補の絞り込み（主働が同点のデッドリフトが脚と背中の両方に出る）
- 軸の種目が補助として二重に出ないこと
- 自重の推定（体重あり／体重が無い／体重が42日より古い の3通り）
- 処方が加重で出ること。目標負荷が体重×係数以下なら「自重」と出ること
- 体重が42日以内にあれば、当日に記録が無くても処方が出ること
- 落とせない自重種目にデロードが提案されないこと
- 種目ごとの1RM（床引きを一度もやらずにRDLの重量が出続けること）
- バリエーションの日に軸が差し替わらないこと
- 移行後、ベンチとスクワットの提示重量が変更前と一致すること
- `simulation_test.go` を代表的な軸構成で回し、週目標が到達可能でセッション長が妥当であること
- 変異テストで、上記が本当に検知されることを確かめる

## 今回やらないこと

### 分割法の可変化（次の仕様）

この設計の前に分割から入ろうとして、軸が置けないと成立しないことが分かったので順序を入れ替えた。**軸が置けるようになってから**入れる。決めた内容を保存しておく。

- **プリセットから選ぶだけ**にする。自分で組む画面は作らない
- 用意するのは **全身法 / 上下2分割 / PPL / 5分割** の4つ
- プリセットは「一周の並び」と「それぞれの日が担当する筋区分」を持つ
- 今日がどの日かは **今週N本目 ÷ 一周の日数 の余り** で決める。既存の `sessionIndexInWeek` をそのまま使う
- **重さの決め方は「その日が週に何回来るか」で既存の表を引く。**全身法は一周1日なので「その日が週に来る回数」＝「週に何回行くか」となり、**今と完全に同じ挙動**になる。表は1行も書き換えない
- 守るべき決まりが2つ。**21区分すべてがどこか1日に必ず属する**（属さないと週目標が永久に埋まらない）。**1区分は1日にだけ属する**（重複すると残差の割り算が二重になる）
- **日ごとに軸を明示する必要は無い。**軸が筋肉群ごとに決まるので、その日の担当筋肉群から軸が自動的に決まる
- 分割が入ると `maxFrequencyPerWeek = 4` の制約が外せる。この上限は「毎セッションBIG3すべてにスロットを割り当てる設計だから」置かれていたもので、分割を入れれば理由が消える
- 分割ごとに供給が変わるので、**週目標の測り直しは分割を入れるときにもう一度必要になる**

### 今日の画面の並び順

「どれから始めるか決まらない」の直接の手当て。**軸が先、補助はあと。補助は優先度順**（今はIDのアルファベット順で、優先度の情報が捨てられている）。軸が入ってから同時にやる方が手戻りが無い。

### 今週の見通し

「今週あと何回、次はどの日」を出す。分割が入ってから形が決まる。
