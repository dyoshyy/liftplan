# 軸種目の可変化と自重の扱い

## 背景

実際に使ってみて、**「BIG3が軸」という前提が本人の実態と合っていない**ことが2回続けて出た。

1. **ルーマニアンデッドリフト**をハムの種目としてやっており、床引きデッドリフトはほぼやらない。RDLはデッドリフトの「バリエーション」として登録されていて、重量は `床引きの1RM × 0.70` で出る。床引きをやらなければ推定は42日で古くなり、**RDLの重量が永久に「自分で決める」になる**。しかも床引きは毎回メニューに出続けて、毎回飛ばすことになる
2. **背中の日の軸は懸垂**。懸垂は「補助種目」として登録されており、しかも自重（0kg）のセットは推定から除外されるので、**推定するものが何も残らない**

どちらも例外ではなく、モデルの中心にある固定を突いている。`ExerciseKind` が `KindMain` を持ち、それが BIG3 に固定されていることが原因。

あわせて、「今日の画面が使いにくい」という話の出発点もここに繋がっていた。今日のリストは11種目36セットで、本人には**どれから始めるかが決まらない**。軸が置けないと、その日の起点が定まらない。

## 決めたこと

### 1. 軸の枠は筋肉群で固定、中身は選べる

枠は **胸・背中・脚 の3つ**。それぞれに種目マスタから1つ選ぶ。枠の数はユーザーが決めない。「決めなくていい」から遠ざからないため。

`ExerciseKind`（メイン/バリエーション/補助）は**触らない**。軸は `Program` 側の設定にして、種目の性質とは直交させる。こうすると補助として登録済みの懸垂をそのまま軸に置ける。種目マスタを書き換えずに済む。

既定値：

| 枠 | 既定 | 理由 |
|---|---|---|
| 胸 | ベンチプレス | 変更なし |
| 背中 | チンニング | 今の BIG3 には背中の軸が無い。新設なので既定を決める必要がある |
| 脚 | スクワット | 大腿四頭は最大の筋群 |

**デッドリフトは軸から外れる。**補助扱いになり、残差次第で出る。脚枠をRDLに変えれば後腿が軸に戻る。

**脚が1枠なので、スクワットとRDLの片方は補助に落ちる。**前腿と後腿を別枠にする案（4枠）も検討したが、枠を増やさない方を選んだ。

### 2. 軸に選べる種目の絞り込み

主働区分（`Stimulus` が最大の区分）が、その筋肉群に属する種目だけを候補に出す。

| 筋肉群 | 含む区分 |
|---|---|
| 胸 | `CHEST_UPPER` `CHEST_MID` `CHEST_LOWER` |
| 背中 | `LAT` `TRAP_MID` `TRAP_UPPER` `ERECTOR` |
| 脚 | `QUAD` `HAMSTRING` `GLUTE` `ADDUCTOR` `CALF` |

三角筋・腕・腹の9区分はどの筋肉群にも属さない。軸は大きい筋肉群だけに置き、残りは補助で埋める。

主働が同点の種目は**両方の候補に出る**。デッドリフトは `Hamstring 1.0` と `Erector 1.0` が同点なので、脚と背中の両方に出る。背中の日にデッドリフトを置く人がいるので、これは都合がよい。

軸に指定できるのは `Program.selected` に含まれる種目だけ。含まれない種目を軸にするのは矛盾なので、バリデーションで弾く。

### 3. 自重は「体重 × 係数 + 加重」で扱う

```
負荷 = 体重 × 係数 + 加重
```

種目に `BodyweightFactor`（0.0〜1.0）を持たせる。0 は「自重が乗らない」。

| 種目 | 係数 |
|---|---|
| チンニング (`pull_up`) | 0.95 |
| ディップス (`dip`) | 0.93 |
| バックエクステンション (`back_extension`) | 0.55 |
| 上記以外 | 0 |

**係数は力学的な正確さを狙っていない。**推定1RMは伸びを測るための相対値なので、**時間を通じて一貫していれば足りる**。絶対値がずれても、同じ係数で測り続ける限り推移は正しく出る。

**記録は加重のまま。**`SetLog` に入るのは「プレートを何kg付けたか」。体重を足すのは推定するときだけ。こうしないと「あの日は何kg付けたか」が記録から読めなくなる。

**処方も加重で出す。**

```
表示する加重 = 目標負荷 − 体重 × 係数
```

画面には `+5kg` と出る。体重込みの `82.5kg` と言われても何をすればいいか分からないため。差が0以下なら「自重」と出す。加重できないので、そこはレップ数で調整する領域。

**体重が記録されていない日**は、その日以前で最も新しい体重を使う。ただし **42日より古ければ使わない**（そのセットは推定から除外する）。42日は推定1RMが「古すぎる」と判定される既存の値で、新しい定数を増やさない。体重は日々ほとんど動かないので直近で代用でき、半年前の体重で計算する事故は防げる。

**当日の体重が分からない場合、自重種目の処方は「自分で決める」になる。**加重に変換できないため。体重はデロード判定にも要るので、記録を促す動機は既にある。

**過去のデータが遡って推定に入る。**今まで0kgの自重セットは捨てられていた。係数が入ると、その日の体重が記録されていれば推定できる。推移グラフの過去に点が増える。

### 4. 推定1RMは種目ごとに持つ。係数換算は廃止する

**バリエーションの重量を「メインの1RM × 係数」で出すのをやめる。**各種目が自分の記録から自分の1RMを持つ。

やめる理由：

- `variation_ratio.go` 145行 + テスト460行、**合わせて605行**を要する
- 対象は**バリエーション8種目だけ**
- 実測係数が効くには「同じ日に土台とバリエーションの両方をやる」を3セッション必要とする。それ未満はシードの固定値のままなので、ほとんどの場面で**汎用の定数を掛けているだけ**
- そして背景に書いた RDL の破綻は、**この仕組みがあるから起きていた**

RDLはRDLの記録から出す。それが一番正確で、土台が消える構造そのものが無くなる。

**`MainLift` は残すが、意味を狭める。**今は「何の代わりにやるか」と「どこから重量を出すか」の両方を担っている。後者を外して**前者だけ**にする。バリエーションの日にベンチをラーセンプレスに差し替える置換の対応表としては引き続き必要。

**一度もやったことがない種目の初回は「自分で決める」。**記録が無いので推定できない。初回1回ぶんの手入力と、605行および「係数」という概念を交換する取引。以降は自分の記録で自動になる。推測より記録、というこのアプリの筋にも合う。

## モデルの変更

### 追加

- `MuscleGroup`（`CHEST` / `BACK` / `LEG`）— 軸の枠を表す新しい列挙。各グループが含む `MuscleRegion` の対応表を持つ
- `Program.axes map[MuscleGroup]ExerciseID` — 3枠すべて必須。既定値があるので入力の手間は無い。軸が無い状態を許すと「今日何も出ない」が起こりうるため
- `Exercise.BodyweightFactor float64` — 0.0〜1.0。0 は自重が乗らない
- `EffectiveLoad(log *SetLog, e *Exercise, c ConditionLog) (Weight, bool)` — 記録された加重と体重から実効負荷を返すドメイン関数。係数が0の種目（自重が乗らない）は記録された重量をそのまま返し、常に `true`。係数が0でない種目は、実施日以前で最も新しい体重を探す。体重が見つからない、または実施日から42日より古いときは `false` を返し、そのセットは推定から除外される（従来の自重除外と同じ扱いになる）

### 変更

- `mainExercises(pool)`（`KindMain` で絞る関数）を廃止し、`Program.axes` が指す3種目を参照する形に置き換える
- `OneRepMaxEstimator` は生の記録ではなく `EffectiveLoad` を通した負荷で推定する
- `SessionPlanner` は自重係数を持つ種目について、処方を加重に変換して返す。変換できない場合は重量なし（「自分で決める」）
- 「メイン種目が1つも無い」の検査は `Program.axes` が空かどうかで行う

### 削除

- `internal/domain/training/variation_ratio.go` と対応するテスト
- `Exercise.DefaultRatioToMain` とシードの係数値
- `SessionPlanner` から `VariationRatioResolver` への依存

## 移行

- `program` テーブルに軸3枠の列を足すマイグレーションを書く
- 既存レコードには既定値（胸=ベンチ、背中=チンニング、脚=スクワット）を入れる
- 既存の設定（週3回・全身）は他に変わらない
- **既存の挙動が変わらないことをテストで示す。**胸枠=ベンチ、脚枠=スクワットのとき、提示重量が今と一致すること

## テスト方針

- 軸の設定とバリデーション（`selected` にない種目を軸にできない、3枠すべて埋まっている）
- 軸候補の絞り込み（主働が同点のデッドリフトが脚と背中の両方に出る）
- 自重の推定（体重あり／体重が無い／体重が42日より古い の3通り）
- 処方が加重で出ること。目標負荷が体重×係数以下なら「自重」と出ること
- 当日の体重が無いとき、自重種目の処方が「自分で決める」になること
- 種目ごとの1RM（床引きを一度もやらずにRDLの重量が出続けること）
- 移行後、ベンチとスクワットの提示重量が変更前と一致すること
- 変異テストで、上記が本当に検知されることを確かめる

## 今回やらないこと

### 分割法の可変化（次の仕様）

この設計の前に分割から入ろうとして、軸が置けないと成立しないことが分かったので順序を入れ替えた。**軸が置けるようになってから**入れる。決めた内容を保存しておく。

- **プリセットから選ぶだけ**にする。自分で組む画面は作らない
- 用意するのは **全身法 / 上下2分割 / PPL / 5分割** の4つ
- プリセットは「一周の並び」と「それぞれの日が担当する筋区分」を持つ
- 今日がどの日かは **今週N本目 ÷ 一周の日数 の余り** で決める。既存の `sessionIndexInWeek` をそのまま使う
- **重さの決め方は「その日が週に何回来るか」で既存の表を引く。**全身法は一周1日なので「その日が週に来る回数」＝「週に何回行くか」となり、**今と完全に同じ挙動**になる。表は1行も書き換えない
- 守るべき決まりが2つ。**21区分すべてがどこか1日に必ず属する**（属さないと週目標が永久に埋まらない）。**1区分は1日にだけ属する**（重複すると残差の割り算が二重になる）
- **日ごとにメインリフトを明示する必要は無い。**軸が筋肉群ごとに決まるので、その日の担当筋肉群から軸が自動的に決まる。デッドリフトの主働が同点で割り振れなかった問題もここで消える
- 分割が入ると `maxFrequencyPerWeek = 4` の制約が外せる。この上限は「毎セッションBIG3すべてにスロットを割り当てる設計だから」置かれていたもので、分割を入れれば理由が消える

### 今日の画面の並び順

「どれから始めるか決まらない」の直接の手当て。**メインが先、補助はあと。補助は優先度順**（今はIDのアルファベット順で、優先度の情報が捨てられている）。軸が入ってから同時にやる方が手戻りが無い。

### 今週の見通し

「今週あと何回、次はどの日」を出す。分割が入ってから形が決まる。

## 軸と種目選択の関係

**軸に指定されている種目は `Program.selected` から外せない。**外そうとしたらエラーにする。「軸を先に別の種目に変えてください」という順序を強制する。

外した瞬間に軸を既定へ戻す案も考えたが、やめた。ユーザーが意図していない軸の入れ替わりが黙って起きるうえ、既定に戻った結果また `selected` に無い種目が軸になるという循環が起きうる。エラーで止める方が短い。
