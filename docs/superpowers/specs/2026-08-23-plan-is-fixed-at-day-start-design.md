# 今日の計画は、その日の始まりに確定する

## 背景

`Plan` は補助種目の選択にだけ**当日の記録**を使っている。そのせいでリストがセッション中に動き、それを抑えるための仕組みが積み上がっていた。

いま `Plan` の中で当日を見ているのはここだけ。

| 場所 | 当日を見るか |
|---|---|
| 役割（今週N本目） | 見ない |
| メインの重量 | 見ない（D-086 で直した） |
| 補助の重量 | 見ない |
| **週の刺激量** `coveredThisWeek` | **見る** |
| **補助の候補** `unfinished` | **見る** |
| **補助の枠** `fitAccessories` | **見る** |

そして、これまで潰してきた不具合は**すべてこの1点から派生していた**。

| 決定記録 | 症状 | 当時の手当て |
|---|---|---|
| D-021 | 終えた補助が再提示され、セッションが終わらない | `unfinished` で候補から外す |
| D-087 | 1セット記録すると種目がリストから消える | 着手中は残す |
| D-087 | 記録するたびに並びが入れ替わる | 出力をIDの昇順で固定する |
| D-088 | 枠が補充されて60手やっても終わらない | 終えたぶん枠を減らす |

**症状を1つずつ潰していて、原因に触っていなかった。**

## 決めたこと

### 1. `Plan` は当日の記録を見ない

今日のリストは、**前日までの履歴**と**対象日**だけで決まる。一日中変わらない。

補助の選択に渡す残差も、前日までの刺激量から出す。

### 2. 表示は当日を含む

履歴タブの「今週の充足」は当日を含んだままにする。今日3セットやったら、その区分の実測が増えて見える。

計算しているのは `query.Stats.WeeklyVolume` で、`Plan` とは別経路（`CoverageBetween(h, pool, asOf.WeekStart(), asOf)`）。**変更しない。**

**表示と計画で基準が違う**ことになるが、意味が違うので正しい。表示は「今週どれだけやったか」、計画は「今日やると決めたこと」。後者が途中で動くほうがおかしい。

### 3. サーバーは「今日は終わり」を言わない

いまは補助が尽きると空が返り、それが暗黙の終了通知になっている。前日までで決めると、リストは一日中同じものが返る。

これは今日の画面の設計と噛み合う。**今日のリストはノルマではなく、上から消していって好きなところでやめられるキュー**、というのが本人の望んだ形だった。やめどきを決めるのは本人で、サーバーではない。

### 4. 消化状況は画面が持つ

「どこまでやったか」は画面が `/api/set-logs` から自前で組んでいる（緑のマス目はそれで塗っている）。**サーバーの `doneToday` は使っていない。**だから `Plan` が返さなくなっても画面は困らない。

## 消えるもの

```
performedOn        当日のセット数を種目ごとに数える
unfinished         今日ぶんを終えた種目を候補から外す
fitAccessories     枠に収める3つの規則
coveredThisWeek    当日を含む版（CoverageBetween は残る）
```

あわせて次も消える。

- `Plan` の「当日すでに記録済みのメインは、カバレッジに二重計上しない」例外。当日を見ないので二重計上が起きない
- 補助の出力を**IDの昇順に固定するソート**。並びが動かないので固定する必要がない

**`AccessorySelector` が返す順序（残差の大きい区分から）が、そのまま画面の並びになる。**「どれから始めるか決まらない」という不満が、ここで同時に解ける。

## モデルの変更

### `SessionPlanner.Plan`

- 残差を出すもとの刺激量を、当日を含まない範囲（週初から前日まで）で数える
- `AccessorySelector.Select` に渡す候補は、当日の消化状況で絞らない
- `fitAccessories` の呼び出しを外す
- 出力のソートを外す
- メインのカバレッジは常に加算する（当日の記録による例外を外す）

### 補助の枠

`MaxSlots`（8枠）は「その日にやる補助は最大8種目」という意味のまま。前日までで決まるので、`Select` が最大8件返して終わり。枠の再計算は要らない。

### 変えないもの

- `query.Stats.WeeklyVolume`（表示は当日を含む）
- `CoverageBetween`（期間を受け取る汎用の数え上げ）
- メインと補助の重量の出し方（もともと当日を見ていない）
- 役割の決め方（もともと当日を見ていない）
- デロードの提案と承認（当日の記録ではなく履歴と体調から決まる）

## テスト方針

**先に「一日中変わらない」を検査するテストを書く。**

> 同じ日について `Plan` を呼び、返ったリストを記録する。その日の記録を1セットずつ足しながら `Plan` を呼び直し、**種目の並びと数が最後まで一致すること**。

これが今回の受け入れ条件で、いまは通らない。

そのうえで、当時の不具合が形を変えて戻らないことを確かめる。

- 補助を1セット記録しても、その種目がリストから消えない（D-087 の症状）
- 補助を3セット記録しても、その種目がリストに残る（**挙動が変わる**。以前は消えていた）
- 記録を足しても並びが入れ替わらない（D-087 の症状）
- 補助の並びが残差の大きい区分の順になっている（新規）

**書き換えるテスト**

| テスト | いまの検査 | 直す先 |
|---|---|---|
| `SessionEndsAfterThePlannedWork` | 消化するとセッションが終わる | 削除。サーバーは終わりを言わなくなる |
| `AccessoriesComeBackInAStableOrder` | IDの昇順であること | 2回呼んで同じ順であること |
| `StartedAccessoriesDoNotJumpToTheTop` | 昇順が崩れていない | 着手の前後で順序が同じであること |
| `DoesNotDoubleCountTodaysMain` | 当日記録済みのメインを二重計上しない | 削除。当日を見ないので起きない |
| `DoesNotDoubleCountTodaysLogs` | 当日の記録で補助の数が変わらない | 残す（より強く成立する） |

**シミュレーション**

`simulation_test.go` は **1日につき `Plan` を1回しか呼ばない**（計画 → 全部こなす → 次の日）。セッション中に計画し直さないので、今回の変更では数字が動かない。動いたら、それは想定外の依存が残っているということなので理由を確かめる。

## 画面への影響

**変わらない。**画面は `/api/sessions` のリストを描き、緑のマス目は `/api/set-logs` から自前で塗っている。リストが一日中同じものになるだけで、コードの変更は要らない。

むしろ今より安定する。いまは「更新」を押すたびに並びが変わりうるが、変わらなくなる。

**終わったことは画面が言える。**サーバーが終了を宣言しなくなる代わりに、画面は「全部のマスが緑か」で完了を判定できる。いまその表示は無いが、必要になったら画面側だけで足せる。サーバーに戻す必要は無い。

## 今回やらないこと

**補助の並びに優先度を出す件（①）は、この変更に吸収される。**別途やる必要が無くなった。IDの昇順ソートを外せば、`AccessorySelector` の優先度順がそのまま出る。

**`unfinished` と `AccessorySelector.Select` の二重絞り込みの整理（④）**は、`unfinished` ごと消えるのでこれも吸収される。

## 想定していない使い方への影響

**1日に2回ジムへ行く場合。**`sessionIndexInWeek` は日付の種類を数えるので、2回目も同じ「今週N本目」になる。今回の変更の前後で挙動は変わらない（もともとそうだった）。

**セッション中に設定を変えた場合。**プログラムを保存すると計画は変わる。これは本人の明示的な操作なので、動いてよい。デロードの承認も同じ（クエリパラメータで渡す明示的な操作）。

**補助を予定より多くやった場合。**リストは変わらない。予定を超えたセットは画面が「4セット目・追加」として出す（D-102）。

## 持ち越し

- `MaxSlots`（8枠）が今の値でよいかは別の話。前日までで決めると、8種目すべてが最初から見えることになる。多いと感じたら枠を減らす調整をする
