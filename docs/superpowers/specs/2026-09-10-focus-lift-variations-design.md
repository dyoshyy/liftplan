# 重点種目のバリエーションを独立したレーンにする

`2026-09-06-training-goals-design.md`（D-117）の続き。軸を1セッション1つに
絞ったあと、**実際の運用と噛み合わない部分が1つ残った**ので足す。

## 背景

D-117 の実装が終わったあと、本人の実際の週を突き合わせた。

```
月 upper   ベンチ（ヘビー）＋ 胸の種目
火 lower   スクワット
木 upper   ベンチ ＋ 背中（チンニングがメイン）
金 lower   RDL
土 upper   ベンチ ＋ 肩
```

**ベンチだけが週3回出ている。**他の宣言（スクワット・RDL・チンニング）は週1回。

軸は各セッション1つで、宣言4つ・週5回なら**各種目が軸になるのは週1回ずつ**。
ここは実態と合っている。合っていないのは「ベンチが残り2回どう出るか」。

いまは**補助として出ている**。胸の週目標が大きいので、残差を埋める種目として
ベンチが選ばれる。だが補助レーンは「残差を埋める」ためのもので、
**「この種目を重点的に伸ばす」という意図を表していない**。たまたま
残差の都合で出ているだけなので、週目標を変えると消えうる。

## 決めたこと

### 1. レーンを3つに分ける

| レーン | 何を出すか | 何が決めるか |
|---|---|---|
| **軸** | 宣言（BIG4）から1つ | 最終実施日が最も古いもの |
| **バリエーション** | 重点種目の系統から1つ | 前回から中1日以上空いているか |
| **補助** | **宣言を除いた全種目** | 区分の残差 |

補助レーンが兼務していた「重点種目を高頻度で回す」を独立させる。

**あわせて、宣言した種目を補助の候補から外す。**

D-117 の実装（PR #50）では「宣言した種目も、ヘビー枠でなければ補助として
残差を埋める」とした。**バリエーションレーンが無かったから必要だった判断**で、
レーンができれば要らない。

そのとき根拠にした「除きすぎると脚の日にスクワットがどこにも出なくなる」は
的外れだった。スクワットが軸でない日に脚のボリュームを埋めるのは
レッグプレスやレッグカールであって、スクワットである必要が無い。

**宣言は軸レーンで扱うもの**と割り切るほうが、レーンの境界がきれいになる。

### 2. 重点種目は本人が1つ選ぶ

宣言の中からさらに1つ。**ノブが1つ増える。**

「何を最も伸ばしたいか」は本人にしか決められない。アプリが答えるべき問い
（何kgでやるか・補助を何にするか）ではないので、これは許容する。

### 3. 間隔は中1日以上

前回その系統をやってから**中1日以上空いていれば**出す。月曜にやったら
水曜以降。**日数を設定させない。**

設定させると却下した「種目ごとの週N回」に戻る（D-117）。定数で持ち、
`AccessorySelector` の `recoveryDays = 2` と同じ形になる。

**「48時間」とは書かない。**記録が持つのは日付だけで時刻が無いので
（`SetLog.PerformedOn` は年月日）、時間で判定しようがない。日付の差で
数える。

軸が重点種目そのものの日は、バリエーションを出さない。同じ系統を1日に
2回やることになるため。

### 4. 重量はバリエーション自身の推定1RM × 強度%

D-113 で「推定1RMは種目ごとに持つ。係数換算をやめる」と決めた。
**対応表は戻すが、係数は戻さない。**

ラーセンプレスはラーセンプレスの記録から推定する。初回は記録が無いので
「自分で決める」になる。以降は自分の記録で自動になる。

`Intent`（STANDARD / HEAVY / LIGHT）も軸と同じ仕組みで付く。ラーセンプレスの
81% はベンチの 81% より軽くなる（推定1RMが低いため）ので、自然に
「メインより軽い日」になる。

## D-114 を覆す

`MainLift`（バリエーションの対応表）は削除済み。**戻す。**

> 係数が消えたら役目が1つしか残らず、それも要らなかった（D-114）

### 何が変わったか

D-114 の時点では、**毎セッションで宣言した種目すべてに処方が付いていた**。
ベンチは毎回出るので、「軽い日にラーセンプレスへ差し替える」以外に
対応表の使い道が無かった。

D-117 でヘビー枠が1セッション1つになり、**重点種目を高頻度で回す枠が
無くなった**。対応表はその枠を埋めるために要る。

### 戻すのは「派生の関係」だけ。旧 `MainLift` の形は引き継がない

- **戻す**：どの種目がどの種目の派生か（ラーセンプレスはベンチの派生）
- **戻さない**：対メイン係数（D-113）。バリエーションは自分の記録から推定する
- **戻さない**：`ExerciseKind`（D-117）。種目の種別という考え方そのもの

**旧 `MainLift` の設計は良くなかった。引っ張られないこと。**

```go
// これが旧実装。真似しない。
type MainLift string
const (
	LiftSquat    MainLift = "SQUAT"
	LiftBench    MainLift = "BENCH"
	LiftDeadlift MainLift = "DEADLIFT"
)
```

問題は3つ。

1. **列挙型なので BIG3 に固定されていた。**チンニングを派生の親にしたければ
   列挙値を増やすことになる。D-117 で「軸は BIG3 に固定されない」と決めた
   のに、対応表だけ固定のまま残る
2. **種目マスタが「どれがメインか」を知っていた。**メイン/補助は種目の性質
   ではなく利用者の目標だった、というのが D-117 の結論。列挙の値が
   `SQUAT` / `BENCH` / `DEADLIFT` である時点で、マスタが目標を持っている
3. **名前が「軸」と紛らわしい。**`MainLift` と「メイン種目」と「軸」が
   同じものを指したり指さなかったりしていた

いま要るのは**種目どうしの関係**であって、種目の分類ではない。「ラーセン
プレスはベンチの派生」を表せればよく、その親が BIG3 である必要も、
列挙で数え上げる必要もない。

## モデルの変更

### 追加

- `Exercise.Family ExerciseID` — その種目が属する系統。空なら系統に属さない。
  マスタの静的データ
- `Program.focus ExerciseID` — 重点種目。宣言の部分集合（`focus ∈ declared`）
- バリエーションレーンの導出（`planning`）

### 変更

- `Plan` にレーンを1つ足す。`PlannedSession` に `variation []PlannedSet`
- `AccessorySelector.Select` の `exclude` に、**今日のヘビー枠だけでなく
  宣言全部と今日のバリエーション**を渡す
- API の応答に `variation` を追加
- 設定画面に「重点種目」の選択

### シードの系統

| 系統 | 属する種目 |
|---|---|
| `bench` | `larsen_press` / `tempo_bench` / `close_grip_bench` |
| `squat` | `pause_squat` / `front_squat` |
| `deadlift` | `deficit_deadlift` / `romanian_deadlift` |

**RDL は宣言にも入りうる。**本人は RDL をハムの種目として常用しており、
床引きデッドリフトはやらない。系統に属することと、宣言に入ることは
両立する——系統は「どの種目の派生か」、宣言は「伸ばしたいかどうか」で、
別の軸。

## 受け入れ条件

- 重点種目をベンチにすると、**ベンチ系統が週3回前後**出る（軸1回 + バリエーション2回）
- 前回から中1日空いていない日（翌日）には、バリエーションが出ない
- 軸がベンチの日には、バリエーションが出ない
- バリエーションの重量は**その種目自身の記録**から出る。記録が無ければ「自分で決める」
- 重点種目を指定しなければ、バリエーションレーンは空（**既定は指定なし**）
- **宣言した種目が補助として出ない。**軸かバリエーションでしか現れない

## やらないこと

**バリエーションを複数出す。**1セッション1つ。増やす理由が出てから。

**間隔を設定させる。**中1日は定数。

**系統ごとに別の間隔を持たせる。**スクワット系は回復が遅いから4日、
のような区別はしない。重点種目は1つなので、いま差がつく場面が無い。

**対メイン係数。**D-113 の判断は覆さない。

## 検証が要る点

宣言を補助から外すと、**その区分のボリュームが減る**。胸はベンチ（軸2回）と
バリエーション（1回）で埋まるが、脚はスクワットが軸の1回だけになり、
残りはレッグプレスなどが埋めることになる。

**シミュレーションで達成率を見てから決める。**足りなければ、週目標を
測り直すか、補助のスロット上限を上げる。

## どのバリエーションを選ぶか

**軸と同じ「最終実施日が最も古いもの」。**ベンチ系が3つあれば、ラーセン →
テンポ → ナロー → ラーセン…と順に回る。

軸の選定と同じ規則にするのは、閾値を持ち込まないため。「N日より古く
なったら出す」を書いた瞬間、却下した「種目ごとの週N回」に戻る（D-117）。
比較だけを使い、判定は置かない。
