# 重点種目のバリエーションを独立したレーンにする

`2026-09-06-training-goals-design.md`（D-117）の続き。軸を1セッション1つに
絞ったあと、**実際の運用と噛み合わない部分が1つ残った**ので足す。

## 背景

D-117 の実装が終わったあと、本人の実際の週を突き合わせた。

```
月 upper   ベンチ（ヘビー）＋ 胸の種目
火 lower   スクワット
木 upper   ベンチ ＋ 背中（チンニングがメイン）
金 lower   RDL
土 upper   ベンチ ＋ 肩
```

**ベンチだけが週3回出ている。**他の宣言（スクワット・RDL・チンニング）は週1回。

軸は各セッション1つで、宣言4つ・週5回なら**各種目が軸になるのは週1回ずつ**。
ここは実態と合っている。合っていないのは「ベンチが残り2回どう出るか」。

いまは**補助として出ている**。胸の週目標が大きいので、残差を埋める種目として
ベンチが選ばれる。だが補助レーンは「残差を埋める」ためのもので、
**「この種目を重点的に伸ばす」という意図を表していない**。たまたま
残差の都合で出ているだけなので、週目標を変えると消えうる。

## 決めたこと

### 1. レーンを3つに分ける

| レーン | 何を出すか | 何が決めるか |
|---|---|---|
| **軸** | 宣言（BIG4）から1つ | 最終実施日が最も古いもの |
| **バリエーション** | 重点種目の系統から1つ | 前回から48時間経過しているか |
| **補助** | 残りの全種目 | 区分の残差 |

補助レーンが兼務していた「重点種目を高頻度で回す」を独立させる。

### 2. 重点種目は本人が1つ選ぶ

宣言の中からさらに1つ。**ノブが1つ増える。**

「何を最も伸ばしたいか」は本人にしか決められない。アプリが答えるべき問い
（何kgでやるか・補助を何にするか）ではないので、これは許容する。

### 3. 間隔は48時間

前回その系統をやってから中1日空いていれば出す。**日数を設定させない。**

設定させると却下した「種目ごとの週N回」に戻る（D-117）。48時間は定数で、
`AccessorySelector` の `recoveryDays = 2` と同じ考え方。

軸が重点種目そのものの日は、バリエーションを出さない。同じ系統を1日に
2回やることになるため。

### 4. 重量はバリエーション自身の推定1RM × 強度%

D-113 で「推定1RMは種目ごとに持つ。係数換算をやめる」と決めた。
**対応表は戻すが、係数は戻さない。**

ラーセンプレスはラーセンプレスの記録から推定する。初回は記録が無いので
「自分で決める」になる。以降は自分の記録で自動になる。

`Intent`（STANDARD / HEAVY / LIGHT）も軸と同じ仕組みで付く。ラーセンプレスの
81% はベンチの 81% より軽くなる（推定1RMが低いため）ので、自然に
「メインより軽い日」になる。

## D-114 を覆す

`MainLift`（バリエーションの対応表）は削除済み。**戻す。**

> 係数が消えたら役目が1つしか残らず、それも要らなかった（D-114）

### 何が変わったか

D-114 の時点では、**毎セッションで宣言した種目すべてに処方が付いていた**。
ベンチは毎回出るので、「軽い日にラーセンプレスへ差し替える」以外に
対応表の使い道が無かった。

D-117 でヘビー枠が1セッション1つになり、**重点種目を高頻度で回す枠が
無くなった**。対応表はその枠を埋めるために要る。

### 戻すのは対応表だけ

- **戻す**：どの種目がどの系統に属するか（ベンチ → ラーセン・テンポ・ナロー）
- **戻さない**：対メイン係数（D-113）。バリエーションは自分の記録から推定する
- **戻さない**：`ExerciseKind`（D-117）。種目の種別ではなく、系統の対応表

## モデルの変更

### 追加

- `Exercise.Family ExerciseID` — その種目が属する系統。空なら系統に属さない。
  マスタの静的データ
- `Program.focus ExerciseID` — 重点種目。宣言の部分集合（`focus ∈ declared`）
- バリエーションレーンの導出（`planning`）

### 変更

- `Plan` にレーンを1つ足す。`PlannedSession` に `variation []PlannedSet`
- API の応答に `variation` を追加
- 設定画面に「重点種目」の選択

### シードの系統

| 系統 | 属する種目 |
|---|---|
| `bench` | `larsen_press` / `tempo_bench` / `close_grip_bench` |
| `squat` | `pause_squat` / `front_squat` |
| `deadlift` | `deficit_deadlift` / `romanian_deadlift` |

**RDL は宣言にも入りうる。**本人は RDL をハムの種目として常用しており、
床引きデッドリフトはやらない。系統に属することと、宣言に入ることは
両立する——系統は「どの種目の派生か」、宣言は「伸ばしたいかどうか」で、
別の軸。

## 受け入れ条件

- 重点種目をベンチにすると、**ベンチ系統が週3回前後**出る（軸1回 + バリエーション2回）
- 前回から48時間経っていない日には、バリエーションが出ない
- 軸がベンチの日には、バリエーションが出ない
- バリエーションの重量は**その種目自身の記録**から出る。記録が無ければ「自分で決める」
- 重点種目を指定しなければ、バリエーションレーンは空（**既定は指定なし**）

## やらないこと

**バリエーションを複数出す。**1セッション1つ。増やす理由が出てから。

**間隔を設定させる。**48時間は定数。

**系統ごとに別の間隔を持たせる。**スクワット系は回復が遅いから4日、
のような区別はしない。重点種目は1つなので、いま差がつく場面が無い。

**対メイン係数。**D-113 の判断は覆さない。

## 未確定

**どのバリエーションを選ぶか。**系統に複数あるとき（ベンチ系は3つ）、
軸と同じ「最終実施日が最も古いもの」でよいか。実装時に決める。

**補助レーンとの重複。**バリエーションで出した種目が、同じ日に補助でも
選ばれうる。軸と同じように `exclude` へ渡すことになる。
