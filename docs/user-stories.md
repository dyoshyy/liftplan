# ユーザーストーリー

利用者は1人（本人）。使う場面は「ジムにいる30秒」と「週のどこかで振り返る5分」の2つで、
必要なものがまったく違う。

ジムでは**判断を減らす**ことが価値になる。振り返りでは**判断の材料を出す**ことが価値になる。
同じ画面で両方をやろうとすると、どちらも中途半端になる。

## A. ジムに着いたとき

| | ストーリー | 満たすもの |
|---|---|---|
| A1 | 開いた瞬間に、今日やる種目が並んでいる | `GET /api/sessions` |
| A2 | 各種目の重量が決まっていて、自分で計算しない | 同上 |
| A3 | 前回その種目で何kgを何レップ挙げたかが見える | `last_performances` |
| A4 | 種目が日本語で表示される | `GET /api/exercises` |
| A5 | 今日が何の枠か分かる（軸・バリエーション・補助） | レーンの見出し |

A3 が無いと、提示された重量を信じる根拠が無い。「今日92.5kg」と言われても、
前回90kgで潰れたのか余裕だったのかで、やることが変わる。

A5 は当初「種目に HEAVY バッジを付ける」だったが、狙いがレーンごとの定数になった時点で
**種目ではなく枠の性質**になったので、見出しに移した（D-126）。

## B. セットをこなす間

| | ストーリー | 満たすもの |
|---|---|---|
| B1 | 1セット終わったら数タップで記録できる | 画面 |
| B2 | 実際のレップが計画と違っても記録できる | `POST /api/set-logs` |
| B3 | どこまでやったかが、画面を閉じても残る | `GET /api/set-logs` |
| B4 | 電波が切れても記録が失われない | 待ち行列（D-079 / D-107） |
| B5 | 打ち間違いを直せる | `DELETE /api/set-logs/{id}`（D-081）。過去の日は履歴から |
| B6 | 器具が埋まっていたら順番を飛ばせる | 画面（順序は表示だけ） |
| B7 | セット間の休憩を計る | 休憩タイマー（下記） |
| B8 | 予定に無い種目を、自分で選んで記録できる | 今日の画面の「種目を選んで記録」。`POST /api/set-logs` は手元の種目一覧にある種目なら受ける |

B3 は地味だが実運用では効く。スマホは勝手に閉じる。開き直して
「3セット目まで終わったんだっけ？」となると、記録が信用できなくなる。

B8 は、器具が埋まっていて予定の種目ができない日や、予定に無い種目をやりたい日のための
逃げ道。何kgで何セットやるかは本人が決めるので、処方は出さない（重量は「自分で決める」、
セットは記録のたびに次の空き枠が出る）。記録した分は、ほかの記録と同じく推定1RMと
週目標の充足に数えられる。選んだ状態は画面を開き直すと消えるが、記録は「今日やったもの」に残る。

B5 が無いと打ち間違いを直す手段がゼロになる。同じIDで直そうとすると 409 で弾かれ（D-060）、
別IDで正しい値を入れても間違った記録が推定1RMを汚し続ける。

## C. トレーニング後

| | ストーリー | 満たすもの |
|---|---|---|
| C1 | 体重・睡眠を記録できる | `POST /api/conditions` |
| C2 | 今日こなした総量が分かる | **出していない**。今日の画面のマスを見れば数えられる |

## D. 週のどこかで振り返る

| | ストーリー | 満たすもの |
|---|---|---|
| D1 | 過去のセッションを日付順に見られる | 履歴の画面（D-127）。月ごとに送る |
| D2 | 種目ごとの推定1RMの推移が見える | `GET /api/stats` |
| D3 | 週目標に対してどれだけ埋まったかが分かる | 同上 |

D2 は「伸びているか」を答える唯一の線。体感は当てにならない。

D3 は**このアプリの中心概念**で、これが見えないと「なぜ今日この補助種目が出たのか」が
分からない。週目標と残差で補助を選んでいるのに、利用者はその存在すら見えない状態だった。

**既知の見え方の問題。**「今週の充足」は埋まっていない順に並べる設計なので、記録があっても
先頭に 0.0 が並び「何も記録されていない」に読める。仕様どおりなので変えていない。

## E. 設定

| | ストーリー | 満たすもの |
|---|---|---|
| E1 | 使う種目を選べる | 「今日」の末尾の `ProgramSettings` |
| E2 | 週に通う回数・週目標を変えられる | 同上 |
| E3 | 伸ばしたい種目・重点種目を選べる | 同上 |
| E4 | 分割法をプリセットから選べる | 同上 |
| E5 | トークンを入れ替えられる／消せる | 設定画面 |

**1フィールドずつの口を叩く。**全置換の `PUT /api/program` はクライアントから呼ばない。
欠落したフィールドが黙って初期値に戻る事故を実際に踏んだ（D-127）。

**自分で組む画面は作らない。**分割法はプリセットから選ぶだけ。設定項目が増えるほど、
消したかった判断が戻ってくる。

## 出さないと決めたもの

- **カレンダー表示**。未来のセッションは保存しない設計なので、未来の枠は描けない。
  描けるのは過去だけで、それは履歴の一覧で足りる
- **グラフの作り込み**。推移は折れ線1本で足りる。軸や凡例を足すほど、
  ジムで一瞬見るものから遠ざかる
- **前回との差分バッジ**。レーンが違えば重量が違うのは当然で、「増えた＝良い」という
  誤った要約になる（D-084）

### 休憩タイマーは覆した

当初は「RIR は止め時の指示であって秒数ではない。タイマーを置くと『2分たったから次』という
運用に寄り、設計思想と衝突する」として出さないと決めていた。**入れた。**

止め時を指示するのは RIR で、休憩の長さはそれとは別の軸だった。**RIR を守るには
十分に休む必要がある**ので、タイマーはむしろ RIR を守るための道具になる。

**経過は「いま − 開始時刻」で計算し直す。**数え続ける実装にすると、画面をバックグラウンドに
回したあいだ JS のタイマーが止まり、復帰したときに止まっていた分だけ長く残る。
**ジムでは画面を消すので必ず踏む。**
